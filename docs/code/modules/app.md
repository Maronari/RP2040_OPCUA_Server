# Модуль: `app/`

## Назначение

Связывает всю прошивку воедино: инициализация платформы, создание задач
FreeRTOS и единственная точка входа `main()`. Сам `app/` не определяет
целей сборки — `app/CMakeLists.txt` содержит только
`add_subdirectory(basic_profile)`. Всё реальное содержимое находится в
`app/basic_profile/`.

## Публичный API

Отсутствует — это конечный исполняемый файл верхнего уровня, а не
библиотека, с которой линкуется другой код. Его единственный «интерфейс» —
это цель(и) сборки CMake, которые он производит.

## Внутренняя реализация

`main()` ([app/basic_profile/main.c:582](../../../app/basic_profile/main.c))
намеренно делает немного: инициализация тактового генератора/светодиода/
stdio/ожидания USB/аллокатора PSRAM/кучи lwIP, затем создаёт одну
загрузочную задачу (`InitTask`) и запускает планировщик FreeRTOS. Вся
инициализация хранения/сети/сервисов/OPC UA и создание всех шести рабочих
задач происходит внутри `InitTask` (`app_init_task`, `main.c:432-580`) —
полную последовательность и классификацию каждого сбоя инициализации
(фатальный/только логируемый) см. в [startup-flow.md](../startup-flow.md).

`app_acknowledge_ota_boot_if_needed()` (`main.c:274-289`) и
`app_log_ota_state()` — две точки соприкосновения `app/` с конечным
автоматом состояния OTA — см.
[ota-bootloader.md](../ota-bootloader.md#health-confirmation-and-rollback--current-gap).
`watchdog_task` (`main.c:416-430`), единственная функция-точка входа
задачи, живущая непосредственно в `app/`, а не в `services/`, также
определена здесь.

`ota_layout_sanity.c` не содержит кода времени выполнения — это чистый
файл с проверками `_Static_assert`, подтверждающий, что сгенерированная
раскладка областей Flash для OTA (загрузчик/банк A/банк B/журнал/история/
конфигурация/слоты безопасности/состояние OTA) выровнена по границе
стирания и не содержит пересечений.

## Зависимости

`FIRMWARE_DRIVERS`, `FIRMWARE_SERVICES`, `PSRAM_ALLOCATOR`, `OTA_SHARED`,
`OTA_FLASH_BACKEND_APPLICATION` и (если не задано
`W5X00_DIAGNOSTIC_NO_OPCUA`) `OPCUA_DEVICE_MODEL`. Полный граф целей CMake
см. в [build-system.md](../build-system.md).

## Зависимые модули

Отсутствуют — `app/basic_profile` производит конечную(ые) исполняемую(ые)
цель(и); ничто с ним не линкуется.

## Владение состоянием

Нет постоянного состояния уровня модуля, кроме локальных статических
переменных внутри `main.c` (`g_watchdog_kick_enabled`, учёт состояния
задачи наблюдения за сторожевым таймером). Всё энергонезависимое
состояние принадлежит `services/`.

## Контекст выполнения

Запускается первым, на ядре 0, до старта планировщика; затем `InitTask`
выполняется с приоритетом 4 (наивысший прикладной приоритет) и
самоудаляется по завершении своей последовательности.

## Синхронизация

Ничего не принадлежит модулю напрямую — `app/` только создаёт задачи;
состояние, которое эти задачи затрагивают, синхронизируется
модулем-владельцем — сервисом или драйвером.

## Аппаратные ресурсы

Косвенно, через драйверы, которые он инициализирует последовательно:
системный тактовый генератор, GPIO светодиода, аллокатор PSRAM, сторожевой
таймер (взводится здесь, до появления `OpcUaTask` — см.
[startup-flow.md](../startup-flow.md#notable-ordering-observations-as-implemented-not-fixed-by-this-pass)).

## Персистентное состояние

Не принадлежит напрямую; при загрузке считывает (но не сбрасывает)
состояние OTA через `app_log_ota_state()`, затем безусловно сбрасывает его
через `app_acknowledge_ota_boot_if_needed()` после того, как все рабочие
задачи созданы.

## Поведение при сбоях

Полную таблицу «фатальный/только логируемый» см. в
[startup-flow.md](../startup-flow.md). Сам `main()` уходит в фатальную
ловушку (`app_fault_trap`) только при сбое `lwip_psram_heap_init()` и при
сбое создания `InitTask`.

## Связанные тесты

Отдельного каталога `static/tests/` для самого `app/` нет;
`test_bootloader_handoff.py` и `test_opcua_logging_source.py` — ближайшие
статические проверки контракта исходного кода, затрагивающие поведение
загрузки/логирования этого слоя.
