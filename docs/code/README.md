# Документация по коду

Инженерная карта прошивки первой стороны RP2350 + W5500 OPC UA: FreeRTOS,
lwIP, open62541, PSRAM и собственный загрузчик OTA. Документирует кодовую
базу в том виде, в каком она существует на ветке `docs/architecture-map`
(картирование выполнено по тому же дереву, что и
`refactor/opcua-model-modularization`), текущая цель релиза — `v0.5.0`
согласно [ROADMAP.md](../../ROADMAP.md).

Сначала прочитайте [AGENTS.md](../../AGENTS.md) и
[ROADMAP.md](../../ROADMAP.md) — это авторитетные правила для контрибьюторов
и план релиза. Этот каталог документирует **что делает код**, а не что
предстоит собрать дальше.

## Как это было создано

Шесть параллельных проходов картирования только для чтения (по одному на
каждую основную подсистему: app/boot, drivers, services, opcua_model,
OTA/загрузчик, сборка/тесты) напрямую изучили исходный код и подтвердили
каждое утверждение ссылкой `path:line`. Извлечение топологии на основе
регулярных выражений (`docs/code/topology/`) дополняет вручную проверенные
диаграммы графом зависимостей на уровне файлов. Подробности об
инструментарии и ограничениях — внизу этой страницы.

**Каждая диаграмма и таблица здесь отражает исходный код, который был
фактически прочитан.** Там, где вызов можно было достичь только через
указатель на функцию, коллбэк, установленный ISR, или диспетчеризацию,
выбираемую драйвером, и он не мог быть полностью разрешён, исходный
документ прямо говорит об этом («не подтверждено статически»), а не
утверждает это как факт.

## Машиночитаемый граф

`docs/code/topology/topology.json` (схема: дерево система → домен → модуль,
плюс `edges`/`entryPoints`/`deadEnds`/`observations`) и интерактивный
просмотрщик `docs/code/topology/TOPOLOGY.html` — откройте HTML-файл прямо в
браузере. Сгенерирован специально написанным экстрактором на регулярных
выражениях (`extract_topology.py`, не закоммичен — одноразовый
вспомогательный скрипт), **не** настоящим парсером C: он разрешает вызовы к
первому одноимённому определению функции в любом месте исходников первой
стороны, поэтому может неверно атрибутировать вызовы между одноимёнными
функциями в разных файлах, и вообще не видит диспетчеризацию через
указатели на функции/vtable (именно поэтому [call-graphs.md](call-graphs.md)
и документы по модулям существуют как проверенный вручную источник истины —
относитесь к графу JSON как к грубому вспомогательному средству навигации, а
не источнику для цитирования).

## Инструментарий, использованный для этого прохода

- **Шесть параллельных субагентов `general-purpose`**, каждый только для
  чтения, по одному на подсистему (app/boot, drivers, services,
  opcua_model, OTA/загрузчик, сборка/тесты), подтверждающих каждое
  утверждение ссылкой `path:line`.
- **Скилл `/modernize-map` плагина `code-modernization`** — вызван только
  для получения рекомендаций по картированию топологии/зависимостей
  (функции трансформации не использовались); его вывод представлял собой
  общий многостековый шаблон, адаптированный в специально написанный выше
  скрипт `extract_topology.py`, поскольку ориентированные на
  COBOL/мейнфреймы правила извлечения шаблона не подходили для кодовой
  базы на C/CMake.
- **`compile_commands.json`** существует в `build/compile_commands.json`
  (сгенерирован предыдущей конфигурацией CMake), но не использовался
  напрямую — в этом окружении не были доступны
  `clangd`/`clang`/`ctags`/`cscope`/`cflow` (только `cppcheck` и
  `ripgrep`), поэтому проверка графа вызовов опиралась на прямое чтение
  исходного кода и поиск, а не на семантический индекс. Структурный
  MCP-сервер графа кода (`code-cortex-mcp` или аналог) был проверен на
  доступность и не установлен и не доступен как пакет npm в этом
  окружении; вместо этого использовался проход картирования шестью
  read-only субагентами.
- **Локальные для проекта агенты Claude Code**, созданные в `.claude/agents/`:
  `code-mapper`, `embedded-architecture-mapper` (структурный/встраиваемый
  анализ только для чтения), `documentation-writer` и
  `documentation-reviewer` (ограничены `docs/code/**`), для использования в
  будущих проходах поддержки документации.

## Ограничения этого прохода

- У `security_service.c`, `security_state_service.c`, `network_manager.c`,
  `time_service.c` и `diag_service.c` заголовки были прочитаны полностью, но
  тела `.c`-файлов — лишь частично; утверждения о писателях/читателях
  глобального состояния для этих файлов помечены в
  [state-ownership.md](state-ownership.md) как «не прочитано в рамках этого
  прохода», а не заявлены как факт.
- Около 50 тел коллбэков методов в `model_ota.c`/`model_security.c` были
  подтверждены как делегирующие сервисам структурно (по наличию `#include`
  и выборочным проверкам), но не каждое было прочитано построчно.
- В рамках этой документационной задачи сборка не выполнялась, проверка на
  оборудовании/через UaExpert не проводилась — это исключительно
  документация исходного кода.
- Внутренности сторонних компонентов (`libraries/`, `open62541_v1.5.3/`,
  `port/*` за пределами границы вызова первой стороны) намеренно не
  анализировались, согласно области задачи.
