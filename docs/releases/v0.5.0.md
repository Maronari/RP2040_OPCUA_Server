# v0.5.0 — Transactional Runtime Configuration

## Contract

Baseline: merged `v0.4.3` on `main`, merge commit
`dec08ba22e835e8037f9fd5342dcc63ddc03f5ac` (PR #17,
`v0.4.3/history-hardening` → `main`) — this is `ROADMAP.md`'s own designated
baseline citation (section 8, "Immediate next action", added on `main` after
this plan's initial draft; confirmed byte-identical to this plan's v0.5.0
scope otherwise). Implementation branch `v0.5.0/transactional-config` is cut
from `origin/main` HEAD at merge commit `fe33c0f` (PR #18,
`docs/doxygen-coverage-pass` → `main`), which is a strict descendant of
`dec08ba2` adding only documentation (Doxygen pass, architecture docs,
industrial-hardware-qualification roadmap sections) — confirmed zero
non-Markdown diff between this plan's original mapping baseline and the
branch point.

Make one firmware image safely reconfigurable for multiple device profiles.
Add an explicit configuration schema version with migration functions,
restructure the existing candidate/active configuration pipeline into a real
validate→persist-staged→stop→activate→verify→commit/rollback transaction
with a last-known-good fallback, add exhaustive missing-driver reporting,
give history/alarm services a way to clear per-channel state on
delete/modify, and wire the already-computed "reboot required" diagnostic to
an actual controlled OPC UA server restart. Add profile presets (sensor
node, remote I/O, development/benchmark) as runtime configuration presets,
distinct from the compile-time driver packs in `ROADMAP.md` section 5.1.

Preserve all unrelated v0.4.3 public NodeIds, BrowseNames, Method
signatures, EventTypes, permissions and externally visible behavior except
where this release's contract explicitly changes it (schema version field
semantics, reboot-required diagnostic becoming an actual restart trigger,
per-channel history/alarm state lifecycle on delete/modify).

This release may extend internal service and OPC UA adapter APIs where
required. It must not implement OPC UA Part 11 Historical Event Access
(v0.8.1), a Driver SDK or new reference drivers (v0.5.1), resource/benchmark
instrumentation (v0.5.2), dynamic native-driver loading (explicitly deferred
beyond v1.0.0 per `ROADMAP.md` 5.1), compile-time driver-pack changes, or
unrelated model refactoring.

## Baseline

Treat tag `v0.4.3` as the accepted implementation and compatibility
baseline. Capture the v0.4.3 public-contract inventory, resource metrics and
QSPI Flash layout before making any change, and confirm the reference
board's Flash layout is unchanged from the table below.

Current Flash layout (16 MiB reference target, from
`build/generated/ota_layout/ota_layout.h:12-50`; **zero spare bytes**, ends
exactly at `0x1000000`):

| Region | Offset | Size |
|---|---|---|
| Bootloader | `0x000000` | `0x010000` (64 KiB) |
| Bank A (app) | `0x010000` | `0x7A4000` |
| Bank B (app staging) | `0x7B4000` | `0x7A4000` |
| Maintenance journal | `0xF58000` | `0x008000` (32 KiB) |
| History Flash ring | `0xF60000` | `0x020000` (128 KiB) |
| Config slot 0 | `0xF80000` | `0x010000` (64 KiB) |
| Config slot 1 | `0xF90000` | `0x010000` (64 KiB) |
| Security identity slot 0/1 | `0xFA0000` / `0xFB0000` | 64 KiB each |
| Security trust slot 0/1 | `0xFC0000` / `0xFD0000` | 64 KiB each |
| Security lifecycle state | `0xFE0000` | 64 KiB |
| OTA state record | `0xFF0000` | 64 KiB |

The existing 2-slot config store (`services/include/services/
config_wire.h:16-74`, `config_store_service.h:39-56,91-117`) already
alternates generations on write, giving one implicit "previous generation"
level today — but no distinct region separates an uncommitted **staged**
blob from the **running** one, and there is no dedicated **last-known-good**
slot independent of both. Any new Flash region requires shrinking existing
regions, the same precedent v0.4.3 set when it shrank both OTA banks by
64 KiB each for the history ring.

## Scope decisions frozen before implementation

Resolved during pre-implementation interview and code-mapper evidence
gathering (2026-08-25/26); binding for this release:

1. **Driver stop/restart**: extend the existing `sensor_manager_activate_config()`
   orchestration and `telemetry_driver_vtbl_t.stop` contract — do not
   redesign from scratch. Current drivers have no shared DMA/IRQ/PWM state
   to release, but the `stop()` contract must stay defensive for future
   drivers that do. **Kill criterion**: if repeated, unresolved race
   conditions or hangs appear specifically in the driver stop path after
   several fix attempts, simplify or defer that piece rather than continuing
   to push on it.
2. **Staged/running/last-known-good Flash model**: follow the maintenance
   journal's transactional pattern (`drivers/src/maintenance_journal_backend.c`
   — physical-read-back commit-page classification, not application-return-value
   trust; two-pass recovery scan), not the non-transactional history-ring
   pattern. The commit-page IS the whole config blob (no separate A/B
   full-image region like OTA — rejected as overkill for a KB-scale blob and
   because that scheme has a documented "no true last-known-good" gap; see
   `docs/code/ota-bootloader.md:201-217`).
3. **Verify phase (before commit)**: successful init of every new/changed
   driver **and at least one valid read**, bounded by an explicit
   per-channel timeout, from each new or changed channel. (Tightened during
   interview — "init alone" was judged insufficient once the "I2C init
   succeeds even with no sensor physically present" failure mode was
   raised.) **Correction after plan review (2026-08-26)**: namespace
   (re)build is explicitly OUT of this gate — it was found to create a
   circular dependency on T6, which owns all namespace-rebuild logic and
   doesn't exist until after T4. See "Architecture and public-contract
   rules" for the resolved design: namespace rebuild is a separate,
   synchronous, post-commit step consuming `model_config_requires_server_reboot()`,
   not a pre-commit verification gate.
4. **Profile presets**: build and prove the transaction engine against one
   profile first; add the remaining two presets (sensor node, remote I/O,
   dev-benchmark) before the final gate, not from the first commit.
5. **Power-loss recovery testing**: simulate abort/reset between transaction
   phases at the firmware/host-test level (deterministic, automatable),
   accepting this will not catch real Flash write-alignment bugs the way a
   physical power-cut test would. Whether a real hardware power-cut pass is
   additionally needed before the final gate is an open question — decide
   during T9 planning, not assumed either way. **Explicit fallback (added
   after adversarial review, which flagged the open question as
   under-specified for a "frozen" decision)**: if T9 concludes a hardware
   power-cut test is warranted but the reference board isn't available
   before the gate is otherwise ready, ship with host-test coverage only,
   record it explicitly in the release notes as an accepted residual risk,
   and do not block the gate indefinitely waiting for hardware access.
6. **OPC UA client reconnect contract**: full server restart on any
   transaction that changes the running model (same behavior as firmware
   reboot), not a lighter live namespace-only rebuild. Matches
   `ROADMAP.md`'s own guidance: "do not implement fragile live mutation
   merely to avoid a short reconnect."
7. **Channel history/alarm state on reconfiguration**: both channel deletion
   AND channel modification (same `channel_id`, different driver/value type)
   zero the channel's Flash-backed history ring and alarm condition
   instance/acknowledgement state. Treated uniformly as delete+recreate; no
   orphan-record audit trail is preserved. **Traceability note (added after
   adversarial review)**: `ROADMAP.md` does not mention this requirement at
   all — it was invented during planning, not derived from the roadmap
   text. Assessed on the merits it holds up (delete-clear prevents a reused
   `channel_id` from surfacing a stranger's stale state; modify-clear is
   narrowly scoped to driver/value-type changes specifically because
   history/alarm records are typed per channel), but T10 must record it
   explicitly in the release notes/CHANGELOG as "in addition to
   `ROADMAP.md`'s v0.5.0 scope" rather than silently folding it into the
   roadmap-derived completion checklist, since `ROADMAP.md` itself must not
   be edited during implementation. Also record as a conscious, documented
   tradeoff (not an implicit byproduct) that discarding alarm
   acknowledgement history on every qualifying reconfiguration has no
   retention/audit-trail guarantee — industrial alarm-management practice
   (e.g. ISA-18.2) often expects that retained independent of point
   reconfiguration, and this project doesn't currently claim that
   compliance bar, but it should be a stated choice, not silent.
8. **Work split**: deferred until T1's file-level task boundaries are
   confirmed — do not assume a v0.4.3-style parallel split.
9. No hard deadline; paced by reaching the verification gate.

## Architecture and public-contract rules

`config_service` remains the sole transaction owner. `sensor_manager`
remains the hardware/driver-lifecycle executor invoked as `config_service`'s
runtime-apply callback — this release restructures the *ordering* and
*persistence* around that existing split, not the split itself.

The transaction pipeline, once restructured, must always execute in this
order and no other: **validate → persist staged copy → stop affected
drivers → activate (start new drivers, publish channel-registry generation)
→ verify (driver init + at least one valid read per new/changed channel,
each bounded by an explicit per-channel timeout) → commit (promote staged to
running, update last-known-good) or rollback (restart previous drivers,
restore previous registry, leave staged/running Flash state unchanged)**.
`config_service_replace_and_save()`'s current activate-before-persist order
must not survive this release.

**Namespace/OPC UA restart is explicitly NOT part of this gate** — fixing a
circular dependency found during plan review: T4's activate/verify steps
must not require building or rebuilding the live OPC UA namespace, because
that capability belongs entirely to T6 and doesn't exist until T6 lands.
`config_validate_service` (T1 baseline + T5) is the thing that guarantees a
committed config *can* produce a valid namespace; T4's verify step trusts
that guarantee rather than re-proving it live. Namespace rebuild is a
separate, subsequent action: after T4 commits, the same commit step must
synchronously consume `model_config_requires_server_reboot()` (already
computed every apply, currently unconsumed) and, if true, invoke T6's
controlled restart before returning control to the caller — not as a
deferred/asynchronous follow-up. This closes a second review finding: doing
it synchronously in the same commit step means no live server ever serves
the old namespace against already-T7-cleared history/alarm state, since any
transaction that deletes or modifies a channel always trips
`model_config_requires_server_reboot()`.

`alarm_service` and `history_service` must expose an explicit per-channel
clear entry point each; nothing else may reach into their internal
condition-slot or Flash-binding state to force a clear.

Every Flash write in the new staged-config path must go through the shared
`flash_operation_coordinator` used by `maintenance_journal_backend.c`, not a
new direct-write path.

without new evidence:

- **Flash geometry — resolved, no new region needed.** `device_profile_config_t`
  (`services/include/services/config_service.h:134-171`) is exactly 5,624
  bytes; `CONFIG_STORE_MAX_PAYLOAD_SIZE_BYTES` (`services/src/config_store_limits.h:18`)
  is 65,492 bytes per existing 64 KiB slot — an ~11.6x margin in one slot
  alone. Restructuring the existing 128 KiB config-slot pair (`0xF80000`/
  `0xF90000`) into 3 logical roles (staged/running/last-known-good), **one
  physical copy per role** (not two — see T3's corrected reasoning: the
  journal-style commit-page/CRC classification this task already commits to
  makes a second physical copy per role redundant, it was flagged as
  over-engineering during adversarial review), fits comfortably. **No
  OTA-bank shrink and no new Flash region are required for this release.**
  (If a bank shrink were ever needed for something else, note that
  `app/basic_profile/ota_layout_sanity.c:52-60` hardcodes a
  `_Static_assert` pinning exact bank/journal/history geometry and would
  need updating too — not currently relevant given this decision.)
- **Schema-version migration hook — location corrected.** The boot-time
  decode path (`config_service_init()`, `services/src/config_service.c:641-703`)
  never inspects `schema_version` today — it's read into `persisted_info`
  but only `.generation` is consulted. `config_service.c` must be added to
  T2's file list (not just `config_wire.h`/`config_compat.h/.c`); the new
  version-keyed dispatch needs a hook there, with `config_compat_decode_binary()`
  demoted to a fallback path.
- **Exhaustive missing-driver reporting — exact insertion point found.**
  `config_validate_service.c:1404-1415`'s per-channel check OR's
  `driver == NULL` together with three unrelated conditions (source
  validation, out-of-range `kind`, out-of-range `value_type`) into one
  `if`, sharing the single generic `CONFIG_VALIDATE_RESULT_INVALID_CHANNEL`
  (no dedicated "missing driver" result code exists in
  `config_validate_service.h:51-71` today). T5 must split `driver == NULL`
  into its own check with its own result code before exhaustive collection
  is possible, while leaving the other three conditions' short-circuit
  behavior untouched.
- **Locking model — confirmed feasible, `history_service.c`'s mutex is a
  valid template.** Today only `config_service`'s `g_transaction_active`
  (a `taskENTER_CRITICAL`-guarded bool, not a real mutex,
  `config_service.c:104-126`) serializes `sensor_manager_activate_config()`
  runs reached through `config_service`; the one direct boot-time call
  (`sensor_manager.c:428-433` → `sensor_manager_init()` →
  `main.c:793`) is safe only because it runs in `InitTask` before other
  tasks exist. FreeRTOS is confirmed available at every relevant call site,
  so an explicit `SemaphoreHandle_t` mutex (mirroring
  `history_service.c:79-80`'s `g_history_mutex` + bounded timeout) is a
  realistic, precedented addition — proceed with it in T4.
- **`SensorTask` creation — citation corrected, claim confirmed.** The gate
  is at `app/basic_profile/main.c:863-865` (not `:863-866` as originally
  written), inside `app_init_task()`; confirmed by full-repo grep as the
  only `xTaskCreate`-family site for `sensor_manager_task` anywhere in
  first-party code. One-shot, boot-only — T4 must address this directly.
- **Alarm per-channel clear — critical allocator bug found, changes T7's
  scope.** `alarm_service_find_or_bind_snapshot()`
  (`services/src/alarm_service.c:126-174`) allocates new condition slots
  via a **strictly monotonically increasing** cursor (`g_condition_count`,
  never reclaimed) — it never scans for an existing `in_use == false` hole
  below the high-water mark. A naive `alarm_service_clear_channel()` that
  only sets `in_use = false` would **not** free capacity: it would
  permanently shrink available condition slots by one per clear. Across
  repeated delete/modify cycles on the same `channel_id` (which T7
  explicitly treats as delete+recreate), `g_condition_count` would climb to
  `ALARM_SERVICE_MAX_CONDITIONS` (=16, `alarm_service.h:16`) and then
  legitimately alarm-eligible channels would start being silently rejected
  (`alarm_service.c:159`), even though live channel occupancy never exceeds
  `PLATFORM_CHANNEL_LIMIT`. **T7's `alarm_service_clear_channel()` must fix
  the allocator itself** (search for the first `in_use == false` slot below
  `g_condition_count` before extending the cursor), not just add a setter.
- **History per-channel clear — needs the mutex.** The `bind_channel(slot,
  NULL)` unbind pattern already exists but only inside
  `history_service_init()`'s one-time boot sequence
  (`history_service.c:352-357`), never running concurrently with anything.
  A runtime `history_service_clear_channel()` reusing this call shape must
  additionally take `g_history_mutex` (`history_service.c:79-80`), since
  post-boot it will run concurrently with `SensorTask` writes and OPC UA
  `HistoryRead`. Confirmed sole caller of `history_flash_backend_bind_channel()`
  is `history_service.c` — safe to extend without coordinating other
  callers.
- **Existing test coverage gap for T9.** The pre-existing
  `static/tests/config_transaction/config_transaction_test.c` already
  exercises the activate-before-persist ordering bug directly (event trace
  assertion at line 149, with `g_fail_save = true`) — useful as the
  baseline T4 must preserve/extend while inverting the order. It does
  **not** cover a `stop()` failure path (`fake_stop` always returns OK,
  line 43-44; `'O'` is never in the injected-failure step set at line 125)
  — T9 must add that scenario explicitly, it will not appear for free.

T2, T5, T7 and T9 below have been updated to reflect these findings.

### T2 — Explicit configuration schema version and migration functions

Primary files:

- `services/include/services/config_wire.h`;
- `services/include/services/config_compat.h`, `services/src/config_compat.c`;
- `services/src/config_export_service.c` (line 390 hardcodes the JSON
  export's `"schemaVersion":1` as a raw literal — must source from the same

- `services/src/config_validate_service.c` (line 1203 gates JSON *import*

**Adversarial review finding (2026-08-26), addressed above**: as originally
scoped, this task versioned only the Flash-binary format. `ROADMAP.md`
explicitly asks for configuration **import/export** versioning — the
host-facing JSON path operators and tooling actually use. Without adding
the two files above, export would keep stamping a stale literal and import
would keep gating on a frozen constant the moment a second schema version
exists for the Flash format, silently desynchronizing the two paths.

Give `schema_version` (currently always the constant
`CONFIG_STORE_SCHEMA_VERSION_OPAQUE_BINARY`) real discriminating meaning,
and add a migration-function table keyed on it, shared by the Flash-binary
decode path, JSON export, and JSON import. Keep the existing payload-size
dispatch (`config_compat_decode_binary()`) as a compatibility fallback for
Flash records written before this release. Reject an incompatible/future
schema version (either format) with a diagnostic rather than attempting to
decode it.

**Boot-hook wiring deferred to T3/T4**: `config_service.c`'s boot-time
decode path (`config_service_init()`, `:641-703`) currently calls
`config_store_load_active()` — the 2-slot generation-MRU selector T3
replaces wholesale with the staged/running/last-known-good scheme. Do not
wire the new schema-version dispatch into `config_service.c`'s boot path as
part of this task; define the version format and migration-function table
here, and let T3 (which already must touch this function) wire the actual
call-site integration once the underlying slot-selection primitive is
final. This avoids rewriting the same ~70-line function twice in
back-to-back tasks (flagged during plan review).

Tests cover: decoding every pre-v0.5.0 record shape via the fallback path,
decoding a current-schema record via the version-keyed path, and rejecting
an unknown future version.

### T3 — Staged/last-known-good Flash transaction backend

Primary files:

- `services/include/services/config_wire.h`, `config_store_limits.h`;
- `services/src/config_store_service.c`;
- `services/src/config_service.c` (boot-time decode path,
  `config_service_init()` `:641-703` — wire T2's schema-version dispatch
  here, into this task, once the slot-selection primitive below is final;
  see T2's note);
- new `drivers/include/drivers/config_transaction_backend.h` and
  `drivers/src/config_transaction_backend.c` (or equivalently named).

**Flash geometry is frozen by T1: no new region, no OTA-bank shrink.**
Restructure the existing 128 KiB config-slot pair (`0xF80000`/`0xF90000`)
into 3 logical roles — staged, running, last-known-good.
`ota/cmake/ota_layout.cmake` and `app/basic_profile/ota_layout_sanity.c`
should not need region-boundary changes; touch them only if the final slot
layout needs a different physical split within the existing 128 KiB budget
than today's 2×64 KiB.

**One physical copy per role, not two — corrected during adversarial
review.** The original framing ("2 physical copies per role for
atomic-swap safety, 6 slots total") contradicted the very reason this task
chose the maintenance-journal pattern over an OTA-style A/B scheme:
commit-page/CRC physical-read-back classification (mirroring
`maintenance_journal_backend_recover()`'s EMPTY/OK/DEGRADED/INDETERMINATE/
FATAL outcomes, never trusting the flash-program call's own return value)
already answers "did the last write to this region complete" *without*
needing a second physical copy to compare against — that's the entire point
of the technique. A torn staged write simply classifies as
NOT_COMMITTED/CORRUPT and is discarded; last-known-good gets crash-safety
from the same classification, updated only after a successful commit, no
physical twin required. Implement one region per role (staged, running,
last-known-good) with commit-page classification each; do not add a second
physical copy unless a *different*, explicitly stated reason (e.g.
wear-leveling across many writes) is identified during implementation — not
"atomic-swap safety," which commit-page classification already provides
alone.

Implement the transaction backend: stage-write with commit-page
classification, a recovery scan on boot for each role, and a last-known-good
promotion step on successful commit.

Tests cover: power loss before/during/after stage-write, before/during/after
commit-page write, recovery classification for every outcome, and
last-known-good promotion/retrieval across reboot.

### T4 — Restructure the config transaction pipeline

Primary files:

- `services/src/config_service.c`;
- `services/include/services/config_service.h`;
- `services/src/sensor_manager.c`;
- `app/basic_profile/main.c`.

This task bundles four logically separable concerns landing in the same
files — sub-itemize them as distinct commits/steps rather than one
undifferentiated diff (flagged during plan review as a coupling risk if
attempted as a single unreviewable change):

**(a) Ordering fix.** Rebuild `config_service_apply()`/
`config_service_replace_and_save()` (retiring the latter's
activate-before-persist bug) into the single frozen order: validate →
persist staged (via T3's backend) → stop affected drivers → activate
(driver start + registry publish only, no namespace — see "Architecture and
public-contract rules") → verify (driver init + per-channel valid read,
each bounded by an explicit timeout) → commit/rollback.

**(b) Locking.** Add the explicit mutex frozen in T1 around
`sensor_manager_activate_config()`.

**(c) SensorTask handoff.** Ensure a transaction activating the first
channel on a channel-less device creates/hands off to `SensorTask`
correctly (fix the boot-only creation gate at `app/basic_profile/main.c:863-865`
or make activation itself responsible for ensuring the task exists).

**(d) Reboot recovery.** Recover correctly on reboot after a power loss at
every phase: staged-only (discard, keep previous running),
persisted-but-not-activated (resume or discard per T1's frozen recovery
contract), activated-but-not-committed (roll back to last-known-good), and
committed (keep new running, promote to last-known-good).

**Commit-step contract carried forward to T6/T7**: the commit step this
task builds is not a finished artifact — T7 adds per-channel history/alarm
clearing into it, and per "Architecture and public-contract rules" the same
commit step must synchronously invoke T6's restart when
`model_config_requires_server_reboot()` is true, before returning to the
caller. Build the commit step with an explicit extension point for both,
rather than a closed function T7/T6 have to reopen and restructure.

**API note for T5**: the validate step's calls to
`config_validate_service_validate_candidate()` must keep working with an
additive signature (new out-parameter or overload) if/when T5 extends it
for exhaustive missing-driver reporting — do not let T5 force a breaking
signature change back into this task's files after the fact.

Tests cover: successful apply, rollback on driver-init failure, and

### T6 — Controlled OPC UA server restart

Primary files:

- `opcua_model/src/model_core_lifecycle.c`;
- `opcua_model/src/model_address_space.c`;
- `opcua_model/src/model_channels.c`;
- `opcua_model/src/opcua_model_internal.h`;

Consume `model_config_requires_server_reboot()` (already computed every
apply) as the trigger for an actual controlled full server restart — tear
down the current `UA_Server` instance and rebuild the namespace from the
newly-committed configuration, matching the full-restart reconnect contract
frozen above. This restart must be invoked **synchronously from within T4's
commit step** (per "Architecture and public-contract rules"), not as a
deferred/asynchronous follow-up — closing a review-identified race window
where a live server could otherwise keep serving the old namespace against
already-T7-cleared history/alarm state for a just-deleted-or-modified
channel. Document the exact client-visible sequence (session/subscription
loss, reconnect requirement) since no client-facing teardown path exists in
the code today (`UA_Server_delete` currently only runs on fatal
startup-failure paths).

**Reuse the boot-time construction entry point exactly** — the runtime
rebuild must call the same `model_build_address_space()`/`model_core_init()`
path used at cold boot (`model_core_lifecycle.c:897`), not a second,
parallel implementation of namespace construction. Two codepaths building
the same address space would drift silently over time; this is an explicit
acceptance criterion, not an implementation detail left to discretion.

Tests cover: a transaction that does NOT require restart leaves existing

### T7 — Per-channel history/alarm state cleanup on delete/modify

Primary files:

- `services/include/services/alarm_service.h`, `services/src/alarm_service.c`;
- `services/include/services/history_service.h`, `services/src/history_service.c`;
- `drivers/include/drivers/history_flash_backend.h`, `drivers/src/history_flash_backend.c`.

Add `alarm_service_clear_channel(channel_id)`. **Must fix the allocator, not
just add a setter**: `alarm_service_find_or_bind_snapshot()`
(`alarm_service.c:126-174`) allocates via a strictly monotonically
increasing `g_condition_count` cursor that never reclaims a freed slot. A
clear that only sets `in_use = false` permanently shrinks available
condition capacity by one per call — across repeated delete/modify cycles
on the same `channel_id` this will eventually exhaust
`ALARM_SERVICE_MAX_CONDITIONS` (=16) and start silently rejecting
legitimately alarm-eligible channels, even though live channel occupancy
never exceeds `PLATFORM_CHANNEL_LIMIT`. Change slot allocation to search for
the first `in_use == false` slot below `g_condition_count` before extending
the cursor, then clear via that reclaimed path.

Add `history_service_clear_channel(channel_id)`: drop the channel's PSRAM
ring and un-claim its Flash slot (`history_flash_backend_bind_channel(slot,
NULL)`), consistent with the existing unbind pattern at
`history_service.c:352-357` — but that pattern today only ever runs during
`history_service_init()`'s one-time boot sequence. A runtime call must take
`g_history_mutex` (`history_service.c:79-80`) first, since post-boot it runs
concurrently with `SensorTask` writes and OPC UA `HistoryRead`.

Wire both into T4's commit-step extension point for every deleted or
modified (same `channel_id`, different driver/value-type) channel. Any such
channel change always trips `model_config_requires_server_reboot()`, so
T6's synchronous restart (see T6, and "Architecture and public-contract
rules") always runs in the same commit step immediately after this
clearing — no live server should ever observe a namespace that still
exposes a channel whose backing state has already been cleared.

Tests cover: deleted channel's history/alarm state is unreachable after
commit; modified channel (same id, new driver) starts with a clean
history/alarm state; an untouched channel's history/alarm state survives a
transaction that changes other channels.

## Completion

Done only when:

- the configuration transaction pipeline executes validate → persist staged
  → stop → activate → verify (including at least one valid read per
  new/changed channel) → commit/rollback in that order, with
  `config_service_replace_and_save()`'s activate-before-persist bug fixed;
- staged, running and last-known-good configuration each have a distinct,
  power-loss-recoverable Flash representation, following the
  maintenance-journal transactional pattern;
- configuration schema version is real (not a constant) with working
  migration functions, and an incompatible/future schema is rejected with
  diagnostics;
- reboot after every transaction phase recovers either the complete old or
  complete new configuration, never a mixture;
- every missing `driver_id` in a rejected candidate configuration is
  reported, not just the first;
- a transaction that changes the running model triggers a controlled full
  OPC UA server restart with documented client-visible reconnect behavior;
  a transaction that doesn't need one leaves existing sessions untouched;
- deleting or modifying a channel zeroes its Flash-backed history and alarm
  condition/acknowledgement state;
- firmware/configuration compatibility data (profile, hardware revision,
  schema version, `SupportedDrivers`, driver capabilities/resources) is
  exposed through the management model;
- at least the reference profile preset is fully proven; the remaining two
  presets exist before the gate;
- public-contract, build, static-analysis, version, size and
  independent-review gates pass.

Do not create a release tag, implement v0.5.1/v0.5.2/later roadmap work, add
dynamic native-driver loading, or modify `ROADMAP.md` while implementing
this plan. Updating `AGENTS.md`'s current-release pointer is a separate,
explicit roadmap-maintenance task.
