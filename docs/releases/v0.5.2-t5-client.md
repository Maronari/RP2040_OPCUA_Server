# v0.5.2 T5 latency and sampling measurements

T5 extends the existing load client and adds benchmark-only native sampling
evidence. The frozen limits and metric meanings remain those in
`v0.5.2-measurement-contract.md` and
`static/benchmarks/v0.5.2/measurement-contract.json`.

## Implementation boundary

- `static/tools/load_test_opcua.py` and its focused tests own client timing,
  profile verification, operation accounting and bounded reports.
- The native sampling hook records successful channel samples using the
  device monotonic clock. Capture must exclude activation verification and
  identify its measurement window. Host notification arrival intervals are
  not device sampling jitter.
- `static/tools/run_host_tests.py` integrates deterministic checks. Runtime
  hardware evidence and measured regression thresholds remain separate gates.

No new public NodeId, persisted configuration field, driver ID or preset is
needed. Production security and resource capacities are preserved.

## Measurement interpretation

Client operation times use a host monotonic clock. Connection establishment
includes the declared connection/session sequence; it must not be described
as the isolated cryptographic operation. Client preparation, connection and
steady-state workload are distinct phases. An already-running server does
not provide cold startup evidence.

`ExportConfig` is the existing read-only Method workload. Its returned
configuration also verifies the selected synthetic profile. Read and
HistoryRead measure their declared request and response populations. Failed
operations and timeouts remain visible and do not enter successful latency
distributions.

The Read rate defines fixed arrival times, not an implicit timeout equal to
the sampling period. Each dispatched Read receives the separately declared
operation timeout. Up to 16 Reads may be in flight per client (64 at the
four-client profile maximum); event-loop-late or capacity-blocked arrivals are
counted as missed instead of being emitted in a catch-up burst. A timed-out
client is fenced before any HistoryRead or resource snapshot, and a coroutine
that ignores cancellation is quarantined without access to the final metric.

The T4 synthetic channels are not writable. A rejected Write must not be
reported as successful write latency. Events-on enables publication but does
not by itself provide a deterministic correlated event trigger. Event
delivery requires correlation and valid source time, with clock and transport
limitations stated. Missing evidence is an explicit result state and reason,
never a zero-valued timing or a passed acceptance criterion.

Device sampling intervals come from successive monotonic timestamps for the
same channel and capture. Missing sequences, capacity exhaustion and invalid
timestamps invalidate the affected measurement. Collection and export
overhead must be reported separately from measured client latency.

Host and mock test results do not establish reference-board startup, sampling
jitter, runtime memory/stack use, UaExpert interoperability or industrial
hardware qualification.

## Running the client

Install the repository's asyncua dependencies and provision a service/admin
account and client certificate through the existing procedure. Supply
credentials with `OPCUA_USERNAME` and `OPCUA_PASSWORD`. Use the metadata from
the exact image flashed to the reference board. For example, the one-channel
secure T4 corner uses:

```powershell
rtk proxy py -3.12 static/tools/load_test_opcua.py opc.tcp://192.0.2.1:4840 --benchmark --benchmark-profile-id v052-syn-c1-ns0full-secbasic256sha256-signandencrypt-cl1-hz1-ev0-hist0 --benchmark-metadata build/v052-t4-secure/benchmark_profile.json --clients 1 --items 1 --read-rate 1 --sampling-ms 1000 --publishing-ms 1000 --warmup 10 --duration 30 --repetitions 1 --git-commit <exact-image-source-commit> --board-revision <actual-board-revision> --toolchain "Arm GCC 13.3.1" --build-type Debug --build-flags "base;primary-OTA;synthetic" --network-setup <actual-network-setup> --time-synchronization <observed-clock-state> --output build/reports/t5/client.json
```

Replace the example endpoint and bracketed values. Add `--git-dirty` if the
image was built from a modified tree, and record those modifications with the
build artifacts. This command is a usage example, not a recorded hardware run.
The plaintext corner requires both its `test-none` profile and `--test-none`.
Client count, monitored items, sampling/publishing periods and read rate must
match the selected profile. Channel namespace indexes are resolved live.

The tool verifies the running configuration with `ExportConfig` before load.
Method timing currently describes that setup request, rather than a repeated
steady-state Method workload. History-enabled profiles use a bounded raw page
and release its continuation point. The report records unsuccessful operations
and missed load deadlines. Exit zero means the implemented workload completed;
it does not mean every T5 metric or release acceptance check is satisfied.

## Native sampling capture

Only synthetic benchmark images accept the serial commands:

```text
benchmark start
benchmark dump
```

Start explicitly after arranging the intended client load. The default native
window is 10 seconds of warmup followed by 30 seconds of capture. End the
client workload before requesting the dump: serial output runs on SensorTask
and is intentionally outside the capture window. A new capture can be started
after successfully exporting the previous completed capture.

The capture retains at most 8192 records, 16 bytes per record, in PSRAM plus
bounded channel mapping/state. It has no SRAM allocation fallback. This is
additional benchmark memory, separate from the T2 diagnostic snapshot budget.
An unavailable allocation, insufficient capacity or runtime overflow produces
an explicit failure state. Normal firmware does not allocate this buffer.

Save one complete native JSON object as evidence. Reject truncated or
log-interleaved output; do not repair missing samples into a successful run.
`--native-sampling-evidence <file>` validates profile, window and sequence
metadata and calculates per-channel interval and absolute jitter distributions.
It identifies the imported file by hash and capture ID. This is independent
external capture evidence: matching settings alone cannot prove that it came
from the same board, firmware or client run. The report therefore leaves its
association with the current workload unverified. A reference-board runner
must establish that association before using it as a workload baseline.

## Remaining T5 acceptance work

Cold device startup needs a boot/readiness measurement with a defensible clock
boundary. Successful Write latency has no target in the frozen read-only
synthetic workload. Correlated event delivery and notification-gap accounting
also remain unavailable. No hardware latency, runtime heap/stack impact,
sampling-hook overhead or UaExpert result is implied by host tests or builds.
These gaps keep T5 and v0.5.2 acceptance open.
