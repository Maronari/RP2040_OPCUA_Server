# v0.6.0 T0 design freeze

Date: 2026-10-29. Scope: T0 of [the release plan](v0.6.0.md).
Compatibility baseline: `2a0bcd8027b37e176e3264f739ee70cfb105e64b`.

Status: **T0 engineering design is frozen; T1 native implementation may start.**
The production/integration gates in this ledger remain blocking and unpassed.

T0 fixes the engineering decisions and entry contracts for implementation.
It does not certify a signed loader, sustained health, recovery timing or a
release. The numerical limits below are selected acceptance budgets informed
by measurements, not claims that an integrated implementation met them.
ROADMAP, AGENTS and the authoritative release plan are unchanged by this task.

## Frozen contracts and evidence

| T0 deliverable | Decision/evidence |
|---|---|
| Trust | SHA-256 and low-S ECDSA P-256; at most two compiled public keys; no private key in firmware; protected manually approved CI signing remains T5. |
| Compatibility | Explicit hardware/profile/pack IDs and uint32 board revision; missing revision rejects production packaging/verification. Actual reference revision is unprovisioned; no value is inferred. |
| Serialization | Fixed 320-byte manifest, signed prefix 256 bytes; exact fields, low-S scalars, reserved bytes, lengths and identity in the engineering companion. |
| Recovery | Boot 256 KiB, A/B/C slots, payload cap 5,271,552 bytes; immutable authenticated B before any A overwrite. |
| Installation interruption | Any reset in INSTALL selects RESTORE, not a C retry. This now agrees with the executable recovery model. |
| State | Exact 1,024-byte record, two 4-KiB sectors and final commit page; host codec covers 13,573 partial-write cases. CRC does not replace image authentication. |
| Attempts | One durable LAUNCH_CONSUMED boundary, one candidate launch; reset after that boundary restores B even if the jump never occurred. |
| Public/native API | [Native and adapter contract](v0.6.0-t0-native-contract.md); existing signatures/Service role retained; new Admin-only manifest/activation design reservations. |
| Pending writes | Per-owner startup/background guard classification is frozen in the native contract; durable confirmation is the only release point. |
| Readiness feasibility | Actual default-reference image reached first iteration without IPv4 in 20,609,988 us and accepted four late-DHCP discovery clients. This is startup/discovery evidence, not health confirmation. |
| Capacity feasibility | Current reference BIN 3,587,232; industrial BIN 3,600,168, both below payload cap. Existing loader plus retained crypto primitives is 103,928 bytes, below 262,144. This is primitive-link feasibility, not final signed-loader size. |
| Timing/resources | [Machine-readable policy](v0.6.0-t0-policy.json), arithmetic/decision model and mandatory integration gates below. |

The early companion's requests for final integrated size, real fallback and
candidate health evidence are mandatory T1–T6 acceptance checks. They cannot
be measured before those implementations exist. They are not reclassified as
passed: T0 freezes their limits, failure behavior and stop conditions.

## Production policy 0x06000001

The existing codec's policy ID 1 remains an isolated fixture value. Production
uses `0x06000001`; the explicit development-only downgrade policy is
`0x86000001`. Development bypasses only the version floor, never authentication,
compatibility or integrity. Neither policy is provisioned by these host tests.
Changing these numerical rules requires a new policy ID and design review.

| Selected limit | Value |
|---|---:|
| Readiness must begin by elapsed | 32,000 ms |
| Continuous healthy interval | 3,000 ms |
| Reserved commit interval | 1,000 ms |
| Maximum confirmation operation budget | 500 ms |
| Logical confirmation cutoff | 36,000 ms |
| Boot-window polling period | 100 ms |
| Network/OPC UA completed-progress freshness | 2,000 ms |
| Independent hardware watchdog | 4,000 ms |
| Nominal hardware reset ceiling after candidate handoff | 40,000 ms |
| First application adoption of watchdog handoff | within 1,000 ms |

The largest observed main-to-first-iteration interval is 22,574,962 us. A
32-second readiness budget leaves 9,425,038 us above that observation; the
unmeasured handoff allowance consumes up to another second. Three seconds of
continuous health is a chosen short verification interval. The 100-ms/2-second
cadences are selected limits, informed by the current NetworkTask 10-ms poll
and OpcUaTask 10–100-ms post-iterate delay. These are engineering margins and
requirements, not measured worst-case startup or proof of owner freshness.

The origin is the loader's final watchdog feed immediately before the candidate
jump, not USB reconnection or log receipt. Ordinary feeds never restart this
origin. If readiness is unavailable at 32 seconds, fails explicitly, or loses
required progress during the sustained interval, confirmation is refused.
At the 36-second cutoff no confirmation or feed is allowed. A runnable owner
requests immediate reset on failure; a starved owner cannot prevent the
independent watchdog from expiring after the last permitted feed. Thus 36
seconds is a logical cutoff and 40 seconds the nominal fallback-reset target;
they are not the same deadline. Actual clock tolerance, handoff time and reset
latency must be measured in T2/T3 before production eligibility.

Confirmation is only eligible after the entire interval and enough commit
reserve remain. A successful API call, task handle or first iterate alone
cannot confirm. The guard stays active until a complete durable CONFIRMED
transaction advances identity and version floor together. A failed/torn commit
leaves LAUNCH_CONSUMED selectable and leads to restoration. The state-record
readback and last commit-page operation must obey the integration timing gate;
a post-write timeout is never used to pretend a durable commit did not happen.

## Health ownership and watchdog handoff

Five fixed owner slots are required: scheduler, configuration, storage, local
network stack and OPC UA. Each publishes a copied bounded snapshot with state
UNAVAILABLE/READY/FAILED, monotonic observation time, observation generation and
bounded reason. One writer owns each slot; a brief existing critical section
protects publication/copy. No borrowed task/model pointer, queue or allocation
is part of the snapshot interface.

- Scheduler: the boot-window task runs and observes advancing monotonic time.
- Configuration: latch the actual compatible configuration-load result;
  `config_service_get() != NULL` is insufficient.
- Storage: aggregate explicit required config/security/history/journal
  read/recovery results. Valid empty optional stores and explicitly disabled
  optional persistence are not failures. Required unreadable data fails health.
  Suppressing writes during the window must not itself make healthy storage fail.
- NetworkTask: publish initialized local stack plus completed polling progress;
  do not use link, lease or `network_manager_is_ready()` as the health predicate.
- OpcUaTask: publish successful server/address-space startup and completed
  iterations. Refresh time/generation only on actual progress, not on a read
  of the snapshot by the boot-window task.

Config/storage initialization results may remain latched; idle storage need
not write data or invent a heartbeat. Network and OPC UA progress must remain
fresh after readiness. A zero/unavailable observation is never a passed test.
Ethernet, DHCP, NTP, external clients and a USB console are excluded. The
known `Sensor manager init failed` diagnostic remains outside this narrowly
defined OTA window; this is not the v0.6.2 board-health supervisor.

The loader validates the pinned state/images, commits LAUNCH_CONSUMED and reads
back its complete commit before the jump. A power failure between commit and
jump consumes the attempt. It arms a 4-second watchdog with debug pause **off**.
The first candidate action establishes its guard and adopts the watchdog before
stdio, console waits, provisioning or any service with persistent side effects.
Unconfirmed boot skips the existing up-to-15-second console wait; logging must
drop/bound output when the host is absent. The early-to-scheduler adoption gap
must be measured below the watchdog period; no hidden ordinary feed is allowed.

Reserve watchdog scratch words 0–3 only:

| Word | Content |
|---|---|
| 0 | `0x3641544f` (OTA6), handoff hint only |
| 1 | CRC-32 of the verified running candidate, diagnostic only |
| 2, 3 | Low/high halves of the selected committed generation |

ROM/SDK scratch words 4–7 are untouched. Match the generation against validated
LAUNCH_CONSUMED metadata and the compiled policy ID; scratch never authenticates
an image or overrides durable selection. Missing/mismatched handoff cannot clear
pending state or grant another launch. CRC is only the existing status diagnostic,
never the authorization check.

The old immediate `app_acknowledge_ota_boot_if_needed()` reset of legacy READY
state must not run for a v2 unconfirmed boot. T3 replaces that path with the
boot-window-owned durable confirmation; detecting a task or clearing a flag
cannot acknowledge the candidate.

Before any adoption/feed, use the independently running watchdog's remaining
counter to account for time since the loader's final feed. Establish a local
monotonic origin including that elapsed interval. A feed/reconfiguration never
resets the logical deadline. Counter/tick continuity across SDK initialization
and clock setup is an explicit T2 target gate. Invalid time, expired counter or
unavailable adoption fails closed; do not manufacture a new 36-second window.

During the window, the boot-window owner alone authorizes watchdog operations
through the driver. The existing unconditional WatchdogTask must be suppressed;
the ordinary configured watchdog cannot re-arm, feed or extend the candidate
deadline. Only after durable confirmation is feed ownership transferred to
normal application behavior. Services never touch watchdog registers directly.
These are T2/T3 requirements; today's generic watchdog is not certified by this
design. No general watchdog or supervisor redesign is introduced.

## Bounded installation and recovery work

Use one erase/program/readback step per sector. The current whole-image erase
in the legacy loader cannot be retained under this policy. Feed the loader's
watchdog only between successful bounded steps; an unreturned hardware call is
limited by the independent watchdog, not a cooperative timeout.

The full payload has 1,287 sectors; adding its manifest gives 1,288 per copy.
The observed programmed-sector erase/verify, sixteen-page programming and
readback sum to 55,612 us. A selected 150-ms step budget is about 2.697 times
that sample; 1,288 steps give a **193,200-ms design budget per copy**. This is
linear extrapolation from one sector with generic Flash reads, not measured
full-copy timing or a datasheet maximum. It must be qualified on the target.

Each image verification has an 8-second design budget. Scaling the measured
CPU-copy hash to full payload gives less than 5.582 seconds; the measured
ECDSA operation is about 0.212 seconds. Individual nonpreemptible crypto
operations must finish within one second and hash streaming yields/feed points
are bounded by 4-KiB chunks. A library hang cannot keep the watchdog alive.

At most three copy passes (backup, install, possible restore), eight full-image
verifications/rechecks and four seconds of metadata work are budgeted for an
uninterrupted transaction. Their conservative arithmetic is 647,600 ms; the
loader transaction ceiling is 650,000 ms. Adding the possible failed candidate's
nominal 40-second reset interval gives a 690,000-ms transaction budget. This
accounts for preparation and a later restore; it does not assert that all work
occurs in one boot. Normal confirmed boot does not perform these copy passes.

No in-boot copy retry is allowed. BACKUP error or reset aborts the activation:
authenticate unchanged A and durably return to CONFIRMED with STORAGE_ERROR
(which also covers an interrupted preparation), clearing the candidate. If A
or the abort commit is unusable, enter local recovery. Do not automatically
restart B preparation. INSTALL reset/error selects RESTORE. A power interruption
of RESTORE may restart that one restoration on the next boot; a detected
write/readback failure during RESTORE, invalid backup, or a watchdog reset
while restoring enters local recovery instead of an endless retry. B is never
erased by restoration. Repeated independent external power interruptions have
no finite elapsed-time guarantee. Eight verification slots cover A/C validation,
B readback, B/C pre-install rechecks, installed A, and B/restored A during
fallback; exhaustion is RECOVERY_REQUIRED, never an extra unbounded pass.

## Resource and production gates

Selected ceilings are in the JSON policy. Bootloader Flash stays at 262,144
bytes; static data at 98,304 bytes, stack at 8,192 bytes, crypto arena at 65,536
bytes and the copy buffer at 4,096 bytes. The arena was successful in the
isolated RAM fixture; it is not a measured integrated-loader allocation peak.
The 3,420-byte useful allocator peak excludes headers, and the 1,392-byte MSP
extent includes the probe window; neither is renamed a production stack/heap
measurement.

The 8-KiB loader stack requires an explicit disjoint reservation in main SRAM;
it cannot fit the SDK's default 4-KiB SCRATCH_Y region. T2/T5 must reserve it
in the loader linker layout and report it separately from `.data`/`.bss` and
any heap. This is a selected placement requirement, not an existing linker result.

Application additional static SRAM is limited to 2,048 bytes, leaving space
under the current reference/industrial static reservations. The boot-window
task, stack and associated dynamic state must fit an 8,192-byte allocation
budget from the existing bounded FreeRTOS heap; a verifier can reserve at most
65,536 bytes in the existing PSRAM allocator, with no silent SRAM fallback.
Allocation failure refuses verification/confirmation; it never frees a fallback
or silently relaxes a cap. No permanent image-sized buffer is allowed.

| Next gate | Required result; failure blocks integration/production |
|---|---|
| T1 | Native vectors/negative/overflow/allocator tests and target-linked crypto/parser sizes within these caps; static, heap, arena headers and stack measured separately. |
| T2 | Signed A-linked reference/industrial image fit; final loader fit; full-capacity sector-copy/restore and all timing limits instrumented; actual watchdog adoption/clock continuity and deliberate starvation. |
| T3 | Owner-published readiness, sustained interval and durable confirmation, every mutation gate, no USB/cable/DHCP/client dependence, actual post-startup stack/PSRAM peaks. |
| T4 | Actual bounded C JSON emission, old keys/types/roles and new reservations verified; authorization/rejection/contention, authenticated interoperability and UaExpert. |
| T5 | Supplied board revision and public keys; protected CI signing/environment/secret evidence; exact-source packaging. Missing inputs block production artifacts, not test-vector development. |
| T6 | Actual power interruption, one launch, verified fallback and confirmation on hardware. Host fault models never substitute for these results. |

Exceeding a limit blocks the affected artifact/profile. It is not permission
to shrink preserved storage, borrow an image-sized buffer or silently increase
the policy deadline. A required policy change returns to design review.
