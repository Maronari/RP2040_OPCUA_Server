# v0.3.2 atomic maintenance publication resolution

## Status and scope

This document resolves the atomic-publication design blocker for v0.3.2. It
does not change the release scope: maintenance remains volatile, service-owned,
bounded, and limited to the four scheduled Methods and three AMB transitions.

## Consistency boundary

Atomicity applies to one logical maintenance snapshot: state, revision,
activity fields, AMB state text and NodeId, optional maintenance fields, and
condition metadata derived from that revision.

Atomicity is not required across an entire multi-node OPC UA Read service
request. Independent data-source callbacks may execute separately and may
acquire the committed snapshot independently. Each callback must nevertheless
return a value derived entirely from one committed snapshot revision; it must
never read or expose prepared state.

## Transaction and commit point

Every command uses one prepare/apply/commit transaction.

Before commit:

1. Validate authorization, arguments, bounds, source state, and resource
   availability.
2. Build a complete candidate snapshot without changing committed service
   state.
3. Prepare any bounded OPC UA values and event allocation needed by the
   candidate.
4. Apply prepared values only to inactive transaction storage. Prepared values
   must not be reachable through the active OPC UA AddressSpace or data-source
   callbacks.

The single commit point is the atomic replacement of the service's active
snapshot pointer/index and revision with the prepared snapshot. At that point
the complete candidate becomes the committed business state and the only
snapshot visible to subsequent OPC UA data-source callbacks.

After commit:

1. Trigger the prepared transition event, when the operation is a transition.
2. Release the previous snapshot and transaction resources according to their
   bounded lifetime rules.
3. Record and recover from post-commit infrastructure faults without changing
   the committed business revision.

## Failure semantics

Before-commit failure:

- abort and discard all prepared values;
- leave the committed service state and revision unchanged;
- leave the public OPC UA snapshot unchanged;
- emit no transition event;
- return the documented non-Good status.

After-commit failure:

- never roll back committed business state;
- never republish the previous snapshot as current;
- report an infrastructure fault through bounded diagnostics;
- preserve the committed snapshot as the source of truth;
- follow the recovery policy below.

## Event semantics and recovery

Event allocation and field preparation may occur before commit, but a
transition event must be triggered only after the snapshot commit succeeds.
Rejected, aborted, and reschedule operations do not emit a transition event.

The firmware correctness boundary ends at the public open62541 event API. A
successful return from that API constitutes successful event publication by
the firmware. An event-publication failure observable through the public API is
a post-commit infrastructure fault. It does not change the successful Method
transition and must not roll back the committed snapshot.

Failures hidden inside the internal open62541 event distribution path are
outside the firmware correctness contract. In particular, the firmware is not
required to detect delivery failures for individual subscribers. Such hidden
failures must be documented as platform limitations and do not activate the
firmware recovery policy.

Recovery policy:

1. Set a bounded `event_publication_fault` diagnostic containing the committed
   revision and operation.
2. Prevent duplicate automatic publication for that revision.
3. Keep maintenance reads available from the committed snapshot.
4. Reject subsequent state-changing maintenance Methods with
   `BadResourceUnavailable` until the event subsystem is reconciled or the
   volatile runtime is reinitialized.
5. Clear the fault only after a deterministic health check proves that the
   public open62541 event API is available. v0.3.2 does not add an event journal
   or replay a missing transition event.

## OPC UA publication requirements

Service-backed data sources must read only the active committed snapshot.
Cached condition fields, if required by open62541, may be constructed in
inactive storage during prepare/apply but must remain invisible until the
service snapshot commit.

The implementation must establish, with exact open62541 API and source
evidence, how cached condition fields become visible without exposing a
partially prepared field set. If the available open62541 APIs cannot satisfy
this guarantee, implementation must stop and document:

- the APIs and source paths inspected;
- the missing visibility or atomic-swap capability;
- which fields cannot be made service-backed;
- the smallest upstream or architectural capability required.

Best-effort multi-node writes, compensating rollback after partial visibility,
and fail-closed handling of an already mixed public snapshot are not acceptable
substitutes.

## Acceptance evidence

The blocker is resolved only when automated failure injection demonstrates:

- every pre-commit failure leaves the old service and public snapshot visible;
- commit exposes one complete new revision;
- no data source returns prepared values;
- successful transitions trigger exactly one event after commit;
- a post-commit event failure reported by the public open62541 API preserves
  the new revision and activates the documented infrastructure-fault policy;
- a successful return from the public open62541 event API is accepted as
  successful firmware publication without requiring proof of delivery to
  individual subscribers;
- failures hidden inside open62541 event distribution are documented as
  platform limitations;
- independent reads always return values from committed revisions;
- independent review finds no best-effort publication or rollback path.
