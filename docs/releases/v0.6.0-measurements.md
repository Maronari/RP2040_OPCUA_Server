# v0.6.0 T0 measurement builds

Preparation scope: diagnostic builds and collection tools only. This does not
implement signed OTA, health confirmation or fallback, and does not authorize
executing the optional destructive Flash experiment merely by building it.
The production application remains on its existing behavior by default.

## Safety and measurement boundaries

The application profile emits observations; it does not bypass its existing
startup behavior. In particular, the current OPC UA task waits for IPv4.
Without DHCP/cable it must report that initialization is unavailable, not
declare a passed health window. Device monotonic timestamps are distinct from
host serial-enumeration timing and from the actual power-on/bootloader jump.

The RAM probe initializes XIP via the SDK before reading Flash, runs without
FreeRTOS/core1/PSRAM and reboots to the installed application. Its MSP paint
measurement covers the diagnostic window including harness/interrupt use;
it is not a FreeRTOS task watermark or an exclusive ECDSA stack measurement.
Unmeasured/censored/saturated observations must not be rendered as zero.

Application `stack_hwm_bytes` is the **minimum remaining** FreeRTOS stack,
converted from StackType_t words to bytes, not bytes consumed. `init_stack`
is sampled before the legacy acknowledgement/delete path; `opcua_stack` is
sampled after successful server startup, before its first loop iteration.
These bounded observations include instrumentation overhead and are not full
runtime peak claims. The RAM probe's `observed_used_bytes` instead describes
observed MSP paint consumption during its own window; do not combine those
two kinds of stack measurement.

The optional write build targets only offset `0xF57000`, length 4096 bytes,
immediately below the preserved tail. This is inside the **legacy Bank B**,
not free storage and not a deployed v0.6.0 candidate slot. It must require an
exact baseline image match, a valid IDLE legacy OTA record and a completely
erased test sector before any write. A fresh complete verified backup is an
additional host-side execution precondition. It never programs OTA metadata,
Bank A or preserved data. After programming/verifying a fixed test pattern,
it must erase the sector back to its original all-FF state and verify it.
Loss of power during the experiment can leave that staging sector dirty;
local recovery from the verified backup is then required before reusing it.
The optional experiment is unsuitable while preserving an active/staged OTA
transaction, and absence of a valid IDLE record is a refusal, not permission.

Erase/program/read timings in generic slow 03h mode are microbenchmarks, not
production XIP throughput, whole-image copy bounds or release timing evidence.
No hardware measurement is established by successful compilation.

## Execution procedure (prepared, not run)

Run the baseline-pinned RAM experiments **before** installing the instrumented
application. Both probes deliberately require the installed 3,586,824-byte
baseline BIN hash recorded in the earlier hardware evidence; another image
fails their verification. The original installed BIN is preserved locally as
`build/hardware/v060-t0/C3F9822180D224D1-20261025/baseline-flashed.bin`.
Do not change the expected hash merely to make a failed check pass.

For the first, read-only run, enter BOOTSEL manually and use a new local output
directory. Example execution commands below are instructions for a later run;
they have **not** been executed during preparation:

```powershell
rtk proxy powershell -NoProfile -Command 'New-Item -ItemType Directory -Path build/hardware/v060-measurement-ro-001 -ErrorAction Stop'
rtk proxy py -3.12 static/tools/collect_ota_measurements.py run-ram --elf build/v060-measurement-ram/v060_crypto_probe.elf --sha256 8122c5c40ab6e22e4a651f5656dd33708a0e5625be8be44484b3c3b21b4e9969 --picotool build/host-picotool-usb/picotool.exe --port COM6 --seconds 90 --output build/hardware/v060-measurement-ro-001/result.json
```

The tool pins USB serial `C3F9822180D224D1`; capture also checks that the CDC
port belongs to that serial. It verifies RAM load addresses and observes the
probe followed by return to the installed baseline. If enumeration changes the
COM port, supply its actual port. It never loads an application into Flash.

For the separately selected write experiment, use another new directory,
the write ELF/hash above and `--allow-flash-write`. The tool first saves the
entire connected board with `picotool save -r 0x10000000 0x11000000 -v`, keeps
the recovery BIN locally, then validates baseline, canonical IDLE and empty
target sector. Any failed guard prevents RAM execution. An invalid/uninitialized
OTA record is a refusal; the tool never initializes it or erases metadata to
make the test possible. Existing evidence/backups are never overwritten.
Private device data is present in the full backup; keep it under ignored local
build storage. Never publish that BIN or treat it as a factory image.

After RAM measurements, installation of the instrumented application is a
separate local development-flash step with a fresh verified backup. Its normal
startup may perform the same persistence operations as the existing firmware;
it does not implement the future unconfirmed-boot mutation guard. Once that
application is installed, collect its next boot with:

```powershell
rtk proxy py -3.12 static/tools/collect_ota_measurements.py capture --kind app --port COM6 --seconds 90 --output build/hardware/NEW-APP-RUN/startup.json
```

Create the new output directory first and start capture before resetting the
board. Use separate directories/runs for normal DHCP and a deliberately absent
lease/cable; record the actual physical setup alongside the report. The tool
does not infer cable state. With current startup code the no-IPv4 run is
expected to show `waiting_ipv4=unavailable`, not successful offline OPC UA
initialization. This identifies the existing T3 prerequisite rather than
closing it by changing health semantics in a measurement build.

Capture is bounded to 1--300 seconds, 1 MiB and 2048-character console lines.
One application `main_enter` or one RAM `start..PASS/FAIL` session is required;
stale/mixed diagnostic sessions are rejected. Output includes raw console text
and a JSON report. Exit 0 means complete requested evidence, 2 unavailable/
incomplete observations, and 1 failure/malformed evidence. Missing timings and
watermarks are not converted to zero. A completed `UA_Server_run_iterate`
observation means loop progress; its numeric return is a wait interval, not
a UA success status. No report is an OTA health-confirmation or power-cut test.
