# v0.6.0 T0 native OTA and adapter contract

Date: 2026-10-29. This freezes the native verifier, update-service,
boot-transaction and OPC UA adapter boundary for v0.6.0. It is a design
contract only: no firmware implementation, node registration, signing setup,
hardware qualification or confirmation-timing result is implied.

The fixed manifest, recovery geometry and persistent-record byte contracts
remain in [the T0 engineering companion](v0.6.0-ota-design.md). This document
does not modify the release plan or that companion.

## Compatibility baseline and ownership

| Existing namespace-1 String NodeId | Signature | Existing minimum role |
|---|---|---|
| `Device.Maintenance.GetFirmwareUpdateStatus` | `() -> String` | Service |
| `Device.Maintenance.BeginFirmwareUpdate` | `(UInt32 imageSize, UInt32 imageCrc32, UInt32 version) -> Boolean` | Service |
| `Device.Maintenance.WriteFirmwareChunk` | `(ByteString chunk) -> Boolean` | Service |
| `Device.Maintenance.FinalizeFirmwareUpdate` | `() -> Boolean` | Service |
| `Device.Maintenance.AbortFirmwareUpdate` | `() -> Boolean` | Service |

The existing OTA callbacks use `model_require_method_role()`; the centralized
fallback makes unlisted `Device.Maintenance.*` methods Service-only. They do
not call `model_require_admin_session()`. The prior companion's phrase that
existing OTA mutators are "admin-like" is inaccurate. T0 preserves this
Service-role legacy contract; it does not silently make upload clients Admin.

`firmware_update_service` owns one operation and the Flash-writer lifecycle.
The verifier owns no persistence. The boot-transaction owner owns persistent
state and boot-time copy/restore. The T3 boot-window owner owns the
unconfirmed-window decision. OPC UA adapters validate/copy input, enforce role,
call services and map copied results; they own no OTA state.

## Frozen native T1 verifier boundary

These are C-like API contracts, not a wire layout. The manifest remains the
explicit 320-byte serialized format from the companion.

```c
#define OTA_MANIFEST_BYTES             320u
#define OTA_MANIFEST_SIGNED_BYTES      256u
#define OTA_VERIFY_STREAM_CHUNK_BYTES 4096u
#define OTA_TRUSTED_KEY_LIMIT          2u

typedef bool (*ota_image_reader_fn)(void *context, uint32_t offset,
                                    uint8_t *destination, size_t length);

typedef struct {
    uint32_t key_id[OTA_TRUSTED_KEY_LIMIT];
    uint8_t public_key_sec1[OTA_TRUSTED_KEY_LIMIT][65];
    size_t trusted_key_count;             /* 1..2; never a private key */
    char hardware_profile_id[32];
    char firmware_profile_id[32];
    char driver_pack_id[32];
    uint32_t driver_pack_contract_version;
    uint32_t board_revision;
    bool board_revision_present;
    uint32_t recovery_layout_id;
    uint32_t execution_origin;
    uint32_t policy_id;
    uint32_t maximum_image_size;
    uint32_t confirmed_version_floor;
    uint8_t confirmed_content_identity[32]; /* SHA-256 signed-prefix ID */
    bool test_only_allow_downgrade;
} ota_verifier_policy_t;

typedef enum {
    OTA_VERIFY_OK = 0, OTA_VERIFY_MANIFEST_INVALID,
    OTA_VERIFY_UNKNOWN_KEY, OTA_VERIFY_SIGNATURE_INVALID,
    OTA_VERIFY_IMAGE_HASH_MISMATCH, OTA_VERIFY_INCOMPATIBLE,
    OTA_VERIFY_VERSION_REJECTED, OTA_VERIFY_READER_FAILED,
    OTA_VERIFY_ALLOCATION_FAILED, OTA_VERIFY_ALLOCATOR_BUSY
} ota_verify_result_t;

typedef struct {
    uint8_t manifest[OTA_MANIFEST_BYTES];
    uint8_t content_identity[32];
    uint32_t image_size;
    uint32_t packed_version;
    uint32_t trusted_key_id;
} ota_authenticated_manifest_t;

typedef struct {
    ota_authenticated_manifest_t authenticated;
    uint32_t image_crc32;                 /* legacy diagnostic only */
} ota_verified_candidate_snapshot_t;

ota_verify_result_t ota_authenticate_manifest(
    const ota_verifier_policy_t *immutable_policy,
    const uint8_t *manifest, size_t manifest_size,
    ota_authenticated_manifest_t *out_authenticated);

ota_verify_result_t ota_verify_candidate(
    const ota_verifier_policy_t *immutable_policy,
    const uint8_t *manifest, size_t manifest_size,
    ota_image_reader_fn reader, void *reader_context,
    uint32_t available_image_bytes,
    ota_verified_candidate_snapshot_t *out_verified);
```

The policy is compiled/provisioned before the operation and never comes from a
UA client, configuration export or MCU model string. A production policy with
`board_revision_present == false` rejects the package; T5 supplies the actual
provisioned revision and must not guess it. `policy_id` is the compiled
production value `0x06000001`, or the explicit development-only value
`0x86000001`. `test_only_allow_downgrade` is permitted only in the latter;
production policy rejects it as true and clients cannot set either field.
Test-only downgrade bypasses only the floor comparison.
There is one policy identifier: `policy_id` must equal the immutable local
selection and the selected durable record's policy field. A mismatch fails
closed as incompatible; no independent timing-policy field is introduced.

Each API zeroes its output first when that output is non-NULL. A NULL output,
NULL manifest/policy, empty/truncated manifest input, or a manifest size other
than 320 returns `OTA_VERIFY_MANIFEST_INVALID` before accessing input bytes; a
NULL output cannot be zeroed. `ota_verify_candidate` additionally rejects a
NULL reader before any reader access. The verifier validates exact format, IDs, key,
low-S P-256 signature, compatibility, board revision, image length,
same-version identity and floor; then streams only the declared raw image.
`ota_authenticate_manifest` copies only an authenticated 320-byte manifest and
metadata; it does not claim that an image has been verified. `ota_verify_candidate`
may reuse it internally, then verifies the streamed image and returns the full
descriptor plus CRC. `available_image_bytes` must equal the manifest-declared
raw image size and the actually transferred length, never slot capacity. Each
reader call is at most 4,096 bytes and rejects zero length, offset beyond
available bytes, length beyond `available - offset`, and arithmetic overflow.
It has no image-sized buffer and retains no reader/context pointer after return.
Any failure with a non-NULL output zeroes it and releases mbedTLS state. It
computes `image_crc32` in the same bounded stream only for legacy diagnostic
continuity; CRC never authenticates a package. Allocation failure returns
`OTA_VERIFY_ALLOCATION_FAILED`; a concurrent verifier returns
`OTA_VERIFY_ALLOCATOR_BUSY`. Neither waits indefinitely or uses an unbounded
heap.

## Service and boot-transaction boundary

Existing service-result values 0 through 8 stay unchanged. T1 adds no result
enumerator. Existing APIs retain their signatures:

```c
firmware_update_service_result_t firmware_update_service_begin(
    uint32_t image_size, uint32_t image_crc32, uint32_t version_number);
firmware_update_service_result_t firmware_update_service_write_chunk(
    const uint8_t *data, size_t size);
firmware_update_service_result_t firmware_update_service_finalize(void);
firmware_update_service_result_t firmware_update_service_abort(void);
void firmware_update_service_get_status(firmware_update_service_status_t *out);
```

T3 service integration adds only:

```c
firmware_update_service_result_t firmware_update_service_attach_manifest(
    const uint8_t *manifest, size_t manifest_size);
firmware_update_service_result_t firmware_update_service_activate(void);
```

The one service-owned runtime snapshot contains current writer/Begin fields,
`uint8_t manifest[320]`, attached/verified/activation-pending phase, and a
fixed detail token. Its copied manifest/counters/verified snapshot are bounded
within a 2 KiB application-operation allocation cap; allocation failure cleans
the partial operation and reports an existing service failure result. It copies
every accepted manifest and verified snapshot; no borrowed UA buffer survives a
callback. Concurrent Begin, attach, finalize, activate or abort returns
existing `FIRMWARE_UPDATE_RESULT_BUSY` without mutation. Flash serialization
uses the existing coordinator. No service lock spans streaming, hashing, image
copy or reboot.

Attach is legal only while receiving. It requires exactly 320 bytes, calls
`ota_authenticate_manifest` for format/key/signature/compatibility and Begin
size/version, then copies its authenticated manifest snapshot. An identical
repeat succeeds; a changed repeat is rejected without replacing the first copy.
Attach never activates, reboots or makes a candidate bootable.

Finalize retains its legacy signature. It completes bounded transfer/CRC work,
requires an attached manifest, streams staged C through `ota_verify_candidate`,
and only then lets the boot-transaction owner durably record `VERIFIED`. A
BUSY guard rejection happens before acquiring the operation and clears nothing.
Once Finalize has acquired the operation, it clears the volatile receiving
session on every completion path. Missing manifest, invalid key/signature or
hash returns existing `FIRMWARE_UPDATE_RESULT_VERIFY_FAILED` (7), leaves no
bootable candidate and requires fresh Begin. It never reboots.

Activate is legal only for a durable VERIFIED candidate with no active upload.
It requests the boot owner atomically pin candidate identity and commit
`VERIFIED -> BACKUP`; success means that commit succeeded. Reboot is scheduled
only after a successful response can leave the device. Failure schedules no
reboot. The bootloader then performs frozen BACKUP/INSTALL/RESTORE work and
never grants a second candidate launch after `LAUNCH_CONSUMED`.

The persistent reason enum remains exactly the companion's values 0--15; no
value 16 is added. While unconfirmed, OTA mutation returns existing
`FIRMWARE_UPDATE_RESULT_BUSY` (2) and fixed volatile text
`TEMPORARILY_UNAVAILABLE`; it performs no mutation.
This detail is native service state/local diagnostics, not an extra JSON key.
The legacy JSON keeps `lastResult:"BUSY"`; phase identifies the boot window.
The new adapters return `BadResourceUnavailable`.

### Bounded status projection

`GetFirmwareUpdateStatus` preserves every existing JSON key and its type:
`sessionActive`/`otaStateValid` remain booleans; byte/version/attempt counters
remain JSON numbers; `expectedImageCrc32`, `otaImageCrc32`, offsets and sizes
remain their existing hexadecimal strings; and `lastResult`, `otaState` and
`otaLastError` remain strings. Existing keys are never reused for a different
meaning.

Only these compact additive fields are permitted: `phase` (integer 0--5),
`verify` (integer 0--15), `attemptUsed` (Boolean or `null`), `rollback`
(integer 0--15), and `progress` (integer 0--100 or `null`). With image
counters bounded by 5,271,552, attempts bounded by one, a `uint32_t` version,
and the longest existing result/error strings, the frozen worst case is 508
bytes including NUL. The complete legacy payload plus these fields therefore
fits the existing 512-byte buffer. The T0 host model checks that conservative
shape; T3/T4 must also test the actual C formatter before integration.
When a native datum is unavailable, use the permitted `null` or omit its
additive key (including unknown phase/reason); never substitute enum zero or
zero progress for missing data. The existing short/long legacy shape still
depends on `otaStateValid`.

The deterministic v2-to-legacy state projection is:

| v2 phase | Existing `otaState` projection |
|---|---|
| CONFIRMED | `IDLE`, or `FAILED` when a retained failure is present |
| VERIFIED | `STAGED_IN_BANK_B` (historic name; payload is actually slot C at `0xA50000`) |
| BACKUP, INSTALL, RESTORE | `COPYING_TO_BANK_A` |
| LAUNCH_CONSUMED | `READY_TO_BOOT` |

`otaLastError` is projected deterministically: 0 -> `NONE`; 1--7 ->
`VERIFY_FAILED`; 8 -> `COPY_FAILED`; 9 -> `INVALID_RECORD`; 10--11 ->
`VERIFY_FAILED`; 12--13 -> `BOOT_FAILED`; 14 -> `COPY_FAILED`; 15 ->
`INVALID_RECORD`. The additive numeric fields preserve the exact v2 detail.

`otaImageSize == 0` and `otaImageCrc32 == "0x00000000"` together mean an absent candidate, not
unknown data. For a present candidate, the CRC is the one computed in the
single service verification stream while the application remains in that boot.
After reset, bootloader handoff may supply a diagnostic CRC only when scratch
register 0 carries the handoff magic, register 1 contains the running-A
diagnostic CRC, registers 2--3 contain the matching 64-bit durable-record
generation, and native handoff validation succeeds. Policy ID is validated
from durable state against a compiled constant, never from scratch registers.
If a present candidate lacks this validated CRC, it is unavailable and must
not be serialized as zero. Integration must withhold the v2 legacy projection
(`otaStateValid:false`) until a native handoff is valid; it must not expose a
partly-known candidate as a valid legacy state. Status never outputs keys,
manifests or malformed/truncated JSON.

Native diagnostics use the copied verifier result, phase, numeric reasons,
counters and handoff-validity flag. No additional public CLI or registration
is introduced by this design, and these fields do not certify verification,
fallback, timing or hardware qualification.

## Additive OPC UA reservation and mapping

These are design reservations, not current UA registrations or inventory
changes. Both are collision-free against the current source and attach to the
existing `Device.Maintenance.Firmware` object.

| Namespace-1 String NodeId | BrowseName | Signature | Role |
|---|---|---|---|
| `Device.Maintenance.SetFirmwareManifest` | `SetFirmwareManifest` | `(ByteString Manifest[320]) -> Boolean Success` | Admin |
| `Device.Maintenance.ActivateFirmwareUpdate` | `ActivateFirmwareUpdate` | `() -> Boolean Success` | Admin |

| Condition | Existing OTA methods | New methods |
|---|---|---|
| Insecure or insufficient role | Existing Service policy: `BadSecurityModeInsufficient` / `BadUserAccessDenied` | Admin policy; check before service call |
| Wrong type/count or manifest length | `BadInvalidArgument`, Boolean false where applicable | `BadInvalidArgument` |
| Unconfirmed mutation gate | `Good`, Boolean false; BUSY plus volatile detail | `BadResourceUnavailable` |
| No active session, changed reattach, non-VERIFIED activate | `Good`, Boolean false | `BadInvalidState` |
| Unknown key/signature/hash | Finalize: `Good`, false, VERIFY_FAILED detail | Attach: `BadSecurityChecksFailed` |
| Profile/revision/size/version/floor mismatch | `Good`, false with detail | `BadConfigurationError` |
| Flash coordinator busy | `Good`, false | `BadResourceUnavailable` |
| Durable activation write failure | Not applicable | `BadUnexpectedError`, no reboot |
| Success | `Good`, true | `Good`, true |

Authorization always precedes copying and mutation. Legacy operational rejection
retains Good/false compatibility; additive methods use specific status codes.

## Unconfirmed-window mutation ownership

The guard comes from authenticated boot metadata before these owners initialize.
It is not a callback-only check and this contract adds no general cross-service
API. T3 gives each owner a small internal gate against the boot-window snapshot.

| Owner/path | Unconfirmed behavior |
|---|---|
| Config startup selection/recovery | Load compatible RUNNING/LKG data into RAM; no repair, migration, default save or STAGED promotion. |
| Config apply/import/reset/save | Reject before staging or persistent-slot touch. |
| Security startup/build identity/trust | Read existing usable state; defer repair/replacement/commit or fail health. |
| Security users, passwords, certificates, trust, commissioning persistence | Reject before allocation, erase or replacement. |
| History background persistence | Keep bounded RAM sampling; suppress Flash append, compaction and repair; no deferred backlog. |
| Maintenance journal | Suppress repair/append; retain reads and bounded volatile diagnostics. |
| OTA service/adapters | Reject Begin, attach, finalize, activate and abort. |
| Boot transaction/window owner | Only allowed persistent writes: authenticated transition, confirmation/failure/restore and required pre-scheduler recovery. |

Reads/status/volatile diagnostics remain available under existing roles.
Confirmation releases gates only after its durable commit; failure keeps them
active.

## Remaining validation gates

| Task | Required evidence after this contract freeze |
|---|---|
| T1 | Parser/signature/hash vectors; malformed/truncated/low-S/key/profile/revision/version rejection; reader overflow, allocator-busy and cleanup; no image-sized allocation. |
| T2 | Serialized-state and every erase/program/copy/commit interruption; authenticated A/B/C selection, one-launch rule and real fallback. |
| T3 | Every mutation owner; compatible config/security startup; bounded readiness; measured deadline/watchdog; no cable/DHCP/client rollback. |
| T4 | Inventory/signature diff; all roles/insecure sessions; illegal state; two clients/reconnect; JSON bound; asyncua/open62541 and UaExpert. |
| T5 | Protected signing environment/key isolation; artifact provenance; bootloader/reference/industrial builds and resource limits. |

The primary integration work owns the timing-policy ledger and links to this
contract. This freeze does not claim those gates have passed.
