# v0.5.1 — Driver SDK and Industrial Board Driver Integration

## Contract

Baseline: `main` at `c6da6c4` (PR #19, `v0.5.0/transactional-config` →
`main`) — v0.5.0 (Transactional Runtime Configuration) merged, not yet
tagged. Implementation branch `v0.5.1/driver-sdk-industrial-drivers` cut from
this commit.

Goal, from `ROADMAP.md`'s `v0.5.1` section (lines 537-628): freeze the
pre-1.0 native-driver contract (`start`/`stop`/`read`/`write`/`configure`/
`self_test` plus capability/resource descriptors) and implement the firmware
support required by `RP2350_INDUSTRIAL_MVP_V1` before the custom PCB exists.
This release is explicitly **pre-hardware**: industrial-board drivers must be
source-complete, statically analyzed, and validated against host/mock
transports and datasheet-defined behavior, but must not claim electrical,
timing, calibration, or real-device validation. The reference RP2350 + W5500
board remains the hardware used for release builds and runnable
verification.

This release must not implement OPC UA Part 11 Historical Event Access
(v0.8.1), resource/benchmark instrumentation (v0.5.2), Modbus RTU/TCP
(v0.7.0/v0.7.1), board-level diagnostics as OPC UA nodes (v0.6.2 — see scope
decision 4), dynamic native-driver loading (deferred beyond v1.0.0 per
`ROADMAP.md` §5.1), or any change to `ROADMAP.md` itself (roadmap-maintenance
is a separate, explicit task per `ROADMAP.md` rule 11).

**Strategy fixed during pre-implementation interview (2026-09-03)**: the
driver-API "freeze" required by `ROADMAP.md` is deliberately *not* the first
action of this release. A `code-mapper` survey of the `v0.5.0` baseline found
that `telemetry_driver_vtbl_t`'s `write`/`configure`/`self_test` slots
(`services/include/services/telemetry_driver.h:57-72`) are dispatched but
have **zero real implementations** anywhere in the repository, and that no
SPI/I²C/UART bus abstraction exists for host-side mocking (the only
precedent, `w5x00_ethernet_driver.c`, is mocked by header-substitution at the
build level, not through a designed transport interface — see Baseline
below). Freezing the API from the `ROADMAP.md` text alone, before any of
those three vtable slots or any bus abstraction has been exercised by real
code, was judged too likely to require a breaking re-open once a genuinely
complex driver (an SPI register-mapped ADC) is attempted.

This document therefore plans a **pilot phase** in full file-level detail
(T0-T2) and leaves the remaining ~8 industrial drivers/blocks as a scoped
backlog (see "Phase 1 backlog" below), to be expanded into their own
file-level tasks only after the pilot phase lands and the vtable/resource-
claim contract it exercises is reviewed and frozen. This mirrors this
project's own `v0.5.0` precedent of correcting an initially-assumed design
once code-mapper evidence contradicted it (see `docs/releases/v0.5.0.md`
"Contract" section) — plan against evidence, not against the roadmap text in
isolation.

Use `code-mapper` before implementation of any task below to confirm file:line
citations are still current. Assign driver/bus implementation work to
`embedded-systems`-flavored delegation consistent with `v0.5.0`'s pattern;
this document does not pre-assign subagents per task since Phase 1's tasks
are not yet detailed enough to split.

## Baseline

Captured from a `code-mapper` survey of `main` at `c6da6c4` (2026-09-03),
confirmed by direct reads of the cited headers/sources:

**Driver vtable** (`services/include/services/telemetry_driver.h:57-72`):
`telemetry_driver_vtbl_t` already declares `start`/`stop`/`read`/`write`/
`configure`/`self_test`, each dispatched past a NULL check
(`services/src/channel_manager.c:496,515,521` for `write`;
`services/src/sensor_manager.c:269,307,315,321,359,401,406,412` for the
others). **Only `start`/`stop`/`read` are implemented**, by exactly three
drivers (`drivers/src/internal_temperature_channel_driver.c`,
`adc_voltage_channel_driver.c`, `gpio_input_channel_driver.c`, declared in
`drivers/include/drivers/native_channel_driver.h:88-146`). All three
`stop()` implementations are documented no-ops (no DMA/IRQ/PWM state to
release today). No driver implements `write`, `configure`, or `self_test`.
The OPC UA→`channel_manager_write()`→driver-`write()` path itself is fully
wired end to end (`channel_manager.c:481-536`, flag-gated on
`TELEMETRY_CHANNEL_FLAG_WRITABLE`, referenced from `opcua_model/src/
model_access.c`/`model_configuration.c`/`model_address_space.c`) — it has
simply never been exercised by a real driver, because no writable native
driver exists yet.

**Driver catalog** (`services/include/services/driver_catalog.h`,
`services/src/driver_catalog.c`): `config_channel_driver_id_t`
(`driver_catalog.h:20-26`) currently has 3 non-zero values (`INTERNAL_TEMP`=1,
`ADC_VOLTAGE`=2, `GPIO_INPUT`=3); persisted in `device_profile_config_t`
(Flash) and the config-wire format — **append-only, never renumber**.
`driver_catalog_resource_type_t` (`driver_catalog.h:38-44`) currently has
`ADC_INPUT`/`ADC_PERIPHERAL`/`GPIO` — **not** persisted (computed at
apply-time from persisted `driver_id`+`source_index`+`source_flags` via
`driver_catalog_get_resource_claims()`), so extending this enum is safe with
no wire-format migration concern, unlike `config_channel_driver_id_t`.
`driver_catalog_get_resource_claims()` (`driver_catalog.c:200-251`)
hardcodes an `if (driver_id == ...)` chain per driver rather than a per-entry
claim template — every new driver this release adds requires a new branch
here, not just a new catalog-array entry.

One compile-time `option(FIRMWARE_ENABLE_NATIVE_*_DRIVER ...)` exists per
driver in `drivers/CMakeLists.txt:1-3`, conditionally compiling the driver's
`.c` file into `FIRMWARE_DRIVERS` and, via matching `#if` guards in
`driver_catalog.c:34-150`, excluding both the catalog entry and the driver's
symbols from the link when disabled — this pattern already satisfies
`ROADMAP.md`'s "disabled drivers absent from the final ELF" requirement and
should be replicated per new driver/driver-family, not redesigned.

**No SPI/I²C bus abstraction exists.** `drivers/CMakeLists.txt:61-79` links
`hardware_spi` into `FIRMWARE_DRIVERS` already (consumed today only by
`w5x00_ethernet_driver.c`'s WIZnet ioLibrary calls), but `hardware_i2c` and
`hardware_uart` are **not** currently linked. No first-party file under
`drivers/` wraps SPI/I²C/UART calls behind an interface a host test could
substitute; the only mocking precedent
(`static/tests/w5x00_transport/`, `static/tools/test_w5x00_transport.py:23-28`)
works by putting stub copies of third-party header names earlier on the
host-compiler include path than the real ones — a build-level trick, not a
transport interface `ADS8688`'s driver code could take as a parameter or
link against two ways (real SPI vs. mock).

**No GPIO output/writable, synthetic/benchmark, or loopback/mock driver
exists.** `ROADMAP.md:556-562` ("preserve and harden the existing generic/
reference drivers ... GPIO output/writable channel; synthetic benchmark
source; loopback/mock source") describes drivers that do not exist in the
repository today; they must be built new in this release, not hardened.

**Host test precedent**: `static/tests/<suite>/` + `static/tools/test_*.py`
(per-suite host `gcc -std=c11 -Wall -Wextra -Werror` compile of the real
first-party `.c` against a test-directory main and stub FreeRTOS/pico-sdk
headers) + `static/tools/run_host_tests.py` orchestrator (currently 38
suites per the `v0.5.0` implementation report), wired into CI at
`.github/workflows/build.yml:40`. No CMake/CTest integration exists or is
expected.

**Plan-document precedent**: `docs/releases/v0.5.0.md` — `## Contract`,
`## Baseline`, `## Scope decisions frozen before implementation`,
`## Architecture and public-contract rules`, `## File-level implementation
plan` (T1…Tn), `## Verification gate`, `## Completion`; a companion
`docs/releases/v0.5.0-hardware-verification.md` recorded the separate
hardware-verification pass. Since this release has no target hardware yet,
its equivalent companion document (see "Verification gate" below) records a
**compile/mock-validation** pass instead, not a hardware pass.

## Scope decisions frozen before implementation

Resolved during pre-implementation interview (2026-09-03); binding for this
release:

1. **Pilot-first sequencing, not freeze-first.** T1 (GPIO output driver)
   proves `write`/`configure`/`self_test` end to end using only hardware
   already wrapped by the Pico SDK (no new bus abstraction). T2 (`ADS8688`
   SPI AI driver) proves a new SPI bus abstraction together with a real
   register-mapped, datasheet-driven driver. Only after both land is the
   vtable/resource-claim contract reviewed and treated as frozen for the
   remaining industrial drivers. **Kill criterion**: if T2 reveals the
   vtable shape itself (not just the bus abstraction) needs a breaking
   change, make that change here, once, before any Phase 1 driver is
   started — do not let a second driver force a second breaking change.
2. **Bus abstraction: separate, minimal, per-bus — not one unified
   `transport` interface.** SPI (T2), I²C, and UART have different
   transaction shapes (register address + length vs. 7-bit address + R/W vs.
   byte stream); a single interface across all three was assessed as
   premature abstraction. Each bus gets its own minimal interface designed
   against the first driver that actually needs it (SPI via T2; I²C when the
   `TCAL9539` block is reached; UART when `ISOW1432` is reached).
3. **Phase 1 driver order**: the remaining industrial blocks are implemented
   strictly in `ROADMAP.md`'s own listed order (`ROADMAP.md:556-582`:
   `AD5422` → `MAX22190` → `IPS2050` → UIC → `TCAL9539`/`TCA4307`/`TPS2553`
   board-power-service → `ISOW1432` → `TPS3851` → W5500 board rebind → board
   diagnostics), not reordered by inferred hardware dependency (e.g.
   `TCAL9539` gating sensor power for other blocks was raised during
   interview and explicitly rejected as a reordering reason — pre-hardware,
   there is no real power sequencing to respect yet, and ROADMAP-order
   keeps this document's backlog unambiguous).
4. **OPC UA exposure boundary**:
   - AI/AO/DI/DO channel *values* flow through the existing generic channel
     model (v0.4.2, `opcua_model/src/model_channels.c` et al.) automatically
     once a driver is registered in `driver_catalog` and configured as a
     channel — **no new OPC UA model code** for channel values, matching
     v0.4.2's "no channel-specific creation function is added to model core"
     rule.
   - `SupportedDrivers`/`DriverCapabilities` **is** new OPC UA work explicitly
     required by this release (`ROADMAP.md:553`) — a capability model
     distinct from channel values.
   - Board-level diagnostics (`PWR_IN_FAULT_N`, `PWR_3V3_PGOOD_N`, sensor-
     power faults, `TCA4307 READY`, watchdog state, monitored rails) stay
     **driver/vtable-internal** in this release (`self_test`/diagnostic
     return codes only) — `ROADMAP.md` schedules their OPC UA exposure
     explicitly for `v0.6.2` ("board-health aggregation capable of consuming
     ..."), not `v0.5.1`. Do not add OPC UA nodes for board diagnostics in
     this release.
5. **Datasheets**: not present in the repository; fetched and stored under
   `docs/datasheets/` per driver, as implementation reaches that driver —
   not bulk-collected up front.
6. **Schematic stability**: `RP2350_INDUSTRIAL_MVP_V1` is near-final but may
   still change. Every industrial driver isolates pin/bus/resource-index
   assignment into one small board-binding translation unit (or a clearly
   marked block) separate from register/protocol logic, so a schematic
   correction touches one place, not the driver's command-framing code.
7. **No hard deadline**; paced across multiple sessions.
8. **Process**: this plan document first, subagent-delegated implementation
   per task once Phase 1 tasks are detailed, and a compile/mock verification
   report (not a hardware-verification report — no board exists yet) at the
   pilot-phase gate and again at the full-release gate.

## Architecture and public-contract rules

`telemetry_driver_vtbl_t` (`services/include/services/telemetry_driver.h`)
stays the operation-table shape for this release; T1/T2 give `write`/
`configure`/`self_test` their first real bodies but do not change the
function-pointer signatures unless T2 surfaces a documented reason (see
scope decision 1's kill criterion).

`config_channel_driver_id_t` gains one new value per new driver, strictly
appended (never renumbered) after the existing `GPIO_INPUT = 3` — these
values are persisted in Flash and the config-wire format.

`driver_catalog_resource_type_t` gains new members as each bus/resource type
is introduced (e.g. `SPI_CHIP_SELECT`, `SPI_PERIPHERAL`, `I2C_BUS`,
`UART_PERIPHERAL`, `DMA_CHANNEL`, `PIO_STATE_MACHINE`) — not persisted, safe
to extend freely, but still additive (existing values keep their numeric
meaning since some call sites may reasonably switch on them). Each new
driver_id branch added to `driver_catalog_get_resource_claims()`
(`driver_catalog.c:200-251`) follows the existing hardcoded-`if` pattern
already used for the three native drivers — do not introduce a generic
claim-template mechanism as part of this release unless a specific driver
demonstrably cannot be expressed that way; that would be a second,
unplanned abstraction layered on top of an already-decided "extend the
existing pattern" choice.

One `FIRMWARE_ENABLE_NATIVE_<DRIVER>_DRIVER` (or `_DRIVER_FAMILY` for
multi-chip blocks like the `TCAL9539`/`TCA4307`/`TPS2553` board-power
service) CMake option per driver, following `drivers/CMakeLists.txt`'s
existing conditional-source-list + `#if`-guarded catalog-entry pattern
exactly.

The reference RP2350 + W5500 profile and the `RP2350_INDUSTRIAL_MVP_V1`
profile stay separate build targets; industrial drivers must not probe or
initialize on a reference-board boot. This release does not yet define the
second CMake target/profile in detail — that is Phase 1 scope, deferred
until the first industrial driver (T-something in Phase 1) actually needs
it; T1/T2 both target the reference profile only (`ADS8688` in T2 is wired
through the catalog and enabled by its own `FIRMWARE_ENABLE_NATIVE_ADS8688_DRIVER`
option, buildable but not part of the reference profile's default channel
set).

Bus transport code lives under `drivers/include/drivers/` +
`drivers/src/`, separate from each chip's register/protocol logic, so host
tests can substitute it. T2 decides and records the actual mocking mechanism
(a linked seam vs. header substitution) based on what proves least invasive
once attempted — not decided in the abstract here.

- new `static/tests/gpio_output_driver/` host suite (or extend
  `static/tests/channel_manager/`, matching wherever `driver_catalog_test.c`

  "co-located under `channel_manager`" without an exact path);
- `static/tools/run_host_tests.py` (register the new suite if a new
  directory is created).

`self_test` for this driver: read back the pin's own output-enable/level
state via the Pico SDK (no external readback hardware exists) and report
`TELEMETRY_DRIVER_RESULT_OK`/`_HARDWARE_FAILURE` — deliberately the simplest
possible `self_test` body, since this driver's job is to prove the vtable
slot dispatches and returns correctly, not to exercise every diagnostic
nuance (that comes in Phase 1's real chips, which have actual external
status registers).

`configure`: accept a `NULL`-checked config struct setting initial output
level and open-drain vs. push-pull mode (Pico SDK supports both); reject
malformed input with `TELEMETRY_DRIVER_RESULT_INVALID_ARGUMENT`.

Tests cover: `start`/`stop`/`write`/`self_test`/`configure` each in
isolation; `write` through the full `channel_manager_write()` →
driver dispatch chain (extending the existing write-path test coverage,
which today has no writable driver to exercise it against); resource-claim
conflict between a GPIO output and a GPIO input (or another GPIO output) on
the same pin index, reusing `driver_catalog_claims_are_compatible()`
unmodified; disabled-by-CMake-option exclusion from `g_driver_catalog`
(mirroring how the three existing drivers are already proven excludable).

**T1 implementation report (2026-09-03)**: implemented as designed, with two
refinements made during implementation and recorded here rather than left
implicit:

1. **`configure()`'s payload is narrower than originally sketched.** The
   contract section above proposed a config struct carrying both an initial
   level and open-drain/push-pull mode. Implemented instead:
   `native_gpio_output_config_t { bool safe_level; }` only. Open-drain vs.
   push-pull is carried entirely by `source_flags`
   (`NATIVE_GPIO_OUTPUT_SOURCE_OPEN_DRAIN`), set at configuration time and
   validated by `native_gpio_output_source_is_valid()` — the same place
   every other native driver's mode-like flags already live, and the same
   data `driver_catalog_get_resource_claims()` would need if a future driver
   variant ever made open-drain affect resource claims. Letting `configure()`
   independently retarget the mode at runtime would have created two
   sources of truth for the same property with no precedent elsewhere in
   the driver set.
2. **Open-drain is real, not a stub.** `native_gpio_output_write()` asserts
   (post-invert `true`) by actively driving the pin low and releases
   (post-invert `false`) by switching the pin to high-impedance input,
   relying on an internal pull-up enabled in `native_gpio_output_start()`.
   `self_test()` checks pad *direction* for open-drain (deterministic,
   independent of external wiring) and pad *direction + level* for
   push-pull (the pad reads back its own driven level on real hardware).

**New host-test precedent**: no existing suite compiled a real
`drivers/src/*.c` file against a *stateful* mocked Pico SDK header — the only
prior mocking precedent (`static/tests/w5x00_transport/`) shadows third-party
headers with stubs, but they are effectively no-ops proving link-level
substitution, not real behavior. `static/tests/gpio_output_driver/hardware/gpio.h`
+ `hardware_gpio_stub.c` (new, this task) is the first to model actual pad
state (output-enable, driven level, pull-up) so host tests can assert on
open-drain assert/release transitions and catch a `self_test()` that would
pass despite a wrong observed pad state — not merely that the code compiles
and links. `static/tests/channel_manager/driver_catalog_test.c` and
`channel_manager_test.c` were extended in place (fakes/assertions for the
new `driver_id`, resource-claim conflict between `GPIO_INPUT`/`GPIO_OUTPUT`
on the same pin, and the first real write-path exercise of
`channel_manager_write_value()` against a writable driver), per T1's
original file list.

Verified: `static/tools/run_host_tests.py` — all suites pass except the two
requiring the `asyncua` Python package (`test_verify_channel_model_e2e.py`,
`test_export_nodeset.py`), which is installed in CI
(`.github/workflows/build.yml:37`) but absent from this implementation

### T1 addendum — `configure(channel, NULL)` activation bug found on hardware (2026-09-03)

Live verification on the reference RP2350 + W5500 board (not merely a
compile/host-test pass — the pilot-phase gate itself, per "Verification
gate" below, only requires compile/mock validation, but hardware happened to
be available and the user asked to exercise it) surfaced a defect the host
test suite did not catch, because the host test suite's own expectations
were written to match the same wrong assumption as the driver code.

**Symptom**: flashed the T1 build, then used `static/tools/stage_config.py`
to import a configuration adding one `gpio_output` channel
(`driverId=4`, GPIO2, push-pull). `ValidateImportedConfig` succeeded, but
the client's connection dropped during/around `ApplyImportedConfig`, and the
device subsequently produced no further serial log output and did not
respond on the network — recovered only by re-entering BOOTSEL and
reflashing.

**Root cause**: `sensor_manager_start_candidates()`
(`services/src/sensor_manager.c:314-315`) and `sensor_manager_restart_active()`
(`services/src/sensor_manager.c:405-407`) — the only two real call sites of
`telemetry_driver_vtbl_t.configure` in the firmware, confirmed by a
repository-wide grep — always invoke `channel.driver->configure(&channel, NULL)`.
`native_gpio_output_configure()` was written to require a non-NULL
`native_gpio_output_config_t` and return `TELEMETRY_DRIVER_RESULT_INVALID_ARGUMENT`
otherwise, based on an assumption about the calling convention that was
never checked against the actual call sites before writing the driver. Every
real channel activation of a `gpio_output` channel therefore failed at the
`configure()` step, tripping `sensor_manager_start_candidates()`'s
failure/rollback path. `static/tests/gpio_output_driver/gpio_output_driver_test.c`'s
own `test_configure()` asserted the same wrong expectation
(`configure(&channel, NULL) == INVALID_ARGUMENT`), so it passed while
validating a bug rather than catching one — host-testing a driver in
isolation from its real caller's calling convention is not sufficient by
itself.

**What is, and is not, established about the full symptom**: the
`configure()` defect is confirmed by direct code reading, not inference —
every real caller passes NULL, and the driver rejected NULL. Whether it
alone explains the complete observed symptom (silent hang, not merely a
clean rejected transaction) is not fully established from this session's
evidence; a device console log fragment captured during the incident also
showed `[NET] MACRAW socket recovery failed: len=60 sr=0x00 count=1`
immediately after `ValidateImportedConfig OK`, which may be an independent
contributing factor or coincidental. This is recorded as an open question,
not resolved by this addendum, and is not blocking for the pilot-phase
gate since T1/T2 do not claim hardware qualification (see "v0.5.1
constraints" in `AGENTS.md`).

**Fix**: `native_gpio_output_configure()` now treats `config == NULL` as the
normal case (apply the released/safe default via `native_gpio_output_write()`),
not an error; a non-NULL payload (no current caller supplies one) overrides
the default. `gpio_output_driver_test.c`'s `test_configure()` was corrected
to assert the real expected behavior and documents the bug inline.
`static/tools/run_host_tests.py` — full suite re-verified green (same two
pre-existing `asyncua`-only exclusions as before).

**Fix re-verified on hardware, but did not fully resolve the live scenario**:
the corrected firmware was reflashed and re-tested with the same
`stage_config.py import` against the same GPIO-output-channel payload.
`ValidateImportedConfig` succeeded; `ApplyImportedConfig` this time failed
*cleanly* with `"failed to persist imported configuration"` (a normal,
audited, non-hanging rejection — `opcua_model/src/model_ota.c:486-488`,
covering any false return from `config_service_replace_and_save()`, not
specifically an activation/`configure()` failure) — a clear improvement over
the first attempt's silent hang. However, `[NET] MACRAW socket recovery
failed: ...` appeared again immediately afterward, and the device again
stopped producing any further serial output and stopped responding on the
network, recovered only by a second BOOTSEL reflash. The hang reproduced
**with the `configure()` fix in place**, which rules out `configure()` as
the (sole) cause of the hang itself, even though it was a confirmed, real,
independently-worth-fixing bug.

**Second finding — corrected diagnosis: test-setup error, not a firmware
bug.** Both live-hardware hangs were initially misdiagnosed in this
addendum's first draft as a pre-existing Flash-write/W5x00-driver timing
interaction and a follow-up investigation task was spawned on that premise.
That premise was wrong and the task was withdrawn. The real cause: the test
channel was configured with `sourceIndex = 2` (GPIO2), chosen by checking
`waveshare_core2350b_16mb_psram8mb.h`'s generic `PICO_DEFAULT_SPI_*_PIN`
macros (SCK=18/TX=19/RX=16/CSN=17) and treating GPIO2 as free. Those macros
are not what the W5x00 driver actually uses.
`port/ioLibrary_Driver/inc/w5x00_spi.h:18-21` hardcodes the real pins:
`PIN_SCK=2, PIN_MOSI=3, PIN_MISO=0, PIN_CS=1` (no other definition exists —
confirmed by a repository-wide grep), wired up by
`port/ioLibrary_Driver/src/w5x00_spi.c`'s `gpio_set_function(PIN_SCK, GPIO_FUNC_SPI)`
et al. GPIO2 is the W5500's SPI clock line, not a free pin. This driver's
own `native_gpio_output_start()` calls `gpio_init(source->source_index)`,
which resets the pad's function back to plain SIO — tearing GPIO2 away from
`GPIO_FUNC_SPI` and breaking the SPI bus to the W5500 out from under the
running Ethernet driver. `wizchip_read()`/`wizchip_write()`
(`w5x00_spi.h:54-74`) are blocking with no timeout by design ("SPI hardware
always transfers at a known data rate"), so a broken SPI clock line means
those calls block forever — exactly the observed total, unrecoverable
silence in both attempts.

This is not a defect in this driver's code (it did exactly what it was
configured to do — drive the pin it was given) or in the Flash/config-apply
pipeline. It is a verification-process error: the live test picked a pin
without checking the actual hardware pin ownership beyond the board's
generic (and, for this SPI bus, unused) default macros. **General takeaway
for Phase 1 and any future live-hardware channel test**: before configuring
a channel on any GPIO index during verification, check
`port/ioLibrary_Driver/inc/w5x00_spi.h` (W5500: GPIO0-3),
`boards/include/boards/<board>.h`'s board-specific `_CS_PIN`/similar defines
(e.g. `WAVESHARE_CORE2350B_PSRAM_CS_PIN=47`), and any other fixed-function
pin ownership — not just the generic Pico-SDK `PICO_DEFAULT_*_PIN` macros,
which this board's own W5x00 integration does not use. Separately, this
exposes a real (if lower-priority) architectural gap worth noting for
Phase 1: `driver_catalog_get_resource_claims()`/`driver_catalog_claims_are_compatible()`
only detect conflicts *between configured channels* — nothing in
configuration validation rejects a channel claiming a GPIO/resource already
permanently owned by a fixed board peripheral (W5500 SPI, PSRAM CS). A
human operator or another LLM session could reproduce this exact hang
through the configurator with no code defect involved. Not fixed as part of
T1; noted here for Phase 1 or a dedicated hardening task to consider a
reserved-pin exclusion list.

Both hangs were fully recoverable via BOOTSEL reflash of the same
known-good T1 image; no hardware damage occurred.

**Third finding — the real remaining blocker: v0.5.0's verify gate cannot
pass a write-only channel.** Retesting on a genuinely free pin (GPIO10 —
checked against `w5x00_spi.h`, `waveshare_core2350b_16mb_psram8mb.h`'s
`_CS_PIN`/I²C/UART/LED defines, and `HARDWARE_MVP.md`'s industrial-only
`GPIO10` reference, which does not apply to this reference-board build)
produced no MACRAW error and no hang, but activation still failed cleanly
with `"failed to persist imported configuration"` — deterministically,
reproduced identically on a repeat attempt. A control test (re-importing the
*unchanged* running config, no new channel) applied successfully, proving
the Flash staging/commit path itself was healthy and narrowing the failure
to something specific about activating the new channel.

Root cause, found by adding temporary diagnostic `printf`s to
`native_gpio_output_start/configure/self_test` and rebuilding: all three
calls succeeded on real hardware (`write_result=0`, `self_test ok=1`) — the
driver was never the problem. The failure is in
`sensor_manager_verify_candidate_channels()`
(`services/src/sensor_manager.c:488-537`, the v0.5.0 T4 "verify" gate): it
requires *every* new/changed enabled channel to produce a
`SERVICE_QUALITY_GOOD` read via `channel_manager_poll_all()` within a
bounded number of attempts before the transaction is allowed to commit.
`gpio_output` has no `.read` (it is write-only by design), so
`channel_manager_poll_all()`'s own NULL-check
(`services/src/channel_manager.c:660-665`) always skips it, its quality/
timestamp never become valid, and the verify gate exhausts its retry budget
and fails every time — a structural mismatch between a v0.5.0 gate designed
and tested only against read-capable drivers and v0.5.1's first write-only
driver class. This is exactly the kind of gap the pilot-first strategy in
this document's "Contract" section was adopted to surface before Phase 1
multiplies it across `AD5422`, `IPS2050`, and other write-only industrial
drivers.

**Fix**: `sensor_manager_verify_candidate_channels()` now excludes any
channel whose `driver->read == NULL` from the verify gate entirely —
`sensor_manager_start_candidates()`'s prior `start`/`configure`/`self_test`
calls are that channel's only, and sufficient, hardware-facing confirmation
(matching the role a read provides for a readable channel). Regression
coverage added to `static/tests/sensor_manager/sensor_manager_rollback_test.c`
(a second fake driver entry with no `.read`, activated alongside the
unchanged existing channel) — this is the first host-test exercise of a
write-only channel through the real production activation path, not just
through this driver's own isolated suite. Full host suite re-verified green
(same two pre-existing `asyncua`-only exclusions). The temporary diagnostic
`printf`s were removed from the shipped driver before this commit.

**Verified end-to-end on hardware after the fix**: reflashed; imported the
same GPIO10 `gpio_output`-channel config. Device console:
`[OPC UA]\tApplyImportedConfig succeeded`. The transaction correctly tripped
`model_config_requires_server_reboot()` (adding a channel changes the
model) and the server began its T6 controlled restart; a client
(`stage_config.py`) still connected during the shutdown drain hit the
already-known, already-fixed-with-a-fallback open62541 restart livelock
documented in `docs/releases/v0.5.0-hardware-verification.md` (`UA_Server_run_shutdown
did not complete within 8000 ms ... falling back to a hard reboot`) — this
is pre-existing, accepted v0.5.0 behavior, not a new defect, and it worked
exactly as designed: the watchdog fallback rebooted the device, which came
back up cleanly on the same network. Post-reboot `GetConfigState`:
`runningRevision` advanced (89→90), `rebootRequired: false`,
`stagedDiffers: false` — the new revision is genuinely committed, not
merely staged. `ExportConfig` confirms `channel.gpio_output.1` persisted
with `driverId: 4`, `sourceIndex: 10`, `inUse: true`, `enabled: true`,
surviving the reboot. This closes the live end-to-end verification T1 set
out to establish: a real writable channel, added through the real OPC UA
configuration-management path, activated, committed, and confirmed
persistent on the reference RP2350 + W5500 board.

**Process lessons carried into Phase 1**:
1. Before writing any driver's `configure()`/`self_test()`/`write()` body,
   grep the actual call sites in `sensor_manager.c`/`channel_manager.c` for
   the exact arguments passed and the exact gates a new/changed channel must
   satisfy (start, configure, self_test, *and* the read-based verify gate)
   — do not infer any of this from the vtable's doc comment alone, and do
   not treat a host-test pass as sufficient evidence when the test's own
   expectations were derived from the same unchecked assumption as the code
   under test.
2. Before configuring a channel on any GPIO index during live verification,
   check `port/ioLibrary_Driver/inc/w5x00_spi.h` (W5500: GPIO0-3),
   `boards/include/boards/<board>.h`'s board-specific `_CS_PIN`/similar
   defines (e.g. `WAVESHARE_CORE2350B_PSRAM_CS_PIN=47`), and any other
   fixed-function pin ownership — not just the generic Pico-SDK
   `PICO_DEFAULT_*_PIN` macros, which this board's own W5x00 integration
   does not use.
3. A clean host-test pass and a clean cross-compile are not evidence about
   real-hardware activation gates or pin-ownership conflicts — three
   distinct real issues in this task (a driver bug, a test-setup pin
   collision, and a cross-cutting architectural gap) were each found only
   by testing on real hardware, in order of decreasing "should have been
   caught earlier."
4. Separately (lower priority, not fixed here): `driver_catalog_get_resource_claims()`/
   `driver_catalog_claims_are_compatible()` only detect conflicts *between
   configured channels* — nothing in configuration validation rejects a
   channel claiming a GPIO/resource already permanently owned by a fixed
   board peripheral (W5500 SPI, PSRAM CS). Worth a reserved-pin exclusion
   list in Phase 1 or a dedicated hardening task.

Goal: prove a real, datasheet-driven, register-mapped SPI driver together
with the bus abstraction that makes it host-testable — the two hardest,
least-precedented parts of this entire release, isolated into one pilot
task per scope decision 1.

Primary files:

  `drivers/src/spi_transport.c` (or `rp2350_spi_transport.c` if a
  board-specific vs. generic split proves necessary once attempted): the
  new SPI bus abstraction — signature and mocking mechanism decided during
  this task, recorded here once settled (do not pre-decide in this
  document; T2's own implementation report, added to this file when T2
  lands, is the source of truth for what was actually built);
- new `drivers/include/drivers/ads8688_driver.h` + `drivers/src/ads8688_driver.c`
  (chip-specific register/command framing, range selection, scaling,

  public-contract rules");

  `CONFIG_CHANNEL_DRIVER_ADS8688 = 5`);
- `services/src/driver_catalog.c` (new catalog entry/vtable/resource-claim
  branch, claiming a new `DRIVER_CATALOG_RESOURCE_SPI_CHIP_SELECT` at the
  channel's configured CS index and a shared
  `DRIVER_CATALOG_RESOURCE_SPI_PERIPHERAL`, mirroring the existing
  ADC-input/ADC-peripheral pairing);
- `services/include/services/driver_catalog.h` (append the two new
  `driver_catalog_resource_type_t` members);
- `drivers/CMakeLists.txt` (`FIRMWARE_ENABLE_NATIVE_ADS8688_DRIVER` option;
  link `hardware_spi` explicitly against the new sources if not already
  transitively available);
- new `static/tests/spi_transport/` (bus-abstraction unit tests: command
  framing, mock transaction injection, timeout);
- new `static/tests/ads8688_driver/` (register/command tests against the
  mocked transport: range-select encoding, conversion/scaling, status-byte
  decoding, timeout/retry, device-not-present classification);
- `static/tools/run_host_tests.py` (register both new suites).

`self_test` distinguishes, per `ROADMAP.md:586`, at least: supported and
passed (device responds with an expected identity/status pattern over the
mocked or real transport), supported but hardware unavailable/not present
(transport timeout or a defined "not present" response — the pilot proves
this classification exists and is exercised by a host test, since the
reference board never has this chip attached), and failed (a present but
malfunctioning response). This is the concrete behavior `ROADMAP.md`'s
"must not treat absent pre-production hardware as a false board fault"
requirement cashes out to for this driver.

Resource-claim validation, timeout/retry/backoff, and error classification
follow `ROADMAP.md:585`'s "one missing or failing peripheral must not block
unrelated channels" — proven at the driver level here; the board-diagnostics
aggregation across multiple peripherals is out of scope (v0.6.2, per scope
decision 4).

Tests cover: every `AI0..AI3` range/scaling path against datasheet-derived
expected register values (from T0's reference note); malformed/status-fault
response handling; timeout and device-not-present classification;
resource-claim conflict when two channels claim the same CS index; a new
mock driver (a trivial second SPI device) can be added without editing
`spi_transport.[ch]` or core channel-manager logic, proving the abstraction
is genuinely reusable and not `ADS8688`-shaped.

**T2 implementation report (2026-09-05)**: built as designed, with the
mocking mechanism decided per this section's own deferral ("decided during
this task"): a **linked seam**, not header substitution. `spi_transport.h`
declares a small `spi_bus_vtbl_t` (`cs_assert`/`cs_deassert`/`transfer`)
mirroring the codebase's existing `telemetry_driver_vtbl_t` pattern;
`ads8688_driver.c` depends only on that generic interface plus a
`native_ads8688_bind_bus()` injection point, never on
`hardware_spi`/`hardware_gpio` directly. The real board binding
(`drivers/rp2350_spi_bus.[ch]`) implements the vtable against real
`hardware_spi`/`hardware_gpio` and lives in its own translation unit, so
host tests link `ads8688_driver.c` + `spi_transport.c` + a fake vtable
directly — zero Pico SDK header stubbing needed, unlike T1's `gpio_output`
suite (which calls Pico SDK GPIO functions directly and therefore needed a
stateful `hardware/gpio.h` stub). This is a stronger mocking mechanism than
T1's for any *future* SPI driver that adopts the same pattern.

Real board-binding pins: `HARDWARE_MVP.md` already documents them
(`GPIO12`=MISO, `GPIO13`=`ADC_CS_N`, `GPIO14`=SCK, `GPIO15`=MOSI) — not yet
wired into any compile-time profile (no `RP2350_INDUSTRIAL_MVP_V1` CMake
target exists yet, per this document's own "Architecture and public-contract
rules" deferring that to Phase 1), so `rp2350_spi_bus.c` compiles into the
reference build but is only reachable if `native_ads8688_bind_bus()` is
called with a real config — which nothing does yet on the reference profile.

Resource claims: implemented as two claims per channel exactly as scoped —
`DRIVER_CATALOG_RESOURCE_SPI_CHIP_SELECT` (exclusive, keyed by the ADS8688
mux input index 0-7, preventing two channels from binding the same
physical input) and `DRIVER_CATALOG_RESOURCE_SPI_PERIPHERAL` (shared, fixed
index 0, since only one physical chip is in scope this release — a
multi-chip board would need the CS claim keyed by an actual GPIO pin
instead, noted as a scope limitation, not fixed here).

`self_test` classification (`ROADMAP.md:586`) implemented via a
write/echo-toggle probe on the channel's own `Range_CHn` register (the
`ADS8688` has no dedicated status/alarm register — confirmed in
`docs/datasheets/ADS8688-register-notes.md`): two different valid range
codes are written and read back; a constant echo that never tracks either
written value maps to `TELEMETRY_DRIVER_RESULT_TIMEOUT` ("hardware
unavailable/not present" — this is what an absent/floating chip produces,
since the write-cycle echo is generated by the chip itself, not looped back
in software), a changing-but-wrong echo maps to
`TELEMETRY_DRIVER_RESULT_HARDWARE_FAILURE` ("failed"), and a correct echo
on both probes maps to `TELEMETRY_DRIVER_RESULT_OK` ("passed"). The
channel's actual configured range is restored afterward regardless of
outcome. `TELEMETRY_DRIVER_RESULT_TIMEOUT`/`_HARDWARE_FAILURE` are reused
from the existing generic result enum rather than adding new enum values
for this distinction — consistent with not expanding shared API surface
without a demonstrated need from more than one driver.

Read path proven for both bipolar and unipolar ranges, including negative
(2's-complement) codes, `scale`/`offset` application, and the one-frame
conversion pipeline delay (`MAN_Ch_n` issued twice so the second frame's
result is guaranteed to belong to the just-requested channel, not a
previously-selected one) — a real protocol subtlety a naive single-frame
implementation would have gotten silently wrong.

**Verified**: `static/tools/run_host_tests.py` — full suite green (same two
pre-existing `asyncua`-only exclusions as T1). Reference-profile Debug
build — clean link, only the pre-existing `_stat is not implemented`
newlib note. `FIRMWARE_ENABLE_NATIVE_ADS8688_DRIVER=OFF` build confirms
both `ads8688_driver.c.obj` and `rp2350_spi_bus.c.obj` are absent from
`FIRMWARE_DRIVERS`'s object list (`spi_transport.c.obj` remains, correctly
— it is unconditional shared infrastructure, not gated by any one driver's
option, matching `flash_operation_coordinator.c`'s precedent). No live
hardware verification was attempted or is required for T2 — the `ADS8688`
chip does not physically exist yet; this release's own scope explicitly
requires only compile/mock validation for industrial drivers (see "v0.5.1
constraints" in `AGENTS.md`).

### API/resource-claim review gate (pilot phase close)

Before any Phase 1 task starts: review T1+T2 against
`ROADMAP.md:547` ("freeze the pre-1.0 driver API candidate") with concrete
evidence from two real drivers now implemented. Record in this document
(new subsection here) whether the vtable signatures, the
`driver_catalog_resource_type_t` extension pattern, and the per-bus
transport-abstraction approach are adopted as-is for Phase 1, or whether a
specific, evidenced change is needed — and if so, make it once here, not
per-driver in Phase 1.

**Review outcome (2026-09-05)**: adopted as-is for Phase 1, with three
findings recorded for follow-through rather than a breaking change:

1. **`telemetry_driver_vtbl_t` signatures are frozen unchanged.** Two very
   different drivers (a simple digital output, a register-mapped SPI ADC)
   implemented `start`/`stop`/`read`/`write`/`configure`/`self_test`
   without needing a new parameter or return type. The one real surprise —
   `configure(channel, NULL)` being the universal calling convention — was
   found and fixed in T1, not here; T2's `ads8688_driver.c` does not
   implement `configure` at all (mode lives in `source_flags`, per the T1
   finding), and needed no further change to the contract.
2. **`driver_catalog_resource_type_t`'s extend-as-needed pattern holds.**
   Both T1 (`GPIO`, reused) and T2 (two new SPI-specific types) fit the
   existing `{type, index, shared}` claim shape without modification.
   Recorded limitation, not fixed: the claim model has no cross-type
   physical-pin awareness (a `DRIVER_CATALOG_RESOURCE_GPIO` claim on pin 2
   and a hypothetical `DRIVER_CATALOG_RESOURCE_SPI_CHIP_SELECT` claim
   nominally at "index 2" would not conflict even if they happened to name
   the same physical GPIO), and the SPI peripheral claim is currently a
   fixed index (single-chip assumption). Both are pre-existing-shape
   limitations, not new ones introduced by T1/T2, and are deferred to
   Phase 1 or a dedicated hardening task rather than fixed by breaking the
   claim shape now.
3. **Per-bus transport abstraction, not a unified one, is confirmed the
   right call.** T2's SPI interface (`cs_assert`/`cs_deassert`/`transfer`)
   has no natural generalization to I²C's addressed, no-chip-select
   transaction shape or to a raw UART byte stream — attempting one now,
   before a real I²C or UART consumer exists, would still be speculative.
   Each remaining bus gets its own minimal interface when its first real
   driver (`TCAL9539` for I²C, `ISOW1432` for UART) needs it, per scope
   decision 2, using T2's linked-seam mocking approach as the preferred
   default over T1's header-substitution/stateful-stub approach where the
   driver doesn't already need to call Pico SDK functions directly.

No breaking change to any T1/T2 file was made as a result of this review.
Phase 1 driver tasks may now be scoped in detail.

### T3 — `AD5422` industrial analog-output driver (Phase 1 item 1)

Goal: the first Phase 1 driver, applying T1/T2's now-frozen contract to a
genuinely different hardware topology — two `AD5422BREZ` chips wired as a
2-device SPI daisy chain (`HARDWARE_MVP.md` section 3.2), not independent
chip-selects like `ADS8688`'s single-chip multi-mux-input topology.

**Datasheet research finding, not assumed going in**: `HARDWARE_MVP.md`'s
wiring diagram (`AO0` `SDIN`→chip, `AO0` `SDO`→`AO1` `SDIN`, `AO1` `SDO`→
"NC / dedicated test point", explicitly *not* the shared `BOARD_SPI_MISO`)
means writing one channel does **not** require caching and resending the
other channel's last value — the datasheet's own daisy-chain protocol
(`docs/datasheets/AD5422-register-notes.md`) already lets each device's
24-bit word be addressed independently within one 48-bit/`LATCH` frame; the
untouched device's slot just gets `NOP` (`0x000000`). This is simpler than
a first read of "two chips share one CS-equivalent signal" suggests, and is
proven directly by a host test asserting the untouched channel's simulated
register is unchanged after writing the other.

**Real hardware caveat found and not resolved (see
`ad5422_driver.h`'s file-level doc and the register notes)**: neither
`AD5422`'s `SDO` returns to the shared controller `MISO` per the current
documented wiring — `AO0`'s feeds only `AO1`'s `SDIN`, and `AO1`'s goes to
a dedicated test point. This means the datasheet-documented SPI readback
this driver's `self_test()` implements may not be electrically observable
by firmware on the real board at all. Not fixed here (a wiring/hardware
question, and the driver's protocol implementation is correct against the
chip's own documented capability); flagged for hardware bring-up, and
diagnosis may ultimately need the shared `FAULT` pin instead of SPI
readback.

Primary files:

- new `drivers/include/drivers/ad5422_driver.h` + `drivers/src/ad5422_driver.c`
  (register/command framing, per the daisy-chain notes above; reuses
  `drivers/spi_transport.h` and the existing `rp2350_spi_bus.[ch]` binding
  from T2 — no new board-binding file needed, both `ADS8688` and `AD5422`
  sit on the same physical SPI bus per `HARDWARE_MVP.md`);
- `services/include/services/driver_catalog.h` (append
  `CONFIG_CHANNEL_DRIVER_AD5422 = 6`; append a new
  `DRIVER_CATALOG_RESOURCE_AD5422_CHANNEL` resource type — see below, *not*
  a reuse of `DRIVER_CATALOG_RESOURCE_SPI_CHIP_SELECT`);
- `services/src/driver_catalog.c` (new catalog entry/vtable/resource-claim
  branch);
- `drivers/CMakeLists.txt` (`FIRMWARE_ENABLE_NATIVE_AD5422_DRIVER` option;
  `rp2350_spi_bus.c`'s build condition widened to "`ADS8688` OR `AD5422`
  enabled", since it is now shared infrastructure, not `ADS8688`-specific);
- new `static/tests/ad5422_driver/` (fake two-device daisy-chain model:
  per-device data/control registers, readback-select + `NOP` clock-out);
- `static/tests/channel_manager/driver_catalog_test.c` (fakes + resource-claim
  assertions, including the cross-driver non-conflict proof below);
- `static/tools/run_host_tests.py` (register the new suite).

**Resource-claim design correction made during implementation, not
assumed from the T2 template**: the pilot-phase review gate's own item 2
already flagged that the claim model has no cross-type physical-pin
awareness. Applying T2's `ADS8688` claim shape naively to `AD5422` (reusing
`DRIVER_CATALOG_RESOURCE_SPI_CHIP_SELECT` at index 0/1) would have made an
`ADS8688` channel on mux index 0 and an `AD5422` channel on `AO0` (also
index 0) **false-conflict** — they are different physical devices with no
real resource in common at that index. Root cause: `AD5422` has no
chip-select pin at all (shared `LATCH`), so "chip-select" was never the
right resource name for its per-channel claim. Fixed by adding a genuinely
distinct `DRIVER_CATALOG_RESOURCE_AD5422_CHANNEL` type (exclusive, index =
`source_index` 0/1) for "this daisy-chain position is in use", while both
drivers correctly share `DRIVER_CATALOG_RESOURCE_SPI_PERIPHERAL` at a fixed
index 0 (they are genuinely on the same physical bus). Proven by a host
test asserting exactly this non-conflict/conflict pair.

`self_test` distinguishes the same three outcomes as `ADS8688`'s, via the
datasheet's write-then-readback sequence on the data register (two
distinct probe values); `stop()` is a real safe-state action here (writes
`OUTEN=0`), unlike every read-only native driver's no-op `stop()`, per
`ROADMAP.md`'s "safe-state integration" requirement.

**Verified**: `static/tools/run_host_tests.py` — full suite green (same two
pre-existing `asyncua`-only exclusions as T1/T2), including a host-test
proof that writing one channel leaves the other's simulated register byte-
for-byte unchanged. Reference-profile Debug build and
`FIRMWARE_ENABLE_NATIVE_AD5422_DRIVER=OFF` exclusion check — see this
document's `## Verification gate` section for the recorded results. No
live hardware verification attempted or required — the chip exists on the
board schematic but not as assembled hardware.

### T4 — `MAX22190` industrial digital-input driver (Phase 1 item 2)

Goal: `DI0..DI3` on the single `MAX22190ATJ+` industrial digital-input
frontend (`HARDWARE_MVP.md`), the first Phase 1 driver whose protocol
mandates a CRC on every frame.

**Datasheet research finding, not assumed going in**: the chip's SPI mode
(24-bit frame length, mandatory CRC, no daisy chain vs. wider/daisy-chain
modes) is a hardware pin-strapping choice (`M0`/`M1`), not
software-selectable — `HARDWARE_MVP.md` ties both to `GND_SYS`, selecting
Mode 0. So this driver only ever implements Mode 0; no runtime mode
negotiation exists or is needed. A second, easy-to-miss protocol quirk:
every response's first byte is *always* the chip's live `DI[7:0]` status,
regardless of which register the frame addressed — `read()` still issues an
explicit `DI`-register read command to keep request semantics uniform with
every other driver, but the sampled bit actually comes from the response's
first byte per the datasheet's own description of that behavior (see
`docs/datasheets/MAX22190-register-notes.md`).

**Real hardware caveat found and not resolved (see `max22190_driver.h`'s
file-level doc and the register notes)**: the CRC-5 polynomial
(`x^5+x^4+x^2+x^0`) is stated in the datasheet, but no worked example or
reference test vector is provided anywhere in it, and no physical chip is
available to validate against. `max22190_crc5()` implements the standard
bit-serial construction for a polynomial CRC of this shape (MSB-first,
zero-initialized, XOR mask `0x15` — the polynomial's low 5 bits with the
implicit leading term dropped), and the host test suite proves it is at
least *internally consistent* (see verification below), but internal
consistency is not the same as matching real silicon. **This is the single
largest correctness risk in this driver and must be the first thing
checked during hardware bring-up** — a wrong implementation fails loudly
(every transaction rejected with `FAULT1.CRC` / `TELEMETRY_DRIVER_RESULT_HARDWARE_FAILURE`
from `start()`), not silently, so this risk is bounded in practice.

Primary files:

- new `drivers/include/drivers/max22190_driver.h` + `drivers/src/max22190_driver.c`
  (CRC-5, 24-bit frame build/decode, `start`/`stop`/`read`/`self_test`;
  reuses `drivers/spi_transport.h` and the existing `rp2350_spi_bus.[ch]`
  binding from T2/T3 — no new board-binding file needed, all three chips
  sit on the same physical SPI bus per `HARDWARE_MVP.md`);
- `services/include/services/driver_catalog.h` (append
  `CONFIG_CHANNEL_DRIVER_MAX22190 = 7`; append a new
  `DRIVER_CATALOG_RESOURCE_MAX22190_CHANNEL` resource type — see below, a
  fresh type again, not a reuse of `SPI_CHIP_SELECT` or `AD5422_CHANNEL`);
- `services/src/driver_catalog.c` (new catalog entry/vtable/resource-claim
  branch);
- `drivers/CMakeLists.txt` (`FIRMWARE_ENABLE_NATIVE_MAX22190_DRIVER` option;

### T5 — `IPS2050` protected high-side digital-output driver (Phase 1 item 3)

Goal: `DO0..DO1` on the `IPS2050HTR` dual protected high-side output IC
(`HARDWARE_MVP.md` section 3.4) — the first Phase 1 driver that is a plain
GPIO frontend rather than a bus/protocol device, and the first with an
explicit, fully pre-written firmware contract in `HARDWARE_MVP.md` itself
("Required DO firmware contract from the 2026-09-02 IPS2050H schematic").

**Board-topology finding, not assumed going in**: unlike `ADS8688`/
`AD5422`/`MAX22190`, the actual output at each channel is generated
entirely in hardware as `DO_SAFE_EN AND DOx_CMD`, where `DO_SAFE_EN =
SYS_RESET_N AND DO_ENABLE_REQ` is itself hardware-generated from a single
shared `GPIO10` line and the board's reset supervisor. This driver never
computes that AND — it only ever drives `DOx_CMD` (`GPIO20`/`GPIO21`) and
asserts the shared `DO_ENABLE_REQ` once. `GPIO10`/`GPIO20`/`GPIO21` all
carry `100k -> GND_SYS` pull-downs on the MCU sheet, so an uninitialized or
just-reset MCU is already hardware-safe (outputs off) before any firmware
runs — this driver's job is only to keep that property true once it does
run, not to establish it.

- new `drivers/include/drivers/ips2050_driver.h` + `drivers/src/ips2050_driver.c`

  SPI/I2C/UART transport involved at all);
- `services/include/services/driver_catalog.h` (append

  `DRIVER_CATALOG_RESOURCE_IPS2050_CHANNEL` resource type);

- new `static/tests/ips2050_driver/` (a stateful GPIO stub, a fresh one
  rather than reusing T1's — see below);
- `static/tests/channel_manager/driver_catalog_test.c` (fakes + resource-claim
  assertions);
- `static/tools/run_host_tests.py` (register the new suite).

**Test-infrastructure decision made during implementation**: this driver's
`self_test()` reads a real externally-driven hardware fault input
(`DOx_FAULT`), a case T1's existing `gpio_output_driver` stateful
`hardware/gpio.h` stub cannot model — that stub's `gpio_get()` only ever
returns the *pull* state for a non-driven pin, since `gpio_output`'s own
self_test only ever re-reads what it just drove itself. A second, separate
`hardware/gpio.h` stub was written for this test directory instead, adding
an explicit `external_level` field the test can set directly to simulate
the board's `TLP383`/pull-up circuit asserting or releasing the fault line,
independent of anything the driver itself drives. T1's stub was not
modified.

**Resource-claim model applied consistently with T3/T4's established
lesson, in the simplest form yet**: `IPS2050`'s two channels are exclusive
GPIO-backed outputs with no shared bus resource at all (unlike `ADS8688`/
`AD5422`/`MAX22190`, which all additionally share one `SPI_PERIPHERAL`
claim), so `DRIVER_CATALOG_RESOURCE_IPS2050_CHANNEL` is this driver's only
claim type, and `driver_catalog_get_resource_claims()` returns exactly one
claim for it (the default `required = 1u`, no `else if` addition needed to
the multi-claim branch). Per this catalog's already-documented limitation,
the underlying fixed `GPIO20..GPIO23`/`GPIO10` pins are not separately
claimed as `DRIVER_CATALOG_RESOURCE_GPIO` — consistent with how `ADS8688`'s
SPI pins are not claimed either, since a user configuring a generic
`gpio_input`/`gpio_output` channel on one of those numbers would be a
misconfiguration this catalog has never defended against for any
dedicated-chip driver.

`self_test()` is a genuine hardware fault readback (unlike `gpio_output`'s
self-consistency-only check) but, being a plain GPIO read rather than an
SPI transaction, only ever reports two outcomes (`OK`/
`HARDWARE_FAILURE`) — there is no communication-failure mode to
distinguish a third "supported but hardware unavailable" outcome for.
`stop()` is a real safe-state action (drives `DOx_CMD` low), matching
`AD5422`'s convention; the shared `DO_ENABLE_REQ` assertion is
deliberately never undone by any per-channel `stop()`, proven by a
dedicated host test that deliberately corrupts the enable pin's simulated
state between two channels' `start()` calls to catch an accidental

### T6 — `UIC` universal-input driver: digital input / pulse count / frequency / period (Phase 1 item 4, partial)

Goal: `UIC0..UIC3` on `GPIO40..GPIO43` (`HARDWARE_MVP.md` section 3.5) —
the first Phase 1 driver behind a comparator frontend rather than a
bus/protocol chip, and the first to introduce RP2350 PIO to this codebase
at all (no `.pio` file or `hardware_pio` link existed before this driver).

**Scope decision, made deliberately and documented, not a silent gap**:
`HARDWARE_MVP.md` section 3.5 also lists a quadrature-encoder mode "using
channel pairs." **That mode is not implemented in this release.** A
correct RP2350 PIO quadrature decoder needs a materially more complex
state machine (a 2-bit transition-table design, several times this
driver's other modes' 3-instruction program) than could be confidently
hand-written and left completely unverified in this pre-hardware, no-PIO-
simulator environment. Unlike every other caveat flagged so far this
release (MAX22190's CRC, AD5422's SDO wiring), a wrong quadrature decoder
would not fail loudly — it would silently miscount or reverse direction
under specific transition sequences, which is a materially worse risk
profile to ship un-reviewable. Deferred to a tracked follow-up (see the
Phase 1 backlog below); the `pio_edge_counter_t` abstraction this driver's
other modes are built on does not block adding it later.

**Design decision: PIO without DMA, on-demand register snapshot instead of
FIFO streaming**. `ROADMAP.md` calls for "RP2350 PIO and DMA where
appropriate rather than nondeterministic task-level GPIO polling." Since a
channel `read()` is a low-rate periodic `SensorTask` poll (not a
continuous high-rate capture), a continuously-DMA-drained FIFO ring buffer
was judged unnecessary complexity for this need. Instead,
`uic_pulse_counter.pio` runs a 3-instruction loop (`wait 0 pin`/`wait 1
pin`/`jmp x-- top`) that decrements the state machine's `X` scratch
register on every full low-to-high pulse (the PIO ISA has no direct
increment, only `JMP X--`); `rp2350_pio_edge_counter.c` reads the running
total on demand via `pio_sm_exec()`-injected `mov isr, x` + `push`
instructions (a documented pico-sdk technique for interjecting
instructions into a stalled state machine without disturbing its
autonomous execution), converting `0xFFFFFFFF - X` into a monotonic
(mod 2^32) edge count. No DMA channel is used at all for this driver.

Primary files:

- new `drivers/include/drivers/pio_edge_counter.h` (the linked-seam
  abstraction, T2-style, isolating `native_uic_driver.c`'s mode logic from
  the real PIO backing so it host-tests against a fake);
- new `drivers/src/uic_pulse_counter.pio` (the 3-instruction counting
  loop) + `drivers/include/drivers/rp2350_pio_edge_counter.h` +
  `drivers/src/rp2350_pio_edge_counter.c` (the real RP2350 backing --
  claims one PIO state machine per active counter-mode channel across the
  RP2350's 3 PIO blocks, loading the shared program into each block at
  most once);
- new `drivers/include/drivers/uic_driver.h` + `drivers/src/uic_driver.c`
  (mode dispatch via `source_flags[2:0]`; frequency/period computed from
  the edge-count/time delta between successive `read()` calls, using

  timestamp so a `uint32_t` counter or tick wraparound is handled
  correctly without special-casing);
- `services/include/services/driver_catalog.h` (append
  `CONFIG_CHANNEL_DRIVER_UIC = 9`; append a new
  `DRIVER_CATALOG_RESOURCE_UIC_CHANNEL` resource type);
- `services/src/driver_catalog.c` (new catalog entry/vtable/resource-claim

### T7 — board-power-service block: `TCAL9539` + `TCA4307` + `TPS2553` (Phase 1 item 5)

Goal: sensor-power enable/fault control (4x `TPS2553`) and external-I2C
isolation/recovery control (2x `TCA4307`), both wired entirely through the
`TCAL9539` internal I2C GPIO expander (`HARDWARE_MVP.md` section covering
the service-I/O sheet) -- the first Phase 1 item that is architecturally
**not** a `native_channel_driver.h`-shaped telemetry channel at all, and
the first consumer of a new I2C transport abstraction (scope decision 2).

**Architectural finding, not assumed going in**: neither `TCA4307` nor
`TPS2553` is a separately I2C-addressable device on this board -- both are
controlled/read purely through specific `TCAL9539` GPIO pins
(`HARDWARE_MVP.md`: "The four `TPS2553 EN` controls... moved to `TCAL9539`
outputs"; `TCA4307` `EN`/`READY` routed through `P10..P13`). This
collapses what ROADMAP describes as three chips into one real I2C device
driver (`tcal9539_driver.c`) plus one interpreting service
(`board_power_service.c`) that assigns board-specific meaning to specific
pins -- no dedicated `TCA4307`/`AD5422`-style per-chip driver files exist
for the other two parts, and none are needed.

**I2C address caveat, flagged prominently like every other unresolved
hardware fact this release**: `HARDWARE_MVP.md` documents the `TCAL9539`'s
pin *functions* in full detail but never specifies this board's actual
`A1`/`A0` address-strap pins. `tcal9539_driver.c` defaults to `0x74`
(`A1=A0=L`) as a placeholder; see
`docs/datasheets/TCAL9539-register-notes.md`'s explicit caveat. Like a
wrong `MAX22190` CRC, a wrong address here fails loudly (every transaction
NACKs), not silently.

Primary files:

- new `drivers/include/drivers/i2c_transport.h` + `drivers/src/i2c_transport.c`
  (the generic I2C bus contract, mirroring T2's `spi_transport.h`'s role
  and linked-seam mocking approach exactly; register read/write

  data" I2C framing);
- new `drivers/include/drivers/rp2350_i2c_bus.h` + `drivers/src/rp2350_i2c_bus.c`

  T2's `rp2350_spi_bus.[ch]`'s lazy shared-peripheral-init pattern);
- new `drivers/include/drivers/tcal9539_driver.h` + `drivers/src/tcal9539_driver.c`
  (register-level read/write only -- deliberately has no pin-meaning

- new `services/include/services/board_power_service.h` + `services/src/board_power_service.c`
  (the actual board service: hardware-safe init ordering, per-port sensor-

  `static/tests/board_power_service/` (a fake I2C register-file device

  pointer write/read framing and this board's exact pin-to-bit mapping --
  not just that calls dispatch);
- `static/tools/run_host_tests.py` (register the three new suites).

**Hardware-safe init ordering, verified directly, not just asserted**:
`TCAL9539`'s Output Port registers power up at `0xFF` (every pin driven
high) while Configuration registers also power up at `0xFF` (every pin an
input) -- meaning a naive "set Configuration for outputs, then set
Output level" init sequence would transiently drive every soon-to-be-
output pin high (asserting every `SENSOR_PWR_EN`/`I2C_ISOL_EN` line,
exactly the unsafe state `HARDWARE_MVP.md` warns against for `TCA4307`
default state) before the correct level is ever written.
`board_power_service_init()` writes Output Port registers to the
safe/disabled level *first*, then Configuration registers second --
mirrors `gpio_output_channel_driver.c`'s own "set level before enabling
direction" ordering from T1, applied here at the register-transaction
level instead of the GPIO-pad level. A host test asserts the actual write
order (not just the final register values) to catch a regression that
would only matter for a few microseconds and would be invisible to a
value-only assertion.

**Bounded power-cycle sequencing**: `board_power_start_sensor_power_cycle()`
disables a port immediately and schedules a single, fixed-duration
(`BOARD_POWER_CYCLE_OFF_MS` = 200 ms) re-enable via `board_power_poll()`
-- a one-shot sequence, not a retry loop, matching `ROADMAP.md`'s "one
missing/failing peripheral must not block unrelated channels" requirement
and avoiding an unbounded retry storm against a persistently-faulted
port. This exact timing/retry policy is a first-cut choice, explicitly
documented as tunable once real `TPS2553` recovery timing is measured
during hardware bring-up.

**Verified**: `static/tools/run_host_tests.py` -- full suite green (same
two pre-existing `asyncua`-only exclusions as T1-T6), including host-test

### T8 — `ISOW1432` raw half-duplex RS-485 transport binding (Phase 1 item 6)
