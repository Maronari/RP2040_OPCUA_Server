### Bugs found and fixed during this verification pass

Two real firmware bugs, both pre-existing (not introduced by the history/
alarm work), found only by actually exercising the server over the wire
against physical hardware:

1. **A&C standard methods completely uncallable** (`5bed455`): the
   compiled-in namespace-zero nodeset lacked `HasComponent` references from
   the Server object to `ConditionRefresh` and from each channel-alarm
   condition instance to `Acknowledge`. Every call failed with
   `BadMethodInvalid` regardless of arguments. Root-caused by capturing
   open62541's own diagnostic log from the device's serial console (COM6)
   during a live repro — no case of the log's "resolved a different NodeId"
   diagnosis fired, proving `findChildByBrowsename()` found no reference at
   all, not a mismatched one.
2. **Task stack-watermark diagnostic nodes always `BadNotFound`** (`4d54aef`):
   `model_add_task_stack_high_water_node()` never set the node context's
   `kind`/`task_name` fields the read callback depends on. Fixed by threading
   through the actual registered FreeRTOS task name (`OpcUaTask`,
   `NetworkTask`, `SensorTask`) alongside the short OPC/SPI/TEMP display
   name used in the NodeId.

Six further bugs were found and fixed in `verify_v043.py` itself (event
`SourceNode` matching against the wrong node, wrong event-subscription
source, `read_data_value()`'s `raise_on_bad_status=True` default, a
false-pass path in the pagination retry, and a guard-lifetime/
re-acknowledge sequencing bug) — see commit `408a1f5` for the full list.

Also removed (`4d54aef`): the temporary open62541 diagnostic logging added
during the Acknowledge/ConditionRefresh investigation
(`checkAdjustArguments()`, `callWithResolvedMethodAndObject()`,
`callWithMethodAndObject()` in `port/open62541/open62541.c`) — both root
causes are now fixed and committed, so the diagnostics are gone per their
own "remove once root cause is confirmed" comments.

## Jitter and stack watermarks under combined load

Measured with `build/measure_jitter_and_stack.py`: 60s of concurrent
HistoryRead bursts (both numeric channels, ~3 requests/sec each) and an
alarm on/off event burst (`channel.temperature.1` forced HIGH and restored
every ~3s via `SetChannelConfig`/`ApplyConfig`, 18 toggles total), while
reading back `channel.adc.test1`'s actual recorded sample timestamps
(configured `SamplePeriodMs`/`HistoryIntervalMs` = 1000ms).

**Sampling jitter**: 56 recorded intervals over the 60s window (~4 fewer
than the nominal 60 one-second beats). Minimum interval 999ms — essentially
exactly on the configured period under no contention. A handful of
intervals landed near 2000ms (one full period skipped/delayed) rather than
showing runaway drift; mean 1144.5ms, stdev 354ms, driven by that bimodal
on-time-vs-one-skip distribution rather than gradual jitter. No formal
jitter budget exists yet for v0.4.3 (`ROADMAP.md`'s "benchmark budget"
language refers to the v0.5.2 benchmark-reporting release, not yet
implemented) — this is a raw measurement for the record, not a pass/fail
against a defined threshold.

**Task stack high-watermarks** (bytes free, worst-case since boot; lower is
tighter):

| Task | Before 60s load | After 60s load |
|---|---|---|
| `OpcUaTask` (OPC) | 13600 | 13600 |
| `NetworkTask` (SPI) | 874 | 874 |
| `SensorTask` (TEMP) | 280 | 280 |

No new worst-case was hit by this load on any task. `SensorTask`'s 280-byte
margin is the tightest of the three and worth watching in future releases,
but is unchanged by this release's history/alarm additions (both before and
after this session's fix, the raw watermark value itself — once actually
readable — was already 280; the fix corrected visibility, not behavior). No
documented safety-margin threshold exists yet (`ROADMAP.md`'s "no stack
watermark below the documented safety margin" is later-release scope) to
evaluate this against.
