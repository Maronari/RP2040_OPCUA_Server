# v0.6.0 T0 reference-board flashing and startup observation

Date: 2026-10-25. The owner authorized checking and flashing the connected
board. This is a baseline startup observation for
[T0](v0.6.0-ota-design.md), not signed-OTA, fallback or health-confirmation
acceptance. No new OTA firmware implementation was flashed.

## Host tool and preservation checks

The SDK-provided `build/_deps/picotool/picotool.exe` was built without USB
support and could not perform save/load. Built a separate USB-capable
picotool v2.2.0 from the already present source, using native MinGW GCC 15.2.0
and the installed libusb, under `build/host-picotool-usb`. No driver, OTP,
partition, key or production source change was made. Host-tool compilation emitted third-party
GCC allocator warnings; this was not a first-party firmware compilation.

Before programming, saved and verified all 16,777,216 Flash bytes:

`build/hardware/v060-t0/C3F9822180D224D1-20261025/flash-before.bin`

Backup SHA-256:
`20f005d7ba29d687e04c9443a99232848c633e83a15b05f7c97b3484f3961bef`.

The preserved certificate/private-key bytes matched the build provisioning
assets; no key contents were printed or added to source control. Backups and
raw observations are in the ignored `build/` directory and are not release
artifacts. The backup includes the original running image and persistent data.

Loaded the BIN at `0x10000000` with verification. Its sector-rounded erase end
is `0x1036C000`, below the persistent data tail at `0x10F58000`. Before reboot,
saved and verified that tail again; all 688,128 bytes matched the backup
exactly, including configuration, identity/trust, history, journal and OTA state
regions. Tail SHA-256:
`3205896d3265a504629ddfd8e3cdb36a807442feb9180070b1207528c9415425`.
This proves preservation through host programming, before application startup;
normal application history/journal activity is not claimed byte-immutable.

## Observed startup

Performed one software reboot from BOOTSEL, not a cold power cycle. A bounded
50-second USB serial observation opened `COM6` approximately 0.906 seconds
after issuing the reboot command. Host read timestamps are observations with
USB buffering/polling latency, not exact task execution timestamps.

| Observation | Host elapsed time | Evidence/limit |
|---|---:|---|
| PSRAM self-test passed | 2.391 s | Reported 8,388,608 bytes, CS GP47 |
| W5500 response | 2.688 s | `Software reset skipped, VERSIONR=0x00` |
| Network startup | 2.688 s | IPv4 `0.0.0.0`, DHCP `Selecting` |
| Sensor initialization | 2.781 s | `Sensor manager init failed` |
| Firmware running | 2.844 s | `Running FW=0.6.0` |
| Identity provisioning | 2.844 s | Existing identity matches build assets |
| Scheduler workers | 2.844 s | Network, sensor, time, alarm and OPC UA tasks created |
| Initialization completion | 2.844 s | Free heap and minimum-so-far both 278,872 bytes |
| OPC UA startup | 2.844 s | Task started but `Waiting for IPv4 before server startup` |

The startup log reports requested watchdog timeout 80,000 ms and effective
timeout 16,000 ms. No deliberate hang/reset test measured that timeout.
Heap figures are boot-time internal FreeRTOS measurements, not the eventual
runtime peak, task stack watermark, static SRAM or PSRAM peak. The PSRAM
initialization line reported free 8,388,584 bytes before application workloads;
it is not steady-state free PSRAM. No stack-watermark measurement was collected.

No further reboot/disconnection was observed within this capture, but the
capture did not establish sustained subsystem health. Early boot text was
partially missed/interleaved, so a zero observed `Booting`-line count cannot
mean zero actual boots. The recorded data is insufficient to select the final
OTA confirmation duration or close T0.

The first GetEndpoints probe of the historical benchmark address timed out
while the host's earlier bounded DHCP helper was stopped. The follow-up below
restored that helper and established the live address. Credentials were absent
from the host environment; no authenticated client, live inventory or UaExpert
pass is claimed. No insecure test profile or persistent network override was
enabled to make the check pass.

## Open hardware checks

Confirm W5500 presence/power/wiring against the current SPI0 assignment
(MISO GP0, CS GP1, SCK GP2, MOSI GP3). An unreadable controller version and
missing DHCP do not establish whether the peripheral is absent, miswired,
unpowered or requires a cold restart; no board fault is inferred. Diagnose
the sensor initialization failure against the preserved running configuration.
The OPC UA IPv4 wait also confirms why the existing predicate cannot satisfy
the approved cable/DHCP-independent OTA health rule.

Read-only source mapping: `port/ioLibrary_Driver/src/w5x00_spi.c` skips its
software reset when the identity register does not report W5500's expected
`0x04`. The current driver continues initialization through helpers without
propagated return statuses. `configure_netif()` in
`drivers/src/w5x00_ethernet_driver.c` unconditionally marks its software netif
up, so the observed link-up line is not evidence of an operational PHY.
`services/src/sensor_manager.c` can independently reject the persisted channel
configuration/catalog/resource claims or fail driver activation. Successful
PSRAM initialization and later worker creation do not prove channel activation.

Signed-image verification, crypto-enabled bootloader sizing, bounded health
signals, real fallback, instrumented cold-boot timing, interruption campaigns and confirmation
timing remain unperformed v0.6.0 gates. ROADMAP, the authoritative release plan
and public/configuration contracts are unchanged by this observation.

## DHCP restoration and owner-reported power cycle

The owner confirmed W5500 power/wiring on the compiled SPI0 pins and direct
Ethernet connection to the PC. The host's Ethernet interface is Up at 100 Mbps,
ifIndex 15, `169.254.34.198/16`. Previous v0.5.2 evidence and the existing
ignored `build/direct_dhcp.py` established the earlier target-only DHCP setup;
the helper was not running at the start of this observation.

Restarted the unchanged bounded helper, filtering client MAC
`00:08:dc:12:34:56`, offering `169.254.34.100`, with a 3,600-second lease. Its
log recorded DISCOVER/OFFER/REQUEST/ACK. It ignored unrelated client MACs.
GetEndpoints then passed against the now-live address and returned
Basic256Sha256/SignAndEncrypt plus the existing None endpoint. Therefore the
initial `VERSIONR=0x00` is not proof that the SPI/PHY path remained unusable;
real DHCP and OPC UA traffic subsequently worked.

The first cold-start observer timed out without observing disconnection.
Afterward the owner reported disconnecting/reconnecting power. A second DHCP
run recorded the board's DISCOVER and REQUEST and sent OFFER/ACK again. The
subsequent 50-second serial capture recorded:

- DHCP Bound, address `169.254.34.100/16`, gateway `169.254.34.198`;
- full namespace/address-space initialization and successful OPC UA startup;
- free internal FreeRTOS heap 281,376 bytes at server startup, minimum-so-far
  278,872 bytes;
- PSRAM total 8,388,608, free 3,159,288 and largest free block 3,159,264 bytes
  at server startup. These are snapshots, not a whole-run peak;
- existing Commissioning/AcceptAll state and an ApplicationUri/certificate URI
  mismatch warning. These were observed, not silently fixed or reclassified
  as v0.6.0 security acceptance.

This is an **owner-reported power cycle with post-start capture**; neither
the actual power-on timestamp nor the complete early cold-boot interval was
measured. It cannot select an OTA deadline/window. The latest endpoint probe
passed. An attempted anonymous read-only session was rejected at
ActivateSession with `BadUserAccessDenied`, so no successful Read/inventory
is claimed. No password was guessed and no authorization setting was changed.

and no resource-claim conflict. Thus incompatible persisted driver IDs are not
supported as the explanation for the first sensor-manager failure. GPIO10
self-test or later registration/verification remains a hypothesis requiring
an explicit result signal; no channel fault cause or sensor pass is asserted.
