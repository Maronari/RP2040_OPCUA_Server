# v0.5.1 driver verification report

Compile/mock-validation report for the v0.5.1 Driver SDK and industrial
board drivers, covering T0-T11 (`docs/releases/v0.5.1.md`). This is a
results record against that plan document's frozen scope, not a plan
itself -- see `docs/releases/v0.5.1.md` for design rationale and scope
decisions.

**This release's drivers are compile/mock validated, not hardware
qualified.** `RP2350_INDUSTRIAL_MVP_V1` does not exist as assembled
hardware; no claim of electrical, timing, calibration or real-device
correctness is made anywhere in this report, per `ROADMAP.md` section
5.2's cross-version qualification-gate language. This is the direct
counterpart to `v0.5.0`'s `-hardware-verification.md` companion, for a
release where hardware verification is not possible at all rather than
attempted-and-found-wanting.

Date: 2026-09-06. Branch: `v0.5.1/driver-sdk-industrial-drivers`, through
T13 (also-tracked items picked up after Phase 1's frozen order T3-T11
closed).

## Verification method, applied uniformly per item

Every native driver/service added this release went through the same four
checks, individually recorded in `docs/releases/v0.5.1.md`'s per-T-item
sections:

1. **Host tests** (`static/tools/run_host_tests.py`) against a fake
   bus/chip/GPIO model exercising real protocol semantics (not just vtable
   dispatch) -- success, transport-failure, and (where the chip has a
   readback path) malformed/status-fault paths.
2. **ARM cross-compile** of the full firmware (`FIRMWARE_DRIVERS`/
   `FIRMWARE_SERVICES` libraries and the complete `device_profile_basic.elf`)
   with the driver's `FIRMWARE_ENABLE_NATIVE_*` option at its default (on).
3. **Disabled-option exclusion check**: a scratch CMake configure+build with
   that option (and, for T11, each of its two dependency options in turn)
   set to `OFF`, confirming the driver's object file is absent from the
   entire tree and the firmware still links -- proving compile-time
   exclusion, not just runtime hiding. Scratch build directories were
   removed after each check.
4. **`static/tools/run_first_party_cppcheck.py`**, run after every item.

failures in a full run are `test_verify_channel_model_e2e.py` and

named 'asyncua'` -- a pre-existing local-environment package gap
unrelated to this release (reproduces identically on `main` before any
v0.5.1 change).

## Unconfirmed hardware facts (bring-up risks, ranked by how loudly they fail)

These are the facts this release could not verify without hardware or
independently obtainable references. Each is documented in its driver's
own header/register-notes file; consolidated here for one-stop bring-up
review, per the still-open `ROADMAP.md:588` resource-claim documentation
item's spirit (see Open items -- a full consolidated resource-claim
document does not yet exist; this table is not a substitute for it).

| Driver | Unconfirmed fact | Failure mode if wrong |
|---|---|---|
| `MAX22190` | Hand-written CRC-5 bit-serial algorithm, no datasheet worked example exists to check against | Loud: every real transaction rejected (`FAULT1.CRC`), immediately obvious at bring-up |
| `UIC` (T6) | Hand-written PIO pulse-counter program (`uic_pulse_counter.pio`), never run on real silicon or a simulator | Silent risk in principle, but the program is only 3 instructions and its assembled disassembly was inspected directly against the intended design |
| `TCAL9539` | I2C device address (`0x74`, `A1=A0=L` assumed) -- schematic doesn't document the strap | Loud: every transaction NACKs |
| `AD5422` | `self_test()`'s SPI readback may not be electrically observable at all (`SDO` wiring only reaches the other daisy-chain device, not the shared `MISO`) | Silent: `self_test` could report a false negative indefinitely; flagged, not fixed, since it is a hardware wiring question outside this driver's scope |
| Rail monitors (T12) | No documented divider ratio for `VIN_PROTECTED_MON`/`AO_15V_MON`/`ANA_5V_MON` -- `rail_*_volts` report raw pin volts, not real rail volts | Silent by design: values are internally consistent but not meaningful as absolute voltages until the schematic specifies the divider network; flagged in the field-level doc comment rather than guessed at |

`ISOW1432`'s UART instance (`UART1`) and `IPS2050`/`TPS3851`'s GPIO
assignments are **not** in this table -- both were independently confirmed
(the former against the official RP2350 datasheet, the latter is a direct
citation from `HARDWARE_MVP.md`'s own frozen GPIO map with no ambiguity).

## `ROADMAP.md:548-591` ("Required implementation") checklist comparison

Status legend: **Done** (verified this release), **Partial** (some real
coverage, real gap remains), **Open** (not started).

- Line 548, freeze the pre-1.0 driver API candidate: **Done** -- the
  pilot phase (T1/T2) plus the "API/resource-claim review gate" in
  `docs/releases/v0.5.1.md` closed this before Phase 1 began.
- Line 549, native drivers statically linked, instantiated only by stable
  `driver_id`: **Done** -- `config_channel_driver_id_t` values 0-9, never
  renumbered.
- Line 550, one compile-time enable/disable option per driver/family:
  **Done** -- every T-item has its own `FIRMWARE_ENABLE_NATIVE_*` option
  (T11's board-diagnostics option is additionally gated on two others,
  documented in its own T-item section).
- Line 551, disabled drivers/dependencies absent from final ELF/UF2:
  **Done** -- verified per T-item via scratch builds.
- Line 552, keep reference-board and `RP2350_INDUSTRIAL_MVP_V1` profiles
  separate, industrial profile building must not make the reference
  profile touch nonexistent peripherals during boot: **Partial**. No
  industrial driver's `bind()`/`init()` call is wired into any live
  board-bring-up path in `app/` yet (every driver added this release is
  compiled but inert, matching the "pre-hardware, compile/mock validated
  only" bar) -- so the reference profile trivially never touches this
  code today, but that is true by omission, not by an actual verified
  two-profile boot-time behavior test, and **no separate
  `RP2350_INDUSTRIAL_MVP_V1` build profile/target exists at all** --
  every driver was proven individually in the single `app/basic_profile`
  target with its option flipped. This is a real, not yet closed, gap
  between what has been proven and what this line asks for.
- Line 553, driver-pack manifests (`base`/`environmental`/`motion`/
  `industrial`/`development`): **Open**.
- Line 554, `SupportedDrivers`/`DriverCapabilities` OPC UA capability
  model: **Done** (corrected from this report's original **Open** rating
  -- T13 found `Device.Compatibility.SupportedDrivers` already existed
  and predated v0.5.1 entirely, walking `driver_catalog` generically with
  zero new-driver-specific code needed; the actual gap was a resource-
  type-name mapping that had silently fallen behind six new v0.5.1
  resource types, now fixed with a self-updating regression guard).
- Line 555, versioned host-side sensor/module descriptor format:
  **Open**.
- Line 556, driver capability descriptors (readable/writable/polling/
  interrupt-driven/self-test/calibration/required resources): **Partial**
  -- `driver_catalog_entry_t.capabilities` (START/STOP/READ/WRITE/
  CONFIGURE/SELF_TEST) and resource claims exist and are exercised by
  every driver; "polling vs. interrupt-driven" and "calibration" are not
  modeled as explicit descriptor fields anywhere.
- Lines 557-563, preserve/harden existing generic drivers (internal
  temperature, ADC voltage, GPIO input, GPIO output, synthetic benchmark,
  loopback/mock): **Partial** -- `gpio_output` was hardened in T1 (real
  bugs found and fixed on hardware); internal temperature, ADC voltage,
  and GPIO input were not touched this release (not known-broken, but not
  re-verified either); synthetic-benchmark/loopback-mock sources were not
  inventoried against this release's new patterns.
- Lines 564-569, extend RP2350 ADC-voltage driver for `ADC0..ADC7`:
  **Partial** -- done to the extent currently possible: raw `ADC4..ADC6`
  rail monitoring is implemented (T12, driver-internal via
  `board_diagnostics_service.c`, no confirmed divider ratio so reported
  as raw pin volts, not real rail volts). `ADC0..ADC3`/UIC analog mode
  remains explicitly blocked by the current `TLV3214` comparator-only
  frontend per `HARDWARE_MVP.md` (a schematic gap, not an implementation
  gap); `ADC7` remains intentionally unassigned per that document's own
  instruction.
- Lines 570-582, add board/native driver support for `RP2350_INDUSTRIAL_MVP_V1`'s
  firmware-visible components: **Done**, except two explicitly flagged
  partial gaps already called out in their own T-items: `UIC`
  quadrature-encoder mode (T6) and "monitored internal rails" within
  board diagnostics (T11, tracked as the ADC extension above). Every
  other named component (`ADS8688`, 2x`AD5422`, `MAX22190`, `IPS2050`,
  `UIC` non-quadrature modes, `TCAL9539`+2x`TCA4307`+4x`TPS2553`,
  `ISOW1432`, `TPS3851`, W5500 rebind, board diagnostics minus rails) has
  a working, tested, compiled-in implementation.
- Line 583, do not create meaningless drivers for passive/autonomous
  parts: **Done** -- `TCA4307`/`TPS2553` deliberately have no dedicated
  driver files (T7 finding); represented only through `TCAL9539`
  pin-level enable/fault semantics.
- Line 584, separate bus/protocol logic from RP2350 peripheral access for
  host-test injection: **Done** -- `spi_transport.h`/`i2c_transport.h`/
  `uart_transport.h`, all with real backings and all host-tested against
  fakes.
- Line 585, validate command framing/registers/bit fields/scaling against
  datasheets: **Done** for every register-driven device, with the caveats
  in the table above recorded rather than glossed over.
- Line 586, deterministic timeout/retry-backoff/stale-quality/error
  classification, one failing peripheral must not block others:
  **Partial** -- every driver distinguishes `OK`/`TIMEOUT`/
  `HARDWARE_FAILURE`/`INVALID_STATE` consistently via
  `telemetry_driver_result_t`, and `board_power_service`'s power-cycle
  sequencing is an explicit bounded (non-retry-loop) recovery action; but
  no new driver this release implements its own automatic retry/backoff
  (retry cadence is a `sensor_manager`-level concern via sample period,
  inherited from before this release, not newly verified here).
- Line 587, `self_test` distinguishes passed/unavailable/failed: **Done**
  where the hardware has a real diagnostic signal to probe (`ADS8688`,
  `AD5422`, `MAX22190`: full three-way; `IPS2050`: two-way, no
  communication-failure mode exists for a plain GPIO read); **not
  applicable** where no such signal exists at all (`UIC`, `TPS3851`,
  matching `gpio_input`'s pre-existing no-self-test convention).
- Line 588, document exact resource claims for SPI/UART/I2C/GPIO/PIO/DMA/
  ADC: **Partial** -- every claim is documented in its own T-item's
  section of `docs/releases/v0.5.1.md` and enforced by
  `driver_catalog_get_resource_claims()`/`driver_catalog_claims_are_compatible()`
  with host-test coverage of every conflict/non-conflict pair; no single
  consolidated resource-claim reference document exists yet.
- Line 589, document how to add a driver: **Open**.
- Line 590, minimal standalone example driver: **Open**.
- Line 591, per-driver hardware-bring-up checklist: **Partial** -- every
  driver's specific unresolved hardware questions are documented inline
  (this report's table above, plus each header/register-notes file), but
  no formal per-driver checklist document (power/reset checks,
  communication identity/readback, nominal I/O, fault injection,
  boundary cases) exists as its own deliverable.

- Line 607, CI explicitly labels industrial drivers as compile/mock
  validated, not hardware qualified: **Open** -- no CI configuration was
  touched this release; this document is the artifact that exists today,
  but nothing automates the labeling in CI itself.

## Open items carried forward

- `UIC` quadrature-encoder mode (T6) -- deliberately deferred, see that
  section's scope decision.
- Extended `ADC0..ADC7` support is now **done to the extent currently
  possible** (T12: raw `ADC4..ADC6` rail monitoring inside
  `board_diagnostics_service.c`, reported as raw pin volts pending a
  documented divider ratio). `ADC0..ADC3` remains blocked by the current
  comparator-only `UIC` frontend (a schematic gap); `ADC7` remains
  intentionally unassigned.
- Driver-pack manifests, host-side descriptor format, "how to add a
  driver" documentation plus a minimal standalone example driver,
  per-driver hardware bring-up checklists -- all still open, not ordered
  by scope decision 3. `SupportedDrivers`/`DriverCapabilities` is now
  **done** (T13) -- removed from this list.
- A genuinely separate `RP2350_INDUSTRIAL_MVP_V1` CMake build
  target/profile does not exist; every driver was proven individually in
  the single reference target with its option flipped. Lines 552/596/601
  above depend on this existing.
- Static-allocation audit for compiled-but-inactive drivers (line 602)
  and a config-rejection re-test against this release's specific new
  drivers (line 603) were not performed.
- CI labeling of industrial drivers as compile/mock validated (line 607)
  has no automation; this document is the only current artifact.
