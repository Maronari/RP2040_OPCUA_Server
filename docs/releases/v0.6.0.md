## Owner-approved decisions — 2026-10-25

The owner confirmed the interview outcome and authorized plan/instruction
maintenance, including the compatibility transition recorded in ROADMAP.
These are requirements for implementation, not claims that features exist.

| Area | Approved decision |
|---|---|
| Initial deployment | One local USB/SWD installation of the new bootloader and signed initial known-good image is allowed. Layout changes must preserve configuration, identity, trust, history and journals; define backup/restore and verify preservation. |
| Threat boundary | Defend against substituted packages, incompatible images, interrupted installation and failed startup. Physical USB/SWD rewriting is outside the threat model; do not claim hardware secure boot. |
| Signing authority | Only the project owner/publisher authorizes signatures. Device admin credentials permit installation, never signing or bypassing verification. |
| CI signing | Sign in CI using a protected GitHub Environment, a private-key environment secret and mandatory manual approval. PR and ordinary build jobs have no key access. Sign only protected release tags pointing to main-branch commits whose required checks passed, using artifacts built from that exact source. Do not sign arbitrary uploaded binaries or branches. |
| Key lifecycle | Trusted public keys are fixed in the bootloader for this release. Lost/compromised key recovery requires USB/SWD reprovisioning. Remote key rotation is excluded. Private keys must never enter firmware, logs, config exports or published artifacts. |
| User initiation | Every upload/update is explicitly requested by the user. Upload plus verification does not reboot; activation requires a separate explicit command. No background updater or automatic retry after rollback. |
| Availability | Installation/reboot may interrupt acquisition and OPC UA. Measure and document a bounded downtime/recovery interval. |
| Candidate attempt | One candidate launch attempt. On failed confirmation, reset or hang, return to known-good firmware rather than launching the candidate again. Interrupted pre-launch installation may recover/resume without consuming extra candidate launches; freeze the persistent launch boundary in T0. |
| Confirmation | Require readiness followed by a short sustained health window; choose its duration and absolute recovery deadline from measured startup behavior. The proposed fixed 60 seconds and three attempts were explicitly rejected. |
| Health signals | Scheduler, configuration, storage, local network stack and OPC UA server must initialize and remain healthy. Missing Ethernet cable, DHCP availability or an external client alone must not cause rollback. T0 must define readiness signals consistent with these conditions. |
| Hang recovery | Use an independent watchdog for the unconfirmed OTA boot window so a hung candidate cannot prevent rollback. General task/deadline supervision remains v0.6.2 scope. |
| Version policy | Reject forbidden downgrades; allow recovery to the specifically retained known-good image while the candidate is unconfirmed. Advance the minimum accepted version after confirmation using a power-loss-safe transaction. Same-version installation is allowed only for identical signed content; changed content requires a higher version. |
| Development override | Downgrade override is compile-time, explicit test-profile-only, disabled in production and unavailable as an ordinary OPC UA admin toggle. It bypasses only the version floor, never signature or hardware compatibility. |
| Configuration rollback | Preserve settings readable by the previous image. An unconfirmed candidate must not irreversibly migrate persistent configuration. Define configuration selection/restore with the image rollback transaction. |
| Pending mutations | Until confirmation, reject persistent user mutations such as config writes, identity/trust replacement and another OTA with a deterministic temporary-unavailable result. Reads and diagnostics remain accessible. T0 must inventory mutation paths and classify necessary internal boot/storage writes without weakening rollback. |
| Failed package | Rollback never triggers another update automatically. A retry requires a new explicit user request, even for the same package. Retain the failure reason. |
| Unusable fallback | If both candidate and fallback fail validation, remain in bootloader recovery and require USB/SWD; never execute an unverified image. |
| Hardware evidence | Completion requires actual reference-board power interruptions during installation, state writes, confirmation and rollback, plus proof of known-good recovery. Host/mock tests supplement these tests. |

### Approved legacy-client migration

Retain existing OTA NodeIds, BrowseNames and method signatures. The approved
behavior change is that a CRC-only client cannot activate an unsigned package.
CRC remains useful for transfer errors, but does not authorize bootability.
Document the exact service result, OPC UA mapping and status reason in T0;
do not invent or reserve new public identifiers in this preparation.

Migration order: back up persistent data; locally install the new bootloader
and signed initial image without losing that data; use the updated signed-
package client to upload and verify; inspect status; request activation
explicitly. Provide a supported recovery procedure for interruption of initial
provisioning and for key loss. Existing non-OTA public/configuration contracts
remain unchanged. Finalize must not silently activate/reboot: freeze its
verification semantics and the separate activation adapter in T0.

Required migration tests cover old-client unsigned rejection without changing
the bootable image, valid signed upload without reboot, activation authorization
and illegal states, explicit retry, same-version changed-content rejection,
test-only downgrade behavior, and persistent-data preservation across initial
provisioning and rollback.

### Facts and remaining engineering decisions

Read-only mapping found two current image banks of 8,011,776 bytes each on the
16 MiB reference layout, with 753,664 bytes reserved outside the image banks.
The measured current BIN is 3,586,824 bytes. Raw capacity alone does not prove
recoverability: current code copies B over A, and only a Bank-A-linked OTA
application target exists. Choose and prove the recovery algorithm and link
strategy in T0; no bank scheme is selected by this interview.

`config_service_init()` currently can save a migrated payload before OTA
acknowledgement. Previous-image recovery must therefore explicitly prevent or
reverse incompatible configuration promotion; retaining a binary alone is
insufficient. Review other persistent initialization paths under the same rule.

T0 still owns exact signed serialization, public APIs/status mappings, region
layout and atomic state format, readiness sources, watchdog handoff, numerical
resource/timing limits and initial-data migration procedure. T5 must verify
actual GitHub environment/ruleset protections and refusal of unauthorized
signing jobs; workflow text alone is not evidence of platform protection.

## Existing implementation and risks

Read-only code-mapper survey established these boundaries:

| Boundary | Existing behavior and required change |
|---|---|

| `ota/src/ota_flash.c`, `ota/include/ota/ota_state.h`, `ota/src/ota_state.c` | CRC-checked staging in Bank B; one erase/program state record. Add authenticated verification and recoverable metadata transactions. |

| `static/tools/test_ota_state.py`, `test_bootloader_handoff.py`, `test_stage_ota_resume.py` | Reuse existing tests; current firmware CI disables bootloader, so add actual bootloader/artifact coverage during implementation. |

## Public contracts and resource limits

Preserve existing BeginFirmwareUpdate, WriteFirmwareChunk, FinalizeFirmwareUpdate,
AbortFirmwareUpdate and GetFirmwareUpdateStatus identifiers and signatures.
Apply only the approved unsigned-activation behavior transition described above
and in ROADMAP. An additive signed-manifest transport and explicit activation
adapter may be needed: reserve no NodeIds until T0 documents their contracts,
authorization and migration/error behavior. Preserve persisted configuration and
driver IDs. CRC remains a transport/error check, never authentication.

T0 must specify finite manifest/image/chunk/string sizes, staging-session count,
verification scratch/stack use, attempts, confirmation duration, timeouts and
event/output limits. Reject oversize, overflow, truncated/unknown fields and
partial initialization deterministically. Define Flash coordination, task
ownership and reset recovery explicitly. Separate internal SRAM, external PSRAM,
external Flash, static sections, runtime peaks and stack watermarks in reports.
Set numerical budgets from measured baseline and layout before implementation;
do not invent runtime measurements from linker sizes.

## Acceptance and evidence

- [ ] SHA-256/ECDSA P-256 authenticates manifest and image before bootability.
- [ ] Hardware profile, revision/range, firmware profile, driver pack/version,
  image version/size/hash and signature are covered by the signed contract.
- [ ] Modified/truncated image or manifest, wrong key/board/revision/profile and
  forbidden older versions are rejected; development override is explicit.
- [ ] Known-good image remains bootable after interrupted erase/copy/state writes.
- [ ] Unhealthy or unconfirmed candidate rolls back to that image on real hardware.
- [ ] Confirmation requires sustained scheduler/config/storage/network/OPC UA health.
- [ ] Upload/verification never activates automatically; activation and any retry
  require explicit user requests, and unconfirmed persistent mutations fail
  deterministically while reads/diagnostics remain accessible.
- [ ] A single failed/hung candidate attempt returns to known-good firmware;
  timing bounds are measured, and missing cable/DHCP/client alone cannot fail health.
- [ ] Configuration and other preserved user data remain usable after provisioning
  and rollback; both-invalid-image recovery never executes an unverified image.
- [ ] CI signing is manually approved, secret-isolated and restricted to protected
  release tags from checked main-branch commits; unauthorized signing is denied.
- [ ] Legacy CRC-client migration, same-version identity and test-only downgrade
  semantics pass positive/negative and illegal-state tests.
- [ ] OTA progress/result/attempt/rollback diagnostics and events pass client,
  authorization, contract/inventory and UaExpert checks.
- [ ] Host/mock suites, blocking cppcheck, reference Debug and bootloader/artifact
  builds pass with no new first-party warnings; industrial compile/mock retained.
- [ ] ELF/UF2/BIN sizes/hashes and measured memory/stack impact are recorded.
- [ ] Version, runtime query, exported config, manifest and release tag agree.
- [ ] ROADMAP general definition of done is satisfied; release commit and
  checklist status are reported without automatically rewriting historical checks.
