# v0.5.1 per-driver hardware bring-up checklists

Per-driver future hardware-bring-up checklists for `RP2350_INDUSTRIAL_MVP_V1`
(`ROADMAP.md:591`, v0.5.1 T17). `RP2350_INDUSTRIAL_MVP_V1` does not exist as
assembled hardware at the time this document was written -- every checklist
below is a **plan to execute once the custom PCB exists**, not a report of
work already done. See `docs/releases/v0.5.1-driver-verification.md` for
what has actually been verified so far (compile/mock validation only).

Each checklist follows the six categories `ROADMAP.md:591` asks for: power/
reset checks, communication identity/readback, nominal I/O operation, fault
injection, boundary/range cases, and the measurements that must be recorded.
Register/timing/scaling facts cited below are already established in this
project's datasheet notes (`docs/datasheets/*-register-notes.md`) and driver
source; this document does not re-derive them, only sequences them into a
bring-up procedure. Where a fact is explicitly unconfirmed against real
hardware (flagged in `docs/releases/v0.5.1-driver-verification.md`'s
consolidated unconfirmed-hardware-facts table), the checklist calls it out
as the first thing to verify, since a wrong assumption there would make
every later step in that checklist meaningless.

**How to use this document**: work through the checklists in the listed
order for a fresh board -- each driver's "power/reset" step assumes the
board's own supply rails and reset supervisor are already confirmed sane
(see the "Board power and diagnostics" checklist first). Record every
measurement in a bring-up log external to this repository (this document
defines *what* to measure, not a data-collection template); once a
checklist's items are all confirmed, promote the corresponding
"compile/mock validated" line in `docs/releases/v0.5.1-driver-verification.md`
to hardware-qualified with a dated note and the actual measured values.

## 0. Board power and diagnostics (do this first)

Covers `PWR_IN_FAULT_N`/`BOARD_FAULT_N`/`PWR_3V3_PGOOD_N`/`PWR_5V_PGOOD_N`
(`services/src/board_diagnostics_service.c`) and the `ADC4..ADC6` raw rail
monitors (v0.5.1 T12).

- **Power/reset checks**: apply board input power at the connector; confirm
  `PWR_3V3_PGOOD_N` (`GPIO34`) and `PWR_5V_PGOOD_N` (`GPIO35`) both read
  de-asserted (logic high, no fault) within the supervisor's specified
  power-good delay. Confirm `PWR_IN_FAULT_N` (`GPIO11`) stays de-asserted
  across the input voltage range the board is rated for. Cycle power at
  least 10 times and confirm the fault GPIOs settle to the same
  no-fault state every time (a marginal power sequencing issue would show
  up as an intermittent, not permanent, fault flag).
- **Communication identity/readback**: not applicable -- these are plain
  GPIO fault/PGOOD signals, no register interface.
- **Nominal I/O operation**: read all four fault-line GPIOs and the three
  raw ADC channels (`ADC4`/`GPIO44`=`VIN_PROTECTED_MON`,
  `ADC5`/`GPIO45`=`AO_15V_MON`, `ADC6`/`GPIO46`=`ANA_5V_MON`) via
  `native_adc_voltage_read_raw()` under normal board operation; confirm the
  raw ADC codes correspond to plausible voltages given the (currently
  undocumented) divider ratio -- this is the first opportunity to actually
  determine that ratio empirically, by comparing the raw reading against a
  bench multimeter measurement of the same net.
- **Fault injection**: momentarily short or remove the `+3.3V`/`+5V` rail
  (bench supply, current-limited) and confirm `PWR_3V3_PGOOD_N`/
  `PWR_5V_PGOOD_N` assert within spec; briefly force `BOARD_FAULT_N` low at
  its source (whatever upstream board-fault aggregator drives it) and
  confirm `board_diagnostics_service.c` reports it.
- **Boundary/range cases**: input voltage at the low and high edges of the
  board's rated input range -- confirm `PWR_IN_FAULT_N` does not chatter at
  the boundary, and does correctly assert outside it.
- **Measurements to record**: actual `VIN_PROTECTED_MON`/`AO_15V_MON`/
  `ANA_5V_MON` divider ratios (bench multimeter vs. raw ADC code, at at
  least two known-good rail voltages each, to derive both ratio and any
  offset); power-good assertion/de-assertion delay relative to rail
  ramp-up; input voltage thresholds at which `PWR_IN_FAULT_N` actually
  trips.

## 1. `ADS8688` industrial ADC (`AI0..AI3`)

- **Power/reset checks**: confirm the chip's supply sequencing relative to
  `VREF` per the datasheet's power-up requirements before issuing any SPI
  transaction; issue `RST` (`0x8500`) and confirm the program registers
  read back their documented POR defaults (`AUTO_SEQ_EN`=`0xFF`, Channel
  Power Down=`0x00`, Feature Select=`0x00`, all `Range_CHn`=`0x00`).
- **Communication identity/readback**: confirm the SPI timing mode
  (datasheet Figure 1 says mode 1, `CPOL=0`/`CPHA=1`) actually matches this
  board's wiring -- this was never electrically verified, only read from
  the datasheet. Run `native_ads8688_self_test()`'s Command Read-Back
  (`0x3F`) probe and confirm the echoed command word matches what was
  written, across several distinct command values.
- **Nominal I/O operation**: apply a known DC voltage to each wired input
  (`AI0..AI3`) in turn and confirm `MAN_Ch_n` conversions track it within
  the ADC's specified accuracy, for at least the two ranges this board
  actually uses (per `AD5422`'s frozen MVP output ranges, whatever `ADS8688`
  ranges the schematic pairs them with).
- **Fault injection**: deliberately end a SPI frame early (raise `CS`
  before the 16th/24th clock) and confirm the driver detects the resulting
  `FRAME_ABORT`/invalid-data condition rather than silently accepting
  garbage, then confirm a subsequent valid command recovers normal
  operation.
- **Boundary/range cases**: drive each wired input to the selected range's
  minimum and maximum voltage (and briefly beyond it, within the chip's
  absolute-maximum rating) and confirm the conversion clamps/saturates as
  the datasheet describes rather than wrapping or reporting a wildly wrong
  code.
- **Measurements to record**: actual SPI mode/timing margins at the
  board's real clock rate; measured full-scale error and offset error per
  channel against a calibrated reference source; confirmed range-select
  bit values that were actually exercised (cross-check against
  `driver_descriptors.json`'s `sourceFlags` table).

## 2. `AD5422` analog outputs (`AO0`/`AO1`, daisy-chained)

- **Power/reset checks**: write the Reset register (`0x0056`/data `0x0001`)
  to each device in turn (`NOP` for the other) and confirm both outputs
  read back tristated/zero-scale via the readback sequence before any
  `OUTEN` write.
- **Communication identity/readback**: this is the single most important
  thing to check first on this driver -- **confirm `AO1`'s `SDO` is truly
  not observable on `BOARD_SPI_MISO`** (per the schematic note that wiring
  it back "would create a push-pull contention risk"). If it turns out to
  be wired after all, the driver's self-test can be extended to cover
  `AO1` directly; if not, this is expected and not a driver defect. Then
  run the two-distinct-values write/readback probe
  (`native_ad5422_self_test()`) on `AO0` and confirm it correctly reports
  match/constant-wrong/varies-but-wrong classification.
- **Nominal I/O operation**: command each of `AO0`/`AO1` through its full
  scale in the two board-qualified ranges (0-10 V, 4-20 mA) and confirm
  the output tracks the commanded engineering-unit value within the
  datasheet's accuracy spec, at both channels simultaneously (to catch any
  daisy-chain cross-talk between the two 24-bit words in one 48-bit
  transaction).
- **Fault injection**: force an open-loop condition on the current-output
  range (disconnect the load) and confirm the status register's `IOUT
  fault` bit sets and the shared `BOARD_FAULT_N` line asserts; separately
  overheat the package (or simulate via datasheet-documented thermal test
  points, if available) to exercise the `Over temp` status bit.
- **Boundary/range cases**: command DAC codes `0x0000` and `0xFFFF` (full
  scale in each direction) in each of the four board-qualified ranges'
  scaling formulas and confirm the measured output matches the documented
  formula, not just mid-scale.
- **Measurements to record**: measured output accuracy/linearity at
  0%/50%/100% of scale per channel per range; confirmed daisy-chain byte
  ordering against the "word sent first reaches `AO1`" rule (swap a
  distinguishable value between the two channel positions and confirm
  which physical output changes); `IOUT fault` trip threshold if
  measurable.

## 3. `MAX22190` digital inputs (`DI0..DI3`)

- **Power/reset checks**: confirm `M0`/`M1` are actually strapped to
  `GND_SYS` as `HARDWARE_MVP.md` documents (this determines the mandatory
  Mode-0/24-bit/CRC framing the whole driver assumes) before any SPI
  traffic. Then confirm `/READY` (`DI_READY_N`, a direct `RP2350 GPIO24`
  input since the 2026-09-10 hardware revision, with its external
  `10k -> +3V3_DIG` pull-up) actually goes LOW before relying on any
  register access -- `HARDWARE_MVP.md`'s initialization sequence requires
  waiting on it, and no firmware currently reads it, so bring-up is where
  that signal is first exercised. Finally read `FAULT1` once after
  power-up and confirm the `POR` bit is set (register map was reset), then
  confirm it clears on the next read per the register's clear-on-read
  semantics.
- **Communication identity/readback**: **verify the CRC-5 implementation
  against real silicon first** -- this is explicitly flagged in
  `docs/datasheets/MAX22190-register-notes.md` as unverified against any
  worked example. A mismatched CRC implementation fails loudly (every
  transaction reports `FAULT1.CRC`), so this should be the very first
  transaction attempted: read `FAULT1` and confirm `CRC` is *not* set. If
  it is set on every transaction, the CRC-5 bit-ordering/polynomial
  assumption in `max22190_driver.c` is wrong and must be corrected against
  a logic-analyzer capture of a known-good frame before anything else in
  this checklist is meaningful.
- **Nominal I/O operation**: drive each wired input (`DI0..DI3`) high and
  low in turn (via a bench signal or the field-side test point) and
  confirm `native_max22190_read()` tracks it, including through the
  chip's glitch filter at its POR default (50 µs).
- **Fault injection**: exercise the per-channel glitch filter by driving
  an input pulse shorter than the configured `DELAY[2:0]` time and
  confirming it is correctly filtered out; separately, disconnect the SPI
  bus mid-transaction and confirm the driver classifies it as a
  communication failure rather than a stale/frozen `DI` value.
- **Boundary/range cases**: exercise every `DELAY[2:0]` filter setting
  (`000` through `111`, 50 µs to 20 ms) via a channel's `source_flags` and
  confirm the measured filter time matches the datasheet table for each.
- **Measurements to record**: confirmed CRC-5 correctness (pass/fail per
  the identity check above -- this is the release's single largest
  correctness risk and must be recorded explicitly either way); measured
  glitch-filter times per `DELAY[2:0]` setting against the datasheet's
  nominal values; input threshold voltage/hysteresis if measurable with
  available bench equipment.

## 4. `IPS2050` protected digital outputs (`DO0`/`DO1`)

- **Power/reset checks**: confirm the shared `DO_ENABLE_REQ` line is
  de-asserted at power-up (no channel drives its output before firmware
  explicitly starts it) and only asserts once `native_ips2050_start()` is
  called on the first channel.
- **Communication identity/readback**: not applicable -- plain GPIO
  frontend, no register interface. The closest equivalent is confirming
  the `DOx_FAULT` GPIO reads the expected idle (no-fault) level immediately
  after `start()`.
- **Nominal I/O operation**: command each of `DO0`/`DO1` high and low in
  turn (via `DOx_CMD`) and confirm the field-side output actually switches,
  and that `native_ips2050_read_fault()` reports no fault under a normal
  resistive load within the driver's rated current.
- **Fault injection**: short the field-side output to ground (within the
  chip's protection rating) and confirm `DOx_FAULT` asserts and
  `native_ips2050_read_fault()` reports it; remove the short and confirm
  the fault clears without requiring a firmware-side reset (per the
  chip's auto-retry/latch behavior -- confirm which one this part actually
  implements, since the driver currently assumes a simple polled read).
- **Boundary/range cases**: drive the output into an open-load condition
  (no load connected) and confirm the fault behavior matches the
  datasheet's open-load detection spec, if the part supports it; test both
  channels asserting `DO_ENABLE_REQ` simultaneously via the shared line to
  confirm no ordering-dependent race exists.
- **Measurements to record**: output on/off switching time; actual
  short-circuit trip current and thermal-shutdown/retry timing if
  triggerable safely on the bench; confirmed fault-clear behavior
  (auto-retry vs. latched).

## 5. `UIC` universal input channels (`UIC0..UIC3`)

Quadrature-encoder mode is explicitly deferred (v0.5.1 T6) and is **not**
part of this checklist -- only digital-input/pulse-count/frequency/period
modes are in scope for v0.5.1 hardware bring-up.

- **Power/reset checks**: confirm the `TLV3214PWR` comparator frontend's
  supply and reference are stable before enabling any UIC channel; confirm
  each channel reads a stable idle level with no input signal applied
  (comparator output should not oscillate/chatter with a floating or
  grounded input, depending on the frontend's designed idle state).
- **Communication identity/readback**: not applicable -- direct GPIO/PIO
  sampling, no register interface. The closest equivalent is confirming
  the correct PIO state machine actually claims the expected GPIO for each
  active channel (one state machine per active counter-mode channel).
- **Nominal I/O operation**: for `digitalInput` mode, drive each channel
  high/low and confirm the read tracks it; for `pulseCount`/`frequency`/
  `period` modes, apply a known-frequency square wave (bench function
  generator) to each channel and confirm the PIO-based counter reports the
  correct count/frequency/period within the expected accuracy.
- **Fault injection**: apply a signal well above the frontend's specified
  input range (within absolute-maximum ratings) and confirm the comparator
  clamps rather than passing through a corrupted edge count; disconnect
  the input mid-count and confirm the counter holds its last value rather
  than free-running.
- **Boundary/range cases**: exercise the counter-mode channels at both the
  lowest frequency the `frequency`/`period` calculation can resolve and
  the highest frequency the PIO program's timing budget supports, since
  the pulse counter uses on-demand snapshot reads (no DMA) -- confirm no
  counts are lost between snapshots at the top of that range.
- **Measurements to record**: comparator threshold/hysteresis voltage per
  channel against the frontend's datasheet spec; maximum count-mode
  frequency actually achievable without snapshot-read-induced count loss.
  (The former "confirm whether an analog-capable path to `ADC0..ADC3`
  exists" item is dropped: `HARDWARE_MVP.md`'s 2026-09-10 revision makes
  the UIC block input-only digital and removes `GPIO40..43`'s ADC
  capability from the hardware contract, so there is no analog path to
  find.)

## 6. ~~`TCAL9539` I/O expander, `TCA4307` I2C isolation, `TPS2553` sensor power~~ — removed 2026-09-10

**This section no longer applies.** `HARDWARE_MVP.md`'s 2026-09-10
revision removed the external I2C/SPI/UART sensor ports, the `TCAL9539`
service-I/O expander, both `TCA4307` isolation buffers and all four
`TPS2553` sensor-power switches from `RP2350_INDUSTRIAL_MVP_V1`. The
drivers were deleted from the tree with them, so there is nothing left to
bring up here and the checklist has been removed rather than left as a
trap for whoever runs bring-up on the assembled board.

Two consequences worth carrying forward for the parts that remain:

- `MAX22190`'s `/READY` is now a direct `RP2350 GPIO24` input, not
  `TCAL9539 P14` — see section 3's checklist, which owns that signal.
- The section-numbering below is unchanged so existing references to
  sections 7-9 stay valid.

## 7. `ISOW1432` RS-485 transport (`UART1`)

Raw half-duplex transport only -- Modbus protocol support is out of scope
for this release (`v0.7.0`).

- **Power/reset checks**: confirm the isolated side of `ISOW1432` powers up
  cleanly and `RS485_DE_RE` (`GPIO38`) defaults to the safe receive level
  (`DE=0`/`/RE=0`, driver disabled) before firmware initializes the UART,
  per the pull-down-to-`GND_SYS` default this driver's header documents.
- **Communication identity/readback**: loop back `RS485_TX`/`RS485_RX`
  (`GPIO36`/`GPIO37`) at the transceiver's differential side (A/B shorted
  to a second node on the same bus, or a bench RS-485 loopback fixture)
  and confirm bytes written are received correctly with `RS485_DE_RE`
  correctly sequenced (assert before transmit, de-assert after the last
  stop bit clears, before switching to receive).
- **Nominal I/O operation**: exchange raw byte streams with a second
  RS-485 node at the driver's configured baud rate and confirm no framing
  errors or dropped bytes across a sustained transfer.
- **Fault injection**: disconnect the bus mid-transmission and confirm the
  driver's read path times out rather than hanging; drive a bus contention
  condition (two transmitters asserting `DE` simultaneously, briefly, at
  safe current levels) and confirm the isolator survives and the bus
  recovers once contention clears.
- **Boundary/range cases**: test at the lowest and highest baud rates this
  driver is expected to support, and at maximum wire length/node count the
  installation is rated for, confirming no dropped bytes at the range's
  edges.
- **Measurements to record**: measured `RS485_DE_RE` turn-around timing
  relative to the last transmitted bit; bit-error rate at each tested baud
  rate; confirmed electrical isolation across `ISOW1432` under a
  realistic ground-potential-difference test if available.

## 8. `TPS3851` external supervisor/watchdog

- **Power/reset checks**: confirm `WD_ENABLE` (`GPIO3`) and `WD_KICK`
  (`GPIO2`) are wired as this driver expects and are **not** simultaneously
  claimed by the reference W5500 pin mapping on this specific board
  revision -- this was flagged as a real conflict against the reference
  module's pins and must be re-confirmed resolved on the actual industrial
  PCB (which uses `FIRMWARE_ENABLE_INDUSTRIAL_W5500_PINS`'s `GPIO4..GPIO8`
  mapping instead of `GPIO0..GPIO3`/`GPIO21`).
- **Communication identity/readback**: not applicable -- plain GPIO
  supervisor interface, no register access. The closest equivalent is
  confirming the supervisor's reset output actually resets the RP2350 when
  `WD_KICK` is withheld past the configured timeout (see Fault injection).
- **Nominal I/O operation**: kick the watchdog at the firmware's normal
  service interval and confirm no spurious reset occurs over an extended
  soak (hours, not minutes, to catch a marginal timing issue).
- **Fault injection**: deliberately stop kicking the watchdog (simulate a
  firmware hang) and confirm the supervisor asserts reset within its
  documented timeout window, and that the RP2350 actually restarts and
  resumes normal operation afterward (a full recovery test, not just the
  reset pulse).
- **Boundary/range cases**: kick the watchdog at intervals just inside and
  just outside the documented timeout window and confirm the pass/fail
  boundary matches the datasheet's specified timeout, accounting for the
  RP2350's own internal watchdog operating as a separate, independent
  layer (confirm the two do not interact or mask each other's behavior).
- **Measurements to record**: measured watchdog timeout period against the
  datasheet's nominal value; reset pulse width; confirmed pin assignment
  with no conflict against the industrial W5500 mapping actually used on
  this board.

## 9. W5500 industrial board binding

- **Power/reset checks**: confirm `PIN_RST`, if wired on the industrial
  board, correctly resets the W5500 on power-up (the reference module's
  binding leaves `PIN_RST` unwired/`-1`; confirm whether the industrial
  PCB wires it and update the binding if so).
- **Communication identity/readback**: with
  `FIRMWARE_ENABLE_INDUSTRIAL_W5500_PINS` compiled in (`GPIO4`=`MISO`,
  `GPIO5`=`CS`, `GPIO6`=`SCK`, `GPIO7`=`MOSI`, `GPIO8`=`INT`), confirm the
  chip's version register reads the expected W5500 identity value over
  SPI -- this is a pure pin-remapping change and should behave identically
  to the already-working reference-module binding once the pins are wired
  correctly.
- **Nominal I/O operation**: bring up the network stack exactly as on the
  reference board (DHCP or static IP, OPC UA client connect) and confirm
  no behavioral difference from the reference pin mapping.
- **Fault injection**: disconnect the Ethernet cable mid-session and
  confirm the existing link-loss/reconnect handling (already exercised on
  the reference board) behaves identically on the industrial pin mapping.
- **Boundary/range cases**: not applicable beyond what the reference
  module's existing verification already covers -- this binding is a pure
  GPIO remap, not new protocol logic.
- **Measurements to record**: confirmed successful compile+link+boot with
  `FIRMWARE_ENABLE_INDUSTRIAL_W5500_PINS=ON` on the actual industrial PCB
  (already verified via ARM cross-compile in both configurations at T10;
  this step is the real-hardware confirmation that was not previously
  possible); `PIN_INT` (`GPIO8`) interrupt latency if the industrial board
  changes trace length/loading versus the reference module.

## Not covered here

- `board diagnostics`'s DO-fault aggregation is covered under checklist 4
  (the underlying signals); its sensor-power-fault aggregation went away
  with the 2026-09-10 hardware removal in section 6.
  `board_diagnostics_service.c` itself has no independent hardware surface
  beyond reading those same GPIOs/ADC channels, already covered in
  checklist 0.
- `synthetic` (T16) has no external hardware dependency and needs no
  bring-up checklist.
- `internal_temp`, `adc_voltage` (`ADC0..ADC3`), `gpio_input`, `gpio_output`
  are the pre-v0.5.1 reference-board drivers already covered by this
  project's existing hardware-verification process
  (`docs/releases/v0.5.0-hardware-verification.md` and earlier); not
  re-listed here since v0.5.1 did not change their hardware contract.
