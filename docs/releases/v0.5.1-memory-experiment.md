This is a reference-board measurement, not industrial hardware qualification.
Industrial drivers remain **compile/mock validated, not hardware qualified**.

> mechanism. Verified: full host suite green, ARM reference build links
> clean, blocking cppcheck clean, and confirmed on the same reference
> board (`opc.tcp://192.168.1.103:4840`) across several intermediate
> diagnostic builds before the final clean image, SHA-256
> `04683e13144a5441588cc3655820be9f8f58430d364e62971f5ab7195bcd9ea1`.
> **MEM-01**: 4 concurrent anonymous connections all completed in

> samples per call, run by the device owner with their own credentials.

The proposed changes were FreeRTOS heap 360 -> 256 KiB and OpcUaTask stack
64 -> 48 KiB. Before changing either budget, the existing read-only load
runner was used against `opc.tcp://192.168.1.103:4840`, with authenticated
Basic256Sha256/SignAndEncrypt sessions, 500 ms publishing, 250 ms sampling,
and a requested 10 reads/s per client. Existing diagnostic NodeIds were
added to the runner's in-memory dictionary for stack watermarks/fault code;
no firmware instrumentation or public contract was changed.

### MEM-01: fourth authenticated connection times out — FIXED, confirmed on hardware 2026-09-09

Reproduced twice. Clients 1–3 connected, but client 4 failed with Windows
`OSError: [WinError 121]` before subscriptions were created. Expected:
four concurrent sessions within the configured four-session limit.

**Root cause**: open62541's lwIP `EventLoop` implementation
(`port/open62541/open62541.c`, `UA_EventLoopLWIP_pipe()`) creates its
internal self-pipe wakeup mechanism as a local loopback TCP connection pair
on this architecture backend ("Windows has no pipes. Use a local TCP
connection for the self-pipe trick" -- true for this embedded lwIP backend
too, not only Windows hosts). That pair (`el->selfpipe[0]`/`[1]`) is
created once when the event loop starts and held open for the server's
entire lifetime, permanently consuming 2 of lwIP's `MEMP_NUM_TCP_PCB` pool
(default 5, never overridden in `port/lwip/lwipopts.h` before this fix).
That left only 3 slots free for real OPC UA client connections, even
though `opcua_model/src/model_core_lifecycle.c` configures
`maxSecureChannels`/`maxSessions = 4` -- the 4th client's TCP `SYN` was
accepted by the listen socket (a separate `MEMP_TCP_PCB_LISTEN` pool,
unaffected) but had no PCB left to become `ESTABLISHED`, so the connection
hung until the client's own timeout fired.

**Fix**: `port/lwip/lwipopts.h` now sets `MEMP_NUM_TCP_PCB` to 8
(2 self-pipe + 4 configured client channels + 2 spare so a departing
client lingering in `TIME_WAIT`/`CLOSE_WAIT` cannot block a new one), with
a comment tying it to `maxSecureChannels` and a cross-reference comment
added at the `maxSecureChannels` definition itself
(`opcua_model/src/model_core_lifecycle.c`) so the two budgets cannot drift
apart silently again. Measured cost: +468 bytes `.bss` (3 additional
`tcp_pcb` structures), negligible against this project's memory budgets.

**Confirmed on hardware (2026-09-09, no credentials needed)**: 4 concurrent
anonymous `asyncua.Client.connect()` calls (`asyncio.gather`, 12 s
per-client timeout) against the reflashed board all completed in
1.16-1.95 s each, every one correctly rejected by this server's security
policy with `BadUserAccessDenied` -- none hung. Note that
`static/tools/load_test_opcua.py`'s ramp logic aborts a whole stage on its
*first* per-client failure, so it does not by itself exercise 4 truly
concurrent attempts in anonymous mode; the standalone `asyncio.gather`
check above was used instead specifically to avoid that early-abort
behavior. Before this fix, the 4th of 4 concurrent connections (of any
kind, authenticated or anonymous, since the failure is at the transport
layer before any credential is even evaluated) would hang until the
client's own timeout; now all 4 reach the OPC UA layer promptly.

An authenticated re-run (credentials supplied through `OPCUA_USERNAME`
and `OPCUA_PASSWORD`, never stored in this report) is still worth doing to
confirm 4 *successful* concurrent sessions specifically, though nothing
about session/subscription handling changed in this fix:

```sh
python static/tools/load_test_opcua.py opc.tcp://192.168.1.103:4840 --clients 4 --items 32 --duration 15 --timeout 30 --read-rate 10 --output build/review-v051/memory-load-four-retry.json
```

### MEM-02: temperature HistoryRead unavailable — FIXED, confirmed on hardware 2026-09-09

Three consecutive authenticated `read_raw_history` calls against
`ns=1;s=Device.Channels.Temperature1.Value`, from UTC now minus one day to
UTC now plus one second, requesting 128 values, returned
`BadResourceUnavailable`. ExportConfig succeeded in the same session.

**Actual root cause, found via live serial diagnostics (temporary, since
removed): a boot-ordering race left the channel's Flash slot permanently
unbound.** `history_service_init()` claims a PSRAM ring for every
channel `channel_manager` already reports as historizable
(`history_service_bind_configured_channels_locked()`), then does a
one-time pass binding each ring's *Flash* slot
(`history_flash_backend_bind_channel()`) and restoring any persisted
data. On this board, `internal_temp`'s very first reading was not yet
`SERVICE_QUALITY_GOOD` by the time `sensor_manager_init()`'s activation
verify-gate ran (a real, if brief, sensor warm-up/first-read latency) --
so at the exact moment `history_service_init()`'s one-time Flash-bind
pass ran, `channel_manager` did not yet report the channel as eligible,
and its Flash slot was bound to "no channel" by that pass's own fallback
branch (`services/src/history_service.c`, the loop inside the
`PICO_ON_DEVICE` block of `history_service_init()`). Moments later, once
the channel *did* produce a good reading, `sensor_manager`'s periodic
re-check (`sensor_manager_task()`) activated it correctly, and
`history_service_record_channel_sample()`'s existing lazy-claim path
correctly created a PSRAM ring for it on first write -- but nothing
re-bound the corresponding *Flash* slot, which stayed permanently "no
channel" for the rest of that boot. Every later
`history_flash_backend_append()` call for this channel therefore failed
`HISTORY_FLASH_BACKEND_NOT_BOUND`, confirmed directly via temporary
`printf` diagnostics read over the reference board's USB-CDC serial
(`COM6`) port -- not a hypothesis, an observed `restore_status=7`
(`FLASH_APPEND_FAILED`) on every single append attempt, with zero
underlying Flash I/O errors, across a live capture spanning dozens of
one-second poll cycles.

Two more bugs surfaced during this investigation, both real and both
fixed, but neither was the operative cause on this specific device
(confirmed by the same live diagnostics: appends were failing
`NOT_BOUND`, before ever reaching either of these code paths):
- `history_service_record_channel_sample()` permanently marked a ring
  `FLASH_APPEND_FAILED` on any single Flash append failure and never
  cleared it on a later success -- a one-way ratchet from one transient
  hiccup (e.g. `flash_operation_coordinator` momentarily busy with
  another channel) to permanent failure for the rest of the device's
  uptime. Fixed: clear back to `READY` on the next successful append for
  that same ring. Every other, more serious restore-status failure
  (boot-time restore/bind/scratch-allocation, which describe whether
  *persisted* history from before this boot loaded correctly, a
  different fact) is left untouched, preserving the documented
  fail-closed HistoryRead contract
  (`services/include/services/history_service.h`) for those.
- `drivers/src/history_flash_backend.c`'s `flush_staging_if_full()`
  permanently refused all future writes for a channel after a single
  failed sector-swap erase, despite its own doc comment claiming "a later
  append retries the erase" -- no such retry existed in the code. Fixed:
  the erase is now actually retried on the next call, matching the
  documented (but previously unimplemented) behavior.

**Fix for the actual root cause**: `history_service_record_channel_sample()`
now binds and restores a channel's Flash slot itself, under the same
lock, at the exact moment its lazy-claim path creates a PSRAM ring for a
channel the boot-time pass missed -- mirroring exactly what the boot pass
does, just deferred to whenever the channel actually becomes eligible.
This is safe unconditionally: reaching that code path means no ring
existed for the channel a moment earlier, which guarantees the boot
pass's fallback already bound that exact Flash slot to "no channel" and
never wrote to it -- there is no prior data or armed write cursor to
clobber.

**Confirmed fixed on hardware, with real credentials, by the device
owner**: `verify_history_read.py` (`static/tools/`, a new manual/
live-hardware-only tool matching `verify_listener_recovery.py`'s existing
precedent -- not in `run_host_tests.py`, credentials via
`OPCUA_USERNAME`/`OPCUA_PASSWORD` environment variables only, never
handled by Claude) against the final image returned
`history-read: PASS (3/3 calls returned GOOD)`, 91 samples per call.

Both findings block adoption of the proposed lower heap/stack budgets.
They were observed with the original 360 KiB heap and 64 KiB OPC stack.

## Baseline outcome

| Load | Result |
|---|---|
| 1 client, 32 monitored items, 30 s | PASS: 288 reads, 328 notifications, no read/connection errors |
| 2 clients, 64 total monitored items, 30 s | PASS: 575 reads, 666 notifications, no read/connection errors |
| 2 clients, 128 total monitored items, 30 s | PASS: 587 reads, 1,328 notifications, no read/connection errors; p95 read latency 53.826 ms |
| 4 clients, requested 128 total monitored items | FAIL: fourth connection timed out with WinError 121 before subscriptions were created |
| Isolated repeat of four-client setup | Same failure on fourth connection |
| ExportConfig, three consecutive calls | PASS: each returned a parseable document, 9,021 bytes when serialized by the client |
| HistoryRead, requested 128 temperature samples, three calls | FAIL: BadResourceUnavailable |

The first two stages did not reboot. A successful authenticated read after
the failed ramp confirmed continuous uptime, firmware 0.5.1, and fault code
0. The baseline script's reboot flag for the failed four-client stage is
not itself evidence: no before/after diagnostics were obtained for that
stage.

Minimum-ever FreeRTOS free heap after the ramp was 261,368 bytes (255.24 KiB),
so peak observed allocator consumption was 107,272 bytes (104.76 KiB).
With two sessions and 64 items, free heap was 271,320 bytes, PSRAM used
4,694,376 bytes, PSRAM free 3,694,232 bytes, and the largest free block
3,680,072 bytes. After cleanup, an authenticated session measured free heap
275,544 bytes and PSRAM used about 4,559,752 bytes.

Observed stack minima remained 7,868 / 874 / 221 ARM words for
OpcUaTask / NetworkTask / SensorTask, respectively: 31,472 / 3,496 / 884
bytes remaining. These minima include earlier activity since boot, not
only this load test.

The final 128-item run also left the stack minima and minimum-ever free
heap unchanged. It measured PSRAM used 4,730,328 bytes, free 3,658,280 bytes
(3.49 MiB), largest free block 3,644,312 bytes; free FreeRTOS heap was
271,320 bytes (264.96 KiB), fault code 0, and uptime increased normally.
The load runner printed BadNoSubscription replies during subscription
teardown, after the load interval; these were not read/connection failures
during the measured load.

## Decision

**2026-09-09 update**: MEM-01 and MEM-02, the two specific failures this
decision was blocked on, are now fixed and confirmed on hardware (see
each section above). This does *not* by itself approve the proposed
256 KiB heap / 48 KiB OPC stack reduction below -- that reduction was
never re-attempted or re-measured against the fixed firmware; doing so
is a separate follow-up, starting from a fresh baseline load test now
that both blockers are cleared. The original decision and its reasoning
below are preserved as the historical record of the baseline experiment.

Do not reduce or deploy memory budgets on this evidence yet. The intended
four-session baseline and successful HistoryRead workload have not passed.
The fourth connection failure is not diagnosed as heap exhaustion: free
heap remains substantial and no fault/reboot was observed. The source
configures four sessions/four secure channels, while lwIP uses five TCP
PCBs by default; these limits alone do not prove the cause.

HistoryRead's BadResourceUnavailable can originate from unavailable model
scratch, incomplete history restoration, or a busy history mutex
(`opcua_model/src/model_history.c`). A successful request is needed to
exercise the complete response path before approving a smaller OPC stack.

OTA staging and configuration apply were not attempted after the baseline
failed. Persistent configuration, firmware and memory budget constants were
left unchanged. No claim of reduced-budget boot, stress qualification,
PSRAM-fallback coverage or absence of leaks is made.

The simple projection for a 256 KiB heap, with identical allocations and
the original stack sizes, leaves 154,872 bytes (151.24 KiB) at the observed
peak. This supports further investigation, not deployment approval:
`ua_port_alloc_raw` can fall back from PSRAM into FreeRTOS heap. Reducing
the OPC stack would additionally return 16 KiB to that heap, but requires
complete workload stack measurements first.

Evidence under `build/review-v051/`: `memory-load-baseline.json`,
`memory-load-four-retry.json`, `memory-operations-baseline.json` and the
additional `memory-load-128.json`, plus the read-only
`memory_operations.py` harness. Credentials are supplied through
the process environment and are not stored in these artifacts.
