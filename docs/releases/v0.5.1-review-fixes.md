# v0.5.1 review corrections and reference-board deployment

Qualification: **compile/mock validated, not hardware qualified** for industrial drivers.

## File-level implementation plan

- `drivers/src/{ads8688,ad5422,max22190}_driver.c`, their headers, datasheet notes and host tests: correct ADS8688 framing/offset-binary conversion and prevent unsafe or falsely successful diagnostic operations.
- `services/src/driver_catalog.c`, its public header and catalog tests: add actual UIC/IPS2050 GPIO claims. Keep persisted driver IDs and configuration fields unchanged. Increase the bounded claim capacity from two to four for the IPS2050 logical channel, command, fault and shared enable pins; all callers size arrays from this constant. Account for the increased temporary stack requirement.
- `drivers/include/drivers/industrial_board_pins.h` and UIC/IPS2050 source: use one pin-definition unit for physical operations and claims.
- `drivers/src/synthetic_driver.c`, `native_channel_driver.h`, synthetic tests and example documentation: move the counter into service-owned per-channel context, retaining same-index independent channels. No persistent-wire/schema change; native source context grows from 2 to 8 bytes, removes the driver's permanent 32-byte counter array. Runtime context lives in the existing bounded, lazily allocated sensor-manager banks.
- `static/tools/verify_opcua_public_contract.py`, a regression suite and `.github/workflows/build.yml`: verify the documented v0.5.1 delta against the immutable v0.5.0 commit, with no allowance for removed NodeIds, BrowseNames or method contracts.
- `cmake/firmware_version.cmake`: identify the candidate firmware as 0.5.1. No tag or release publication.
- SPI transport and board-diagnostic hardware ownership will be corrected after focused protocol fixes, with focused tests before integration.

No change to `ROADMAP.md` or the governing `v0.5.1.md` release plan. The previously authorized deferral of undefined driver packs remains intact. Unsupported industrial hardware modes and missing industrial-profile integration must remain explicitly reported rather than declared complete by reference-board flashing.

## Verification and deployment plan

Run all host suites without exclusions, blocking cppcheck, reference Debug build, base-pack exclusion build, contract/version/artifact gates and independent code review. Flash the checked direct reference UF2 only after these checks, verify BOOTSEL Board-ID and image address ranges, retain persistent configuration sectors, then verify device boot and OPC UA identity/network behavior where reachable. Do not claim industrial electrical qualification or UaExpert interaction without performing it.

## Implemented corrections

- ADS8688 uses 32-clock transfers and unsigned offset-binary bipolar conversion. ADS8688/MAX22190 self-tests check restoration transfers/readback instead of silently succeeding after restoration failure.
- AD5422 self-test reads CONTROL/STATUS without changing the live output. Startup loads the initial DAC code before enabling the output; a failed enable attempts to disable it again.
- SPI transactions acquire the RP2350 backend's shared per-peripheral mutex before asserting CS, with a bounded 20 ms wait. Tests exercise the real backend with mocked FreeRTOS/hardware, including allocation failure, competing devices and release on transfer failure.
- UIC and IPS2050 claims include their physical GPIOs, preventing conflicting generic GPIO activation. Shared enable pins remain explicitly shared. Synthetic same-index instances now have independent counters.
- Board fault input GPIO operations moved from the service into `drivers/src/board_fault_inputs.c`; the service consumes a bounded value snapshot.
- Contract validation uses the exact v0.5.0 baseline `c6da6c44326e6b1fe67b06656ac8a3518c12ea9e` and validates the precise permitted inventory delta. CI uses the same baseline. The firmware version source now reports 0.5.1.

diagnostics (since removed) showing `HISTORY_FLASH_BACKEND_NOT_BOUND` on

`verify_history_read.py` (run by the device owner with their own

**Regression found: OPC UA timestamps ignored SNTP since v0.5.0.** With `Device.Time.TimeSynced=true`, the `546377b` export showed `DeviceHealthAlarms.Failure.ReceiveTime = 1970-01-01T00:00:16`, and a Root export aborted because the server's SecureChannel token `CreatedAt` was 1970 + uptime (asyncua rejects a previous token whose server-reported lifetime has "expired" by its own clock). Cause: `36e03c9` (vendored open62541 v1.5.3 -> v1.5.7, part of the `v0.5.0` tag) replaced the patched FreeRTOS `UA_DateTime_now()`, which delegated to `rp2_ua_datetime_now()`/`time_service`, with the stock tick-based version. Every timestamp taken from it -- event and condition times, maintenance command times, ServerStatus, token `CreatedAt` -- has been 1970 + uptime since then; channel values and history read `time_service` directly and were unaffected. Fixed in `ddc63c5` by re-applying the hook, with a structural check in `test_rp2_ua_datetime_clock.py` that fails if an amalgamation upgrade drops it again. Confirmed on the device: an anonymous SecurityPolicy-None `OpenSecureChannel` returned token `CreatedAt 2026-09-13T12:51:52.372Z` (-1.5 s against the client clock; `token-clock-probe.json`), the `Device` export shows condition `ReceiveTime` values of `2026-09-13T12:51:3x`, and the Root export above completed across a token renewal. DateTime fields that were never set still read `1601-01-01`, the OPC UA null value.

**v0.5.1 is not yet fully release-ready.** The correction tests, static checks, reference builds, exact baseline source-contract check and reference-board deployment above are complete. The broader checklist remains incomplete:

- ~~A separate industrial firmware profile with complete production board bindings/startup integration is still missing.~~ **Addressed 2026-09-12.** The gap was real and concrete: until then no application code called any `native_*_bind_bus()` or `native_uic_bind_counter()` -- only host tests did -- so on an assembled board every `ADS8688`/`AD5422`/`MAX22190` channel and every UIC counter mode would have refused to start. `app/basic_profile/industrial_board_bindings.c` now binds the shared `spi1` bus (one chip-select state per device: `ADC_CS_N`, `AO_LATCH`, `DI_CS_N`) and the PIO edge counter before `sensor_manager_init()` activates the running configuration, and `industrial_seed_config.c` seeds all 16 industrial channels. The CMake default pack also moved `industrial` -> `base`, so the reference board neither carries nor initializes industrial drivers. Verified by building both packs: the `base` ELF contains zero industrial symbols, the `industrial` one links the bindings and the seed, and the pack costs ~12.6 KB flash / 168 B SRAM. Still **not** hardware-verified -- no assembled board exists, and the 8 MHz bus clock is datasheet-derived rather than measured.
- UIC quadrature operation remains unimplemented; unsupported hardware modes must not be advertised as completed.
- ~~Other compiled-but-inactive driver state arrays remain~~ -- **resolved 2026-09-09/10.** `UIC`'s per-channel array was relocated into the service-owned PSRAM context, like `synthetic`'s; the remaining driver-wide singletons (the SPI drivers' bus bindings, `adc_voltage`'s ready latch, `UIC`'s counter binding) were explicitly deferred by user decision rather than left as an oversight; `TCAL9539`/`board_power_service` were deleted with their hardware. The criterion is met for per-channel state and consciously waived for those singletons -- see `v0.5.1-static-allocation-audit.md`.
- ~~Full live capability/NodeSet comparison~~ **done 2026-09-13** (see the live-verification entry above). UaExpert inspection remains incomplete. Authenticated channel checks are done as of 2026-09-10 and repeated 2026-09-13. Runtime memory/stack snapshots are recorded below; workload/peak qualification remains unperformed.
- `environmental`/`motion`/`development` driver packs remain undefined -- **explicitly deferred by user decision (2026-09-06)**, since no project document defines their composition. The decision is recorded in `v0.5.1.md`; the roadmap line itself is unamended.
