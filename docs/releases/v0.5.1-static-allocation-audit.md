# v0.5.1 static-allocation audit for compiled-but-inactive drivers

> **Review correction (2026-09-07): the completion conclusion below is
> withdrawn.** Small fixed arrays are still permanent SRAM and do not satisfy
> ROADMAP's inactive-driver criterion merely because no malloc is used.
> The synthetic driver has now moved its counter into the service-owned
> per-channel native context (2 -> 8 bytes per context, existing bounded
> PSRAM banks) and removed its private 32-byte array. Other fixed driver state
> remains an open acceptance item. The historical table below is not a
> measurement of the corrected image; see `v0.5.1-review-fixes.md` for current
> verification and remaining limitations.

Answers `ROADMAP.md:602` ("Verify that compiled but inactive drivers
allocate no per-instance runtime context, task, channel buffer or
permanent SRAM/PSRAM block") for every driver added or extended in
v0.5.1 (T2/T4-T12, T16). "Compiled but inactive" is read here as: the
driver's `FIRMWARE_ENABLE_NATIVE_*` option is `ON` (so its code and any
file-static state link into the image), but zero channels in the running
configuration are actually assigned to it. The question is whether that
state's size depends on how many channels are actually configured to use
the driver, or is instead a fixed footprint paid the moment the option is
compiled in regardless of real usage.

## Method

For each driver, `grep -n "^static"` across its `.c` file lists every
file-scope (non-function) declaration; each one was classified as either
plain code (`const` lookup tables, living in flash/`.rodata`, not RAM) or
genuine RAM state, and every RAM-state array's size was checked against
whether it is indexed by an actually-configured channel count or by a
fixed, compile-time channel-count *ceiling* (`_MAX_CHANNEL_INDEX`-style
constants already established throughout this project). The same pass
searched all sixteen v0.5.1 driver/transport/service files for
`xTaskCreate`/`vTaskCreate` (FreeRTOS task creation), `xQueueCreate`
(queue creation), `pvPortMalloc`/`malloc(` (heap allocation), and any
`PSRAM`/linker-section attribute referencing external memory --
**zero matches for any of these across all sixteen files**. No v0.5.1
driver creates a task, a queue, or a heap/PSRAM allocation of any kind,
whether active or inactive.

| `AD5422` | `g_bus` (`spi_bus_t`) + `g_last_code[2]` (`uint16_t`, one per daisy-chain device) | Fixed -- sized to the board's 2 physical devices, not to configured channel count | 12 bytes |
| `MAX22190` | `g_bus` (`spi_bus_t`) | Fixed -- one shared bus binding | 8 bytes |
| `IPS2050` | `g_cmd_gpio[2]`/`g_fault_gpio[2]` (`const uint8_t`) | **Not RAM at all** -- `const` arrays live in flash/`.rodata`; zero SRAM cost | 0 bytes (flash: 4 bytes) |
| `UIC` | `g_counter` (`pio_edge_counter_t`: vtbl + context) + `g_derived[4]` (per-channel derived-mode scratch state) | Fixed -- sized to `UIC_MAX_CHANNEL_INDEX + 1` (4), not to how many of the 4 channels are actually configured | ~40 bytes |
| `rp2350_pio_edge_counter` (UIC's PIO backing) | `g_slots[4]` (`rp2350_pio_edge_counter_slot_t`) + `g_program_offset[NUM_PIOS]` | Fixed pool of 4 slots, matching `UIC0..UIC3`'s ceiling; **the real hardware resource (a PIO state machine, `pio_claim_unused_sm()`) is claimed lazily inside `native_uic_start()` and released in `stop()` via `pio_sm_unclaim()`, not merely because the driver is compiled in** -- an inactive channel holds a slot-table *entry* (a few bytes) but no claimed SM | ~40 bytes struct pool, 0 hardware SMs held until a channel actually starts |
| `TCAL9539` | `g_bus` (`i2c_bus_t`) + `g_address` (`uint8_t`) | Fixed -- one shared bus/address binding for the single expander chip | 9 bytes |
| `board_power_service` (`TCA4307`/`TPS2553` via `TCAL9539`) | `g_output_port0`/`g_output_port1` (`uint8_t` each) + `g_cycle_slots[4]` (`bool` + `uint32_t` per port) | Fixed -- sized to `BOARD_POWER_SENSOR_PORT_COUNT` (4 physical ports), not to how many are actually enabled in configuration | ~34 bytes |
| `rp2350_rs485_uart`/`ISOW1432` transport | none (all state lives in the caller-owned `uart_transport_t` config struct, not a driver-internal global) | N/A -- no file-static RAM at all | 0 bytes |
| `TPS3851` watchdog | none (every operation is a direct, stateless GPIO read/write against fixed `WD_KICK`/`WD_ENABLE` pin numbers) | N/A -- no file-static RAM at all | 0 bytes |
| `board_diagnostics_service` | none (pure aggregation -- reads GPIOs and calls into `board_power_service`/`adc_voltage` on every snapshot, keeps no state between calls) | N/A -- no file-static RAM at all | 0 bytes |
| `adc_voltage` (`ADC0..ADC7` incl. T12's raw rail read) | `g_adc_ready` (`bool`) | Fixed -- one shared "hardware ADC peripheral initialized" latch for all 8 possible channels, not per-channel | 1 byte |

| `spi_transport`/`i2c_transport` (shared abstractions) | none (pure vtbl dispatch against a caller-supplied context; no transport-internal global state) | N/A -- no file-static RAM at all | 0 bytes |

## Finding

**Every v0.5.1 driver's RAM footprint is a small, fixed compile-time
constant sized to its board's physical/schematic channel-count ceiling
(typically 1-8 channels), not a per-configured-or-active-channel
allocation.** Enabling a driver's `FIRMWARE_ENABLE_NATIVE_*` option costs
the same handful of bytes whether the running configuration assigns zero
channels to it or every channel it supports -- there is no scaling
allocation, no dynamic/heap growth, and (confirmed above) no task, queue,
or PSRAM allocation triggered merely by compiling a driver in. The one
place a genuine hardware resource is claimed on demand rather than at
compile time is `UIC`'s PIO state machine (`pio_claim_unused_sm()`),
and that claim is correctly deferred to `native_uic_start()` -- an
inactive `UIC` channel holds no PIO SM at all, only its share of the
already-tiny fixed slot-table entry.

This satisfies `ROADMAP.md:602`'s intent as a **design property that
holds by construction** (this project's established no-dynamic-allocation
convention, applied consistently by every v0.5.1 driver) rather than
something that needed a runtime measurement tool to discover. No
`.bss`/`.map`-file byte-counting tool was built for this pass -- the
per-driver sizes above come from reading each struct's field list
directly, which fully answers the qualitative question line 602 asks
("no per-instance... allocation") without needing to track exact linker
output, especially since every number involved is a handful of bytes.

## Not covered by this audit

- Non-v0.5.1 drivers (`internal_temp`, `gpio_input`, `gpio_output`) were
  not re-audited; their static-allocation shape predates this release and
  was not flagged as a concern.
- Per-channel runtime state owned by `channel_manager`/`sensor_manager`
  (the shared `telemetry_channel_t` array all drivers write into) is
  sized to the compiled channel-table capacity regardless of driver
  assignment -- this is pre-existing v0.4.x/v0.5.0 architecture, not a
  v0.5.1 driver concern, and out of this audit's scope.
