# v0.5.1 static-allocation audit for compiled-but-inactive drivers

> **Review correction (2026-09-07): the completion conclusion below is
> withdrawn.** Small fixed arrays are still permanent SRAM and do not satisfy
> ROADMAP's inactive-driver criterion merely because no malloc is used.
> The synthetic driver has now moved its counter into the service-owned
> per-channel native context (2 -> 8 bytes per context, existing bounded
> PSRAM banks) and removed its private 32-byte array. Other fixed driver state
> remains an open acceptance item. The historical table below is not a
> measurement of the corrected image; see `v0.5.1-review-fixes.md` for current
> verification and remaining limitations.
>
> **2026-09-09 update: `UIC`'s `g_derived[4]` fixed the same way; the
> remaining items are a genuinely different category, not a to-do list of
> more of the same fix.** See "Per-channel scratch vs. driver-wide
> singletons" below -- the fix pattern that worked for `synthetic`/`AD5422`/
> `UIC` (move per-channel scratch into the service-owned
> `native_channel_source_t`) does not apply to a true shared-bus/chip
> singleton (`ADS8688`/`MAX22190`'s `g_bus`, `adc_voltage`'s
> `g_adc_ready`, `UIC`'s own `g_counter`) --
> there is exactly one such resource regardless of channel count, so there
> is nothing to distribute across per-channel slots without giving every
> channel of that driver its own incorrect independent copy of a binding
> that must in fact be shared. Eliminating a singleton's footprint would
> require converting it to a lazily `psram_malloc()`-allocated pointer
> (a real, available pattern -- `history_service.c`'s `g_store`/
> `g_flash_backend` already use it) at the cost of a null-check in every
> function that touches it, for a saving of 4-9 bytes per driver only in
> the case where that driver is compiled in with zero channels configured
> for it -- a scope/risk tradeoff this document defers to the user rather
> than deciding unilaterally.
>
> **2026-09-10 scope note: two audited modules no longer exist.**
> `HARDWARE_MVP.md`'s 2026-09-10 revision removed the external sensor
> ports, the `TCAL9539` expander, both `TCA4307` isolation buffers and all
> four `TPS2553` sensor-power switches from `RP2350_INDUSTRIAL_MVP_V1`;
> `tcal9539_driver` and `board_power_service` were deleted from the tree
> with them. The file counts and task/queue/heap sweep described under
> "Method" below record what this audit actually examined when it ran and
> are left as written; the per-driver table and the singleton discussion
> have been updated to stop describing deleted code as present.

Answers `ROADMAP.md:602` ("Verify that compiled but inactive drivers
allocate no per-instance runtime context, task, channel buffer or
permanent SRAM/PSRAM block") for every driver added or extended in
v0.5.1 (T2/T4-T12, T16). "Compiled but inactive" is read here as: the
driver's `FIRMWARE_ENABLE_NATIVE_*` option is `ON` (so its code and any
file-static state link into the image), but zero channels in the running
configuration are actually assigned to it. The question is whether that
state's size depends on how many channels are actually configured to use
the driver, or is instead a fixed footprint paid the moment the option is
compiled in regardless of real usage.

## Method

For each driver, `grep -n "^static"` across its `.c` file lists every
file-scope (non-function) declaration; each one was classified as either
plain code (`const` lookup tables, living in flash/`.rodata`, not RAM) or
genuine RAM state, and every RAM-state array's size was checked against
whether it is indexed by an actually-configured channel count or by a
fixed, compile-time channel-count *ceiling* (`_MAX_CHANNEL_INDEX`-style
constants already established throughout this project). The same pass
searched all sixteen v0.5.1 driver/transport/service files for
`xTaskCreate`/`vTaskCreate` (FreeRTOS task creation), `xQueueCreate`
(queue creation), `pvPortMalloc`/`malloc(` (heap allocation), and any
`PSRAM`/linker-section attribute referencing external memory --
**zero matches for any of these across all sixteen files**. No v0.5.1
driver creates a task, a queue, or a heap/PSRAM allocation of any kind,
whether active or inactive.

## Per-channel scratch vs. driver-wide singletons (2026-09-09)

The remaining "Fixed" entries in the table above split into two genuinely
different categories, and only one of them is fixable the way
`synthetic`'s counter and `UIC`'s `g_derived[4]` were:

- **Per-channel scratch, indexed by `source_index`** (one value *per
  possible channel* of that driver): `synthetic`'s counter (fixed by
  codex, 2026-09-07) and `UIC`'s frequency/period baseline (fixed here,
  2026-09-09) are both this shape. The fix is mechanical and has a real
  payoff beyond satisfying the letter of the ROADMAP line: the state
  moves from a driver-private static (internal SRAM, `.bss`) into
  `native_channel_source_t::scratch`, which lives in the sensor-manager's
  existing per-channel context -- allocated from the **lazily-allocated
  PSRAM bank**, not SRAM. Measured on the reference build: `.bss` actually
  *decreased* by 48 bytes removing `UIC`'s array (`.text`/`.rodata`/`.data`
  effectively unchanged), because the 8-byte-per-slot growth of the
  now-shared scratch union lands in PSRAM instead -- 128 bytes total
  across all `PLATFORM_CHANNEL_LIMIT` (16) slots, against an 8 MiB pool.
  This is a genuine internal-SRAM saving, not just a bookkeeping change.
  `AD5422`'s fix (also 2026-09-07) took a different, better path for that
  driver specifically: it turned out the per-device cached code could be
  eliminated outright (`self_test` redesigned to read live CONTROL/STATUS
  instead of comparing against a remembered value) rather than relocated.
- **Driver-wide singletons** (exactly one value *regardless* of channel
  count -- a shared bus/chip binding): `ADS8688`/`MAX22190`'s
  `g_bus`, `UIC`'s own `g_counter`, and
  `adc_voltage`'s `g_adc_ready`. These cannot move into
  `native_channel_source_t` the way per-channel scratch does -- there is
  only one physical bus/chip/peripheral-ready-flag no matter how many
  channels of that driver are configured, so giving every channel its own
  copy would be wrong (channels sharing one physical bus must observe the
  *same* binding, not independent ones). The only way to make a true
  singleton's footprint disappear when its driver has zero configured
  channels is to convert it from an eager `static` to a `psram_malloc()`-
  allocated pointer, populated on the first channel's `start()` --
  `services/src/history_service.c`'s `g_store`/`g_flash_backend` already
  use exactly this pattern for larger structures, so it is not a novel
  mechanism in this codebase. **Decision (user, 2026-09-09): explicitly
  deferred, not applied.** The saving only materializes in the fairly
  contrived case of compiling a driver in with zero channels configured
  for it, and the cost is a null-check added to every function that
  touches the binding, across the affected driver files, for 4-9 bytes
  each -- a real risk/reward tradeoff, not a to-do backlog item, judged
  not worth it given the marginal saving and the scenario it only helps.
  (That decision covered four drivers when it was made; `TCAL9539`'s
  `g_bus`/`g_address` left the list on 2026-09-10 when the driver itself
  was deleted with its hardware, so three remain.)

## Finding

**Two of `synthetic`/`AD5422`/`UIC`'s three flagged per-channel-scratch
arrays are now fixed by relocation (`synthetic`, `UIC`); the third
(`AD5422`) was eliminated outright.** The remaining flagged state across
all v0.5.1 drivers is exclusively the driver-wide-singleton category
above -- a small, fixed compile-time constant (4-9 bytes) that does not
scale with configured/active channel count, paid once per compiled-in
driver type regardless of how many of its channels are actually
configured. There is no dynamic/heap growth, no scaling allocation, and
(confirmed above) no task, queue, or PSRAM allocation triggered merely by
compiling a driver in. The one place a genuine hardware resource is
claimed on demand rather than at compile time is `UIC`'s PIO state
machine (`pio_claim_unused_sm()`), correctly deferred to
`native_uic_start()` -- an inactive `UIC` channel holds no PIO SM at all,
only its share of the already-tiny fixed slot-table entry.

This satisfies `ROADMAP.md:602`'s intent for the per-channel-scratch
category as **an applied fix**, and for the singleton category as **a
design property that holds by construction** for the "no task/queue/
heap allocation" half of the line; the "no permanent block at all" half
does not hold for these four small (4-9 byte) singletons, by an explicit,
scoped decision (above) rather than an oversight. No `.bss`/`.map`-file
byte-counting tool was built for this pass -- the per-driver sizes above
come from reading each struct's field list directly, confirmed against
`arm-none-eabi-size -A` before/after the `UIC` fix for that one case.

## Not covered by this audit

- Non-v0.5.1 drivers (`internal_temp`, `gpio_input`, `gpio_output`) were
  not re-audited; their static-allocation shape predates this release and
  was not flagged as a concern.
- Per-channel runtime state owned by `channel_manager`/`sensor_manager`
  (the shared `telemetry_channel_t` array all drivers write into) is
  sized to the compiled channel-table capacity regardless of driver
  assignment -- this is pre-existing v0.4.x/v0.5.0 architecture, not a
  v0.5.1 driver concern, and out of this audit's scope.
