# v0.4.3 — Multi-Channel History and Alarm Engine

## Contract

Baseline: tag `v0.4.2`, commit `568dfd4e2a77c2db6fca4cd9a65e6279624928d6`.

Remove the remaining temperature/singleton assumptions from `history_service`
and `alarm_service`. History becomes a typed, owned, per-channel record store
with a bounded PSRAM ring and a bounded, non-transactional Flash-backed ring
for persistence across reboot and power loss. Alarms become independent
per-channel condition instances instead of one hard-coded status singleton.

Preserve all unrelated v0.4.2 public NodeIds, BrowseNames, Method signatures,
EventTypes, permissions, configuration fields and externally visible behavior.

This release may extend internal service and OPC UA adapter APIs where
required to expose generalized `HistoryRead` and per-channel alarm condition
instances. It must not implement OPC UA Part 11 Historical Event Access
(`ReadEventDetails` over the maintenance/alarm journals — scheduled for
v0.8.1), transactional live channel-model regeneration (v0.5.0), new
persistence schemas outside the channel-history Flash ring, Modbus support,
computed channels, dynamically loaded driver code, or unrelated model
refactoring.

Use `code-mapper` before implementation. Assign service/runtime API and Flash
backend work to `embedded-systems`, OPC UA `HistoryRead`/alarm-condition model
and interoperability work to `iot-engineer`, build/version/resource evidence
to `build-engineer`, and the integrated diff to `code-reviewer`. History and
alarms are independent subsystems — history does not depend on alarms, and
alarms read channel snapshots directly rather than through `history_service` —
so `embedded-systems` and `iot-engineer` may work the two subsystems in
parallel, as in v0.4.2. The primary agent owns cross-cutting contracts
(history record schema, alarm condition NodeId grammar, Flash region
ownership), integration and the release gate.

Before implementation, repository instructions must identify v0.4.3 as the
current release. If `AGENTS.md`, `ROADMAP.md` and this plan disagree, stop
before editing. `AGENTS.md` still names v0.4.2 as current at the time this
plan is written; correcting it is a separate, explicit roadmap-maintenance
task and must not be folded into this implementation.

## Baseline

Treat tag `v0.4.2` as the accepted implementation and compatibility baseline.

Capture the v0.4.2 public-contract inventory, resource metrics and QSPI Flash

## Scope decisions frozen before implementation

These were resolved during v0.4.3 planning and are binding for this release:

1. **History backend**: PSRAM per-channel ring (replacing the single global
   `HISTORY_SERVICE_CHANNEL_CAPACITY`-sample `float` ring) plus a bounded
   Flash-backed ring for persistence across reboot/power loss. The Flash ring
   is a **cyclic buffer without transactional guarantees** — unlike the
   maintenance journal, it does not require a commit-page/CRC/recovery-state
   machine. Losing the most recent samples on an interrupted write is
   acceptable; corrupting or exposing a torn sample is not, so per-sample CRC
   plus a simple valid/invalid marker per slot is still required, but no
   cross-sample transactional recovery classification is needed.
   - **Flash budget (frozen 2026-08-16, after T1 mapping)**: the reference
     board's QSPI layout (`ota/cmake/ota_layout.cmake`) has zero free space —
     bootloader plus two ~7.8 MiB OTA banks plus the maintenance journal plus
     config/identity/trust/security-state/OTA-state slots consume the full
     16 MiB, guarded by a `FATAL_ERROR` if they do not sum exactly. A new
     **128 KiB** history region is carved out by shrinking **both** OTA banks
     by **64 KiB each** (new bank size `0x7a4000`, was `0x7b4000`). The last
     shipped OTA payload was 3,297,616 bytes out of ~7.8 MiB per bank, so this
     leaves ample headroom. This changes the maximum firmware image size for
     all future releases, not only v0.4.3, and must be implemented in
     `ota/cmake/ota_layout.cmake` the same way the maintenance journal region
     was added (a new named `OTA_HISTORY_..._SIZE_BYTES`/offset symbol,
     cross-checked by the `app/basic_profile/ota_layout_sanity.c` static
     asserts), placed adjacent to the maintenance journal region.
   - **Per-channel Flash capacity**: 256 samples per channel times 16
     channels (`PLATFORM_CHANNEL_LIMIT`) times a packed ~32-byte record
     (8-byte raw value, 1-byte quality, 8-byte source timestamp, 4-byte CRC,
     remainder alignment/valid-marker padding) equals 128 KiB total, matching
     the budget above. The exact record layout is finalized in T3 but must
     not exceed 32 bytes/sample without revisiting this budget.
2. **Retention**: one fixed sample-count capacity per channel, applied
   uniformly across all channels regardless of configured sample period. A
   fast-sampled channel therefore naturally retains a shorter time window than
   a slow-sampled one; this is accepted as the per-channel retention policy
   required by `ROADMAP.md` and needs no per-channel configurable field or
   config-schema change in this release.
3. **Alarm types**: numeric high, high-high, low and low-low (symmetric),
   configurable hysteresis and debounce/delay, a distinct invalid/stale-quality
   fault state, and discrete state alarm for boolean channels.
4. **Alarm eligibility**: automatic. Every channel whose value type is numeric
   (`Float`, `Double`, `Int32`, `UInt32`, `Int64`, `UInt64`) or `Boolean` gets
   an alarm condition instance; there is no per-channel opt-in/opt-out
   configuration field in this release. `String` channels get no alarm
   instance.
5. **Stale-quality alarm behavior**: when a channel's `service_quality_t`
   becomes invalid/stale, its alarm condition enters a distinct fault
   `ActiveState`/`Severity`, separate from and not overwritten by whatever
   high/high-high/low/low-low state was last evaluated from good-quality data.
   Operators must be able to distinguish "process out of range" from "sensor
   unavailable."
6. **Alarm persistence**: alarms remain **live-event only** in this release —
   no Flash journal for alarm transitions. `ROADMAP.md`'s "record alarm
   transitions through the common event/journal abstraction" is satisfied by
   the existing OPC UA Events/Audit bridge used by `alarm_service` today. A
   Flash-backed alarm journal, and any standard `ReadEventDetails` history
   surface over it, belongs to v0.8.1 alongside the maintenance journal.
7. **HistoryRead scope**: generalized `HistoryRead` covers live/persisted
   channel *value* history only. It must not be extended to alarm/event
   history in this release.

## Architecture and public-contract rules

Services own history and alarm state. OPC UA callbacks remain adapters: they
translate `HistoryRead`/`HistoryReadRaw` requests into service-level history
queries and map per-channel alarm condition state to standard
Alarms & Conditions NodeIds.

The OPC UA layer must not:

- scan history storage directly (Flash or PSRAM) — it calls
  `history_service` read APIs only;
- evaluate alarm thresholds itself — it reflects `alarm_service`-owned
  condition state;
- retain mutable pointers into history or alarm service storage;
- regenerate source timestamps for historical samples.

`history_service` must not scan the complete history ring (PSRAM or Flash)
while interrupts/scheduling are globally locked, per `ROADMAP.md`. Reads must
use a bounded critical section per chunk, not one lock held for the whole
scan, consistent with the existing PSRAM ring's per-scan mutex pattern but
extended to work correctly with the new Flash ring and per-channel storage.

`alarm_service` must create one stable condition instance per alarm-eligible
channel at startup, keyed by the same stable channel ID used by the v0.4.2
channel model — not by registry index or memory address. Acknowledgement
state is tracked independently per condition instance.

## File-level implementation plan

### T1 — Map and freeze existing contracts

Primary files:

- `services/include/services/history_service.h`;
- `services/include/services/alarm_service.h`;
- `services/include/services/telemetry_channel.h`;
- `services/include/services/channel_manager.h`;
- `services/include/services/platform_limits.h`;
- `services/src/history_service.c`;
- `services/src/alarm_service.c`;
- `opcua_model/src/model_history.c`;
- `opcua_model/src/model_events.c`;
- `opcua_model/src/model_channels.c`;
- `drivers/include/drivers/maintenance_journal_backend.h` (Flash-journal
  precedent, not a dependency);
- existing asyncua/open62541 verification tools.

Use `code-mapper` to identify:

- current global-ring critical-section scope in `history_service.c` and
  exactly where it violates the "no scan under global lock" rule;
- current `HistoryRead`/`HistoryReadRaw` callback wiring in
  `model_history.c` and its assumption of one channel/one ring;
- current `alarm_service_status_t` singleton usage sites in
  `model_events.c` and elsewhere;
- available/free QSPI Flash region for the new history ring, accounting for
  the existing maintenance journal region;
- v0.4.2 stable channel-ID and metadata APIs to key alarm conditions and
  history records on.

Before implementation, explicitly freeze:

- per-channel history record schema (fields, size, CRC/valid-marker layout);
- Flash region geometry (base address, sector count, per-channel slot
  layout) and its independence from the maintenance journal region;
- PSRAM-to-Flash write policy (synchronous per sample vs. batched flush) and
  its interaction with sampling-task timing budgets;
- alarm condition NodeId grammar (one condition per eligible channel, derived
  deterministically from the channel ID, consistent with the v0.4.2 channel
  NodeId grammar);
- alarm configuration field set (thresholds, hysteresis, debounce) and where
  it lives in the existing configuration schema;
- fault-state representation for invalid/stale-quality alarms;
- generalized `HistoryRead` continuation-point and max-return-count bounds.

Do not begin implementation while these contracts remain ambiguous.

### T2 — Per-channel history record store (PSRAM)

Primary files:

- `services/include/services/history_service.h`;
- `services/include/services/platform_limits.h`;
- `services/src/history_service.c`.

Replace the single `HISTORY_SERVICE_CHANNEL_CAPACITY`-sample global `float`
ring keyed by borrowed `const char *channel_id` with per-channel typed,
owned record storage sized `PLATFORM_CHANNEL_LIMIT` × a fixed per-channel
sample capacity, bounded so total PSRAM use does not regress uncontrolled
relative to the v0.4.2 baseline.

Support every value type accepted by the v0.4.2 channel runtime (not only
`float`). Own channel-ID storage; do not retain borrowed pointers whose
lifetime is ambiguous.

Read APIs must scan per-channel storage using bounded critical sections, not
one lock for the entire multi-channel scan.

Tests cover mixed value types, per-channel capacity wraparound, concurrent
sampling and reads, and coherent snapshots.

### T3 — Flash-backed history ring

Primary files:

- `ota/cmake/ota_layout.cmake`;
- `app/basic_profile/ota_layout_sanity.c`;
- `docs/flash-storage.md`;
- new `drivers/include/drivers/history_flash_backend.h` and
  `drivers/src/history_flash_backend.c` (or equivalently named);
- `services/src/history_service.c`;
- `services/include/services/history_service.h`.

First, insert a new 128 KiB `OTA_HISTORY_*` reserved region into
`ota_layout.cmake`'s region list, adjacent to the maintenance journal region,
shrinking `OTA_BANK_SIZE_BYTES` by 64 KiB per bank as frozen above. Update
the `_Static_assert`s in `ota_layout_sanity.c` and `docs/flash-storage.md`'s
prose map to match. Confirm the CMake configure step still asserts the
layout covers the full 16 MiB exactly.

Then add a bounded, per-channel Flash-backed ring in that region, following
the `flash_operation_coordinator`-mediated read/program/erase pattern already
used by `maintenance_journal_backend.c` (XIP read at `OTA_LAYOUT_HISTORY_*`
origin, program/erase via the shared coordinator at the matching offset).
Each stored sample carries a per-sample CRC and a valid/invalid marker; a
torn or unreadable sample is skipped, never exposed. No cross-sample
transactional recovery state machine is required — losing the most recent
unwritten samples after power loss is accepted behavior for this release.

Restore available Flash-backed history on startup before the OPC UA
`HistoryRead` surface is exposed. Define and document the write policy
(synchronous vs. batched) and its bound on sampling-task stack/timing impact.

Tests cover: power loss before/during/after a sample write, ring
wraparound, corrupt/torn last-sample skip behavior, and restoration after
reboot for every supported value type.

### T4 — Generalized OPC UA `HistoryRead`

Primary files:

- `opcua_model/src/model_history.c`;

### T5 — Per-channel alarm condition instances

- `services/src/alarm_service.c`;

Replace the `alarm_service_status_t` singleton with one condition instance
per alarm-eligible channel (every numeric or `Boolean` channel present at

Support high, high-high, low, low-low numeric alarms with configurable

overwrite the last good-quality alarm state.

Preserve acknowledgement state independently per condition instance.

Tests cover: simultaneous independent alarms on multiple channels,
hysteresis/debounce timing, quality-fault entry/exit, and acknowledgement
independence across conditions.

## Completion

Done only when:

- history storage is per-channel, typed and owned (no borrowed
  `channel_id`, no single global `float` ring);
- history reads never hold one lock across a full multi-channel scan;
- a bounded, per-channel Flash-backed history ring survives reboot/power
  loss with skip-on-corruption behavior, without a transactional recovery
  state machine;
- `HistoryRead` is generalized to every historizing-enabled channel with
  bounded continuation points and return counts;
- alarm state is one independent condition instance per alarm-eligible
  channel, not a singleton;
- alarms support high/high-high/low/low-low, hysteresis, debounce, discrete
  boolean state, and a distinct invalid/stale-quality fault state;
- acknowledgement state is independent per condition;
- alarm transitions remain live-event only; no Flash journal or
  `ReadEventDetails` surface was added for alarms;
- no v0.8.1 Historical Event Access work entered the diff;
- no v0.5.0 transactional live model-regeneration work entered the diff;
- public-contract, build, static-analysis, version, size and
  independent-review gates pass.

Do not create a release tag, implement v0.4.4/v0.5.0 or later roadmap work,
or modify `ROADMAP.md` while implementing this plan. Updating `AGENTS.md`'s
current-release pointer is a separate, explicit roadmap-maintenance task.
