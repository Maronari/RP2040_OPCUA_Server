## Trust and identity

The bootloader and application must verify SHA-256 and ECDSA on secp256r1 using
the existing mbedTLS source. A checksum, successful transport or administrator
role cannot authorize execution. Verification failure never writes a bootable
state. Physical Flash/SWD replacement is outside this trust boundary.

Use a bootloader-compiled table with at most two entries, each a nonzero
32-bit key ID and a 65-byte uncompressed SEC1 P-256 public point. IDs are unique;
the point must be validated on secp256r1. Unknown IDs and malformed points fail
closed. Application verification uses the identical generated public table;
the bootloader independently rechecks before execution. Missing production
public-key provisioning must fail a production artifact build. No development
key is an implicit default. No private key is generated or provisioned here.

Production signatures belong only to the owner-approved protected CI signing
job. Platform environment approvals, protected tags, checked main ancestry and
exact artifact/source provenance need actual GitHub evidence in T5. YAML alone
does not establish these protections. Lost-key recovery is local USB/SWD
reprovisioning, preserving the data tail; remote rotation is outside v0.6.0.

Compatibility is an explicit provisioning/build tuple: hardware profile,
numeric board revision, firmware profile, driver pack and driver-pack contract
version. Neither the MCU family nor a network-supplied string supplies board
identity. A production build without an explicit board revision must fail.
Hardware/firmware/profile strings use the same canonical IDs in the capability
export, signer and verifier; T0 must inventory and bind the existing IDs before
enabling packages. Driver-pack changes may select another installed native
pack, but never load executable driver modules from configuration.

The current supported production build bindings are now selected explicitly:

| Build selection | Signed hardware ID | Signed firmware ID | Signed pack ID |
|---|---|---|---|
| reference/base | `waveshare_core2350b_16m8m` | `device_profile_basic` | `base` |
| industrial | `rp2350_industrial_mvp_v1` | `device_profile_basic` | `industrial` |

Hardware IDs bind explicitly to the existing pack-to-PICO_BOARD mapping in
root CMake. The reference's full SDK board name
`waveshare_core2350b_16mb_psram8mb` is 33 characters and cannot fit a canonical
31-character manifest ID: use the exact 25-character signed alias
`waveshare_core2350b_16m8m` for that board, never truncate automatically.
The industrial SDK board name fits unchanged. The firmware ID is the existing
application target name. Driver-pack contract
version 1 designates the current supported pack compositions and persisted
driver meanings; it does not renumber driver IDs. Undefined packs and custom
compositions cannot be signed as an existing supported pack by guessing an
identity. T5 must bind one generated metadata source to the native verifier,
artifact provenance and host packaging, and reject inconsistent selections.
Diagnostic/benchmark builds are explicit test profiles, not production signed
artifacts carrying a misleading production identity.

Numeric hardware revision is still an explicit provisioning input: no value is
derived from MCU, module name or an OPC UA client. T5 must require a supplied
revision for a signed production target and include it in provisioning
evidence; omission fails that target, without breaking ordinary legacy/debug
builds. The verifier's immutable local policy carries that provisioned value.
This design does not claim that the connected module's numeric revision has
already been independently identified or provisioned.

## Selected manifest wire contract

Use a fixed 320-byte binary manifest. All integers are unsigned little-endian;
decode explicitly, never cast untrusted bytes to a C struct. There is no JSON,
ASN.1 or variable-length signature in the device parser. Human-readable JSON
may accompany the artifact but is not an authentication input.

| Offset | Bytes | Field and constraints |
|---:|---:|---|
| 0 | 8 | Magic ASCII `RP2OTA06` |
| 8 | 2 | Manifest format, exactly 1 |
| 10 | 2 | Signed byte count, exactly 256 |
| 12 | 4 | Manifest byte count, exactly 320 |
| 16 | 4 | Recovery layout ID, exactly 1 for the proposed layout below |
| 20 | 4 | Trusted key ID, nonzero and present in the compiled table |
| 24 | 4 | Image size, 1 through 5,271,552 inclusive, also subject to vector checks |
| 28 | 4 | Packed firmware version from the existing single version source |
| 32 | 4 | Execution origin, exactly `0x10040000` for layout 1 |
| 36 | 4 | Minimum board revision, inclusive |
| 40 | 4 | Maximum board revision, inclusive and at least the minimum |
| 44 | 4 | Driver-pack contract version, nonzero and supported |
| 48 | 32 | Hardware profile ID |
| 80 | 32 | Firmware profile ID |
| 112 | 32 | Included driver-pack ID |
| 144 | 32 | SHA-256 of exactly image-size raw BIN bytes |
| 176 | 80 | Reserved, every byte zero |
| 256 | 32 | ECDSA `r`, unsigned fixed-width big-endian |
| 288 | 32 | ECDSA `s`, unsigned fixed-width big-endian |

Each ID is 1--31 ASCII characters from `[A-Za-z0-9_.-]`, followed by NUL and
zero padding through the 32-byte field. No case folding or whitespace trimming.
Reject truncation, appended bytes, unknown format/layout, nonzero reserved
bytes, invalid ranges, empty/unterminated IDs and arithmetic overflow.

ECDSA authenticates SHA-256 of bytes `[0,256)` exactly, including the domain
magic, key ID, compatibility fields and image digest. Require `1 <= r < n` and
`1 <= s <= n/2` for the P-256 group order `n`; the signer canonicalizes high-s.
The image digest covers the raw A-linked binary, excluding its reserved
manifest sector and any transport padding. Verify exact image length and hash
as well as signature; authenticating the manifest alone is insufficient.

Define content identity as SHA-256 of the signed 256-byte manifest prefix,
excluding the randomized ECDSA signature. Same-version reinstall is accepted
only when that identity equals the current confirmed identity. A different
identity, including different compatibility/key metadata, needs a higher
version. The confirmed version floor and identity advance together only at
the confirmation commit. During an unconfirmed transaction only the pinned
known-good manifest is exempt from that candidate floor. The test-only
compile-time downgrade override bypasses the version comparison alone;
signature, compatibility, length and hash checks always apply.

## Selected recovery algorithm and proposed geometry

All numbers below are Flash offsets, not XIP addresses. Preserve every
persistent region from `0xF58000` upward at its existing address and size.
No configuration, identity, trust, history or journal capacity is borrowed.

| Region | Start | End exclusive | Bytes |
|---|---:|---:|---:|
| Bootloader reserve | `0x000000` | `0x040000` | 262,144 |
| A: executable working image | `0x040000` | `0x548000` | 5,275,648 |
| B: known-good backup | `0x548000` | `0xA50000` | 5,275,648 |
| C: uploaded candidate | `0xA50000` | `0xF58000` | 5,275,648 |
| Existing data/state tail | `0xF58000` | `0x1000000` | 688,128 |

Reserve the final 4,096-byte erase sector of each image slot for its manifest;
store the 320 bytes at the sector start and keep the remainder erased. Payload
capacity is therefore `0x507000` (5,271,552 bytes). All boundaries align to
4,096-byte erase sectors and 256-byte program pages. The measured preparation
BIN, 3,586,824 bytes, has 1,684,728 bytes of capacity headroom. This comparison
does not predict the final signed-image or industrial size.

Applications link only for A. B and C store the same A-linked bytes and are
never executed at their storage addresses. This avoids B/C relinking or a
relocatable application ABI. Boot code, linker scripts, vectors, ROM handoff
and factory artifacts must all move to A's new origin together in T2/T5.
The 256 KiB bootloader region is a design reservation, not a measured crypto
build size. Reject over-capacity images/artifacts before erasing any slot.

The state machine is:

1. **CONFIRMED**: authenticate A. User upload may write C only. Interrupted or
   failed upload leaves A untouched and never activates anything.
2. **VERIFIED**: authenticate C and record its manifest. A continues running.
   Only a separate authorized activation request can commit **BACKUP**.
3. **BACKUP**: authenticate A, copy A and its manifest to B, then authenticate
   B against the pinned confirmed identity. A stays untouched. Persist
   **INSTALL** only after B passes; failed/interrupted backup aborts to verified
   unchanged A with a committed failure reason. It never automatically restarts
   backup preparation; an unusable A or abort commit requires local recovery.
4. **INSTALL**: before every A erase/copy, validate pinned B and candidate C.
   Copy C into A, read back and authenticate A. Any reset during INSTALL selects
   **RESTORE** on the next boot, with B intact; do not resume C. Invalid C also
   selects RESTORE. This freezes the conservative executable-model choice.
5. **LAUNCH_CONSUMED**: commit the one-attempt boundary before jumping to A,
   then arm the OTA-only watchdog. Any subsequent reset with this state goes
   to **RESTORE**, including power loss between this commit and the jump.
   Such a loss may consume an attempt without a launch; it must never produce
   a second candidate launch. Only the live candidate can request confirmation.
6. **CONFIRMED**: atomically commit candidate identity, version floor and
   cleared pending state after sustained health. A torn commit selects either
   the previous LAUNCH_CONSUMED state (restore) or the fully confirmed new state.
7. **RESTORE**: authenticate pinned B before touching A, copy B to A and
   authenticate the restored A before recording a rollback result. Interruption
   restarts restoration; never erase B or automatically activate C again.

If both A and the pinned backup are unusable, or no trustworthy state can
establish a permitted image, enter local recovery. Never jump merely because
vectors look plausible. Bounds and signed execution-origin checks supplement
the SDK/ROM handoff checks. No boot path treats the legacy FAILED flag as a
restored image. A new update or retry always needs a new explicit request.

## Persistent transaction format and ownership

Use two independent 4 KiB sectors within the existing 64 KiB OTA state region,
at `0xFF0000` and `0xFF1000`. The rest remains reserved. Never erase the newest
valid committed sector when preparing its successor. Serialize a bounded
record in the first 1,024 bytes; program a separate final 256-byte commit page
at sector offset 3,840 only after data read-back validation. A boot read accepts
a record only if header/version, lengths, phase, manifest descriptors, CRC and
commit marker agree. CRC detects torn metadata, not image authenticity.

The proposed record is explicitly serialized little-endian:

| Offset | Bytes | Field |
|---:|---:|---|
| 0 | 8 | ASCII `RP2OST06` |
| 8 | 2 | State format 2; legacy v1 is never promoted implicitly |
| 10 | 2 | Record length 1,024 |
| 12 | 4 | Phase: CONFIRMED=0, VERIFIED=1, BACKUP=2, INSTALL=3, LAUNCH_CONSUMED=4, RESTORE=5 |
| 16 | 8 | Generation, nonzero, no rollover |
| 24 | 4 | Confirmed version floor |
| 28 | 4 | Bounded failure reason enum (native mapping to freeze before integration) |
| 32 | 4 | Board/build confirmation policy ID |
| 36 | 4 | Descriptor presence bits 0=confirmed, 1=candidate, 2=backup; other bits zero |
| 40 | 20 | Reserved zeros |
| 60 | 4 | IEEE CRC-32 of all 1,024 bytes with this field zeroed |
| 64 | 320 | Confirmed manifest |
| 384 | 320 | Candidate manifest, zeros when absent |
| 704 | 320 | Backup manifest, zeros when absent |

The last sector page is exactly ASCII `RP2COM06` (8 bytes), generation (8),
record CRC (4), then 236 zero bytes. Program it once, after record read-back;
require the complete page to match, including zero padding. Leave sector bytes
1,024 through 3,839 erased. A torn page that is fully identical to the intended
page is already a valid commit; otherwise retain the previous sector. Native
tests must inject torn erase and program operations within data and marker
pages, not just whole-operation resets. Descriptor-presence/phase validation
must reject inconsistent states before choosing an image.

Refuse generation exhaustion rather than wrapping. Equal generations with
different data are corruption and require recovery. Validate every selected
image cryptographically even when metadata CRC passes. On confirmation,
replace the confirmed descriptor with candidate and clear candidate; old B
bytes may remain for diagnostics, but clear its descriptor in the new record;
it is no longer authorized as a below-floor fallback after confirmation.
A new transaction snapshots the new
confirmed A into B before installation. The native reason enum below and the
policy IDs in the T0 freeze ledger are now fixed. Integrated confirmation-policy
timing must pass the stated T2/T3 target gates.

The exact descriptor-presence masks selected for the byte-codec design are
CONFIRMED=1, VERIFIED=3, BACKUP=3 and INSTALL/LAUNCH_CONSUMED/RESTORE=7.
BACKUP describes the operation before its authenticated backup is committed;
the transition to INSTALL introduces the pinned backup descriptor. An absent
descriptor is all zero bytes. For phases with a backup, its signed prefix must
equal the confirmed prefix; randomized signature bytes do not change content
identity. The floor equals the confirmed version. Under production policy a
candidate must be newer, or have exactly the same signed prefix at the same
version. Equal-generation byte-identical records may select either copy;
equal-generation differing records fail closed. Generation 0 is invalid and
the successor of UINT64_MAX is refused.

Native bounded diagnostic reasons are assigned as follows; these are not new
public NodeIds or changes to the existing service result enumeration:

| Value | Reason |
|---:|---|
| 0 | NONE |
| 1 | MANIFEST_REQUIRED |
| 2 | MANIFEST_INVALID |
| 3 | UNKNOWN_KEY |
| 4 | SIGNATURE_INVALID |
| 5 | IMAGE_HASH_MISMATCH |
| 6 | INCOMPATIBLE |
| 7 | VERSION_REJECTED |
| 8 | STORAGE_ERROR |
| 9 | STATE_INVALID |
| 10 | BACKUP_INVALID |
| 11 | CANDIDATE_INVALID |
| 12 | HEALTH_TIMEOUT |
| 13 | HEALTH_FAILED |
| 14 | ALLOCATION_FAILED |
| 15 | RECOVERY_REQUIRED |

Unknown reasons are invalid serialized state. Policy ID 1 in the design fixture
is a syntactic test value only; a production timing policy is not provisioned
by that fixture. Development downgrade-override state needs a separately
identified test-only policy and remains outside this production-policy codec
experiment. It cannot silently reuse the production floor rules.

The application update service owns the single update transaction. Bootloader
owns its pre-scheduler persistent phases. A service-owned boot-window component
owns runtime readiness/confirmation; adapters only convert requests/results.
Serialize application state mutation and Flash transactions through the
existing Flash coordinator, with explicit copied snapshots across tasks. Do
not hold service locks through a whole-image hash/copy. Native verification
uses an immutable operation snapshot; no borrowed client buffer survives a
callback. Keep one bounded operation; concurrent activation/abort/confirmation
must fail deterministically and may not erase fallback state.

## Transport and legacy contract

Preserve existing method signatures and NodeIds. Keep Begin size/CRC/version
and chunk payload semantics as raw image transfer, with one session and a
4,096-byte maximum chunk. CRC remains a transfer check. Add a separately
authorized signed-manifest attachment adapter and explicit activation adapter
after native APIs freeze; their exact NodeIds are not allocated here.

Proposed additive method contracts are `SetFirmwareManifest(ByteString[320])
-> Boolean` for the current session, and `ActivateFirmwareUpdate() -> Boolean`
for an already verified candidate. Both new methods require Admin. Existing
OTA methods retain their Service minimum role from the compatibility baseline;
the old "admin-like" description was inaccurate. Attaching or finalizing cannot
activate/reboot. Attach is allowed
once per session (identical retransmission succeeds; changed bytes fail), must
match Begin size/version, and cannot change a verified/activated transaction.
The OPC UA role/inventory review in T4 must verify those additions before
allocating identifiers. No existing field or persisted driver ID is renumbered.

Finalize with no attached signed manifest returns native
`FIRMWARE_UPDATE_RESULT_VERIFY_FAILED` (existing value 7), Boolean false and
OPC UA Good, preserving the existing operational-rejection convention; retain
bounded diagnostic reason `SIGNED_MANIFEST_REQUIRED`. Invalid signature/key
also returns VERIFY_FAILED/false with distinct reason text. Legacy methods
keep Good/false for other operational failures, including compatibility,
version and phase rejection; malformed arguments and authorization keep their
existing bad status codes. The new adapters may map verification failure to
`BadSecurityChecksFailed`, compatibility/version to `BadConfigurationError`,
illegal phase to `BadInvalidState` and temporary unavailability to
`BadResourceUnavailable`. All authorization runs before mutation. Success
maps to Good/true. The unconfirmed-mutation guard must preserve existing
Boolean-method conventions and use a deterministic temporary-unavailable
service reason; write callbacks without a Boolean result use
`BadResourceUnavailable`. These are intended T1/T4 changes, not current
firmware behavior. GetFirmwareUpdateStatus keeps its 512-byte bound: include
phase/progress, verification reason, attempt-used and rollback reason using
bounded enums, never truncate invalid JSON or omit an error as success.

Abort may discard an uploading/verified candidate; it cannot reset a consumed
launch or erase the retained known-good image. Activation pins the verified
identity, and reboot occurs only after its state commit succeeds. Failed
activation must not schedule a reboot. Require explicit retry after rollback.

## Configuration and other persistent data

Refreshed read-only mapping found these existing owners; reuse them rather
than adding another configuration store or a callback-owned state machine:

| Existing path/symbol | Unconfirmed-boot hazard |
|---|---|
| `services/src/config_service.c`, `config_service_init()` | Migrated/default payload can be persisted during initialization |
| `services/src/config_store_service.c`, configuration transaction backend | Stage/commit and running-to-last-known-good promotion can alter rollback selection |
| `app/basic_profile/main.c`, startup identity/trust provisioning | A build-provided identity or trust mismatch can trigger a persistent replacement before acknowledgement |
| Security service/state/import owners | Users, passwords, trust, identity, commissioning and generation commits can change data needed by the old image |
| `services/src/maintenance_service.c` | Journal append can run independently of OTA methods |
| `services/src/history_service.c` | Flash history append can follow a RAM-ring insertion in background work |
| `ota/src/ota_flash.c`, `ota_flash_writer_begin/finish()` | Existing begin resets shared state; abort also resets it without phase protection |

While unconfirmed, load the compatible confirmed configuration into RAM and
defer migration/default persistence. Freeze persistent user mutation entry
points before starting any externally reachable service. Existing transaction
replay must not promote a candidate-only config schema. If old confirmed
configuration cannot be loaded safely, fail health and restore the old image.
There is no new user configuration schema in v0.6.0. Future incompatible schema
updates would need a snapshot/restore design; silently rewriting both config
slots in this release is forbidden.

Gate config commit/reset/import/apply/save, identity/certificate/trust/user
replacement and commissioning persistence, maintenance journal appends and
history Flash writes during the boot window. Reads and volatile diagnostics
remain available. Necessary OTA transaction writes are allowed only through
the boot transaction owner. Classify initialization/recovery writes separately
before integration; a blanket OPC UA callback guard cannot protect startup,
background journal/history workers or native callers.

The owner classification for T3 is explicit:

| Owner/path | Behavior during the unconfirmed window |
|---|---|
| Config startup selection/recovery | Select a compatible committed RUNNING or LKG payload into RAM; do not discard STAGED, repair slots, migrate persisted bytes or save defaults. A compatible existing default selection may be held in RAM; inability to select a configuration readable by the retained image fails health. |
| Config apply/import/reset/save | Reject before staging or touching either persistent slot. Volatile diagnostics are separate from configuration mutation. |
| Security startup/build identity | Read existing identity/trust/users. Defer build-asset replacement and all store repair/commit. If required usable existing security state cannot be loaded without rewriting it, fail health rather than promote new credentials. |
| Security user and certificate/trust mutation | Reject before validation paths that allocate a persistent replacement or erase a slot; expose the existing temporary-unavailable convention. |
| History background persistence | Continue bounded RAM sampling if otherwise valid; suppress Flash append/compaction/repair and report persistence unavailable. Do not queue an unbounded deferred backlog. |
| Maintenance journal | Extend the existing journal-mutations-blocked gate; suppress initialization repair and appends. Preserve reads and bounded volatile diagnostics. |
| OTA service | Reject new begin/attach/activation/abort mutations of the boot transaction while unconfirmed; only the boot-window owner can commit confirmation or failure state. |

These rules cover native callers and startup/background workers as well as
OPC UA. Guard state must be established from authenticated boot metadata before
any of these owners initialize, not after the server starts. Reads must not
silently repair storage while the guard is active. Confirmation releases the
guard only after its durable transaction succeeds; a failed commit keeps it
active. The retained image may perform its normal compatible recovery after
rollback. New guard/API implementation remains T3, after the shared contracts.

Initial deployment must back up the whole preserved tail with offsets, length
and SHA-256, plus exported config/identity/trust where supported. Locally install
the new bootloader, signed A image, authenticated initial backup and committed
initial state without bulk erase or overlapping user-data writes. Verify
preserved user-data read-back and normal data readability before accepting
provisioning; compare OTA state separately against its deliberately new
initialized transaction, not against unchanged legacy state bytes. Old
unsigned firmware/state never becomes an authenticated fallback automatically.
An interrupted first installation is recovered locally from these backups and
signed initial artifacts. Factory tools must reject blanket images containing
erased bytes over protected user storage, and must not treat padding as a
preservation mechanism. This is a procedure to implement/test, not evidence
that current factory tools already preserve data.

## Health, bounded resources and initial gate inventory

This section retains the initial mapping and gate rationale. The 2026-10-29
freeze ledger supplies the current policy and implementation entry conditions;
historical unresolved measurements below are not claims of integrated success.

One candidate attempt is fixed. Boot confirmation needs readiness plus a
sustained healthy interval from scheduler, config, storage, local network stack
and the OPC UA server loop. Link-up, DHCP lease, wall-clock/NTP availability and
client connection are not readiness requirements. Report missing readiness as
unavailable/failure, never as zero measurement or success. Bind readiness to
actual owner updates, not just successful task creation. The existing general
watchdog feed must not be able to extend the OTA absolute deadline or conceal
a stalled candidate. An OTA-only hardware watchdog handoff belongs in T3;
general watchdog/supervisor redesign remains v0.6.2.

Initial mapping found that `network_manager_is_ready()` means `has_ipv4`,
and `model_core_task()` waited for it before creating the OPC UA server. It is
therefore **not an acceptable OTA health predicate** under the approved
no-cable/no-DHCP rule. `network_manager_status_t.initialized` is useful local
evidence but does not prove a progressing server. `config_service_get()` always
returns the running-config address and likewise cannot prove initialization.
Capture `config_service_init()` success and storage recovery results explicitly.
There is currently no public server-ready/first-successful-iterate signal:
the server pointer in model context is private and unsynchronized. T3 needs a
minimal bounded owner-published readiness/progress snapshot and an offline
initialization path that can establish local OPC UA health without a lease.
Validate that path before using its signals for confirmation; do not substitute
task existence or the private server pointer for successful initialization.

The minimal T3 signal ownership is: InitTask publishes scheduler-running and
the actual config initialization result; each storage owner publishes its
read/recovery result without counting an empty store as a failure; NetworkTask
publishes initialized local-stack state and bounded progress independently of
lease/link; OpcUaTask publishes successful server/address-space startup and
iteration progress. Readiness is not a pointer or task-handle test. Publish
fixed-size copied snapshots under brief existing critical sections, with a
monotonic observation generation and explicit unavailable/failed values.
Only the boot-window owner combines those signals and commits confirmation.

For offline startup, T3 must remove the lease dependency from *local* server
initialization while retaining address/lease diagnostics. Bind the local
listener independently of DHCP, and update the advertised endpoint/discovery
address from a copied network snapshot on OpcUaTask after an address change.
Endpoint replacement must complete between server iterations, with bounded
allocation and all-or-nothing replacement; retain the old valid endpoint on
allocation failure and expose the failure. Do not restart the boot timer or
declare failed health just because no routable address exists. Validate this
offline path and address refresh before enabling health confirmation.

The V3 host observer saw firmware logging 1.907 seconds after USB reopened
and server startup 21.797 seconds after reopening, including DHCP and server
setup. These are neither actual jump-to-readiness measurements nor cable-free
startup evidence. They cannot justify a short absolute boot deadline yet.
Those preliminary observations did not select a deadline. The subsequent
freeze ledger selects the sustained interval, cutoff and OTA-only watchdog
policy with explicit integration gates; no 60-second/three-attempt policy
is introduced.

Fixed parser/transport budgets selected here: 320-byte manifest, 256 signed
bytes, three 32-byte IDs, two trusted keys, one session, 4,096-byte chunks,
5,271,552-byte payload cap and 512-byte status output. Copying needs at most one
