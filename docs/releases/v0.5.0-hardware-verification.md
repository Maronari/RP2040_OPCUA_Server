Date: 2026-08-30 (Europe/Moscow)  
Target: `opc.tcp://192.168.1.102:4840`  
Board: `waveshare_core2350b_16mb_psram8mb/W5500`

## Result

**Update (2026-09-01): root-caused and fixed -- see "Root cause confirmed
and fixed (2026-09-01)" at the end of this document.** The section below is
kept as the original finding for the investigation narrative.

The v0.5.0 implementation is not release-ready on the reference hardware.
The validate/persist/activate/rollback path, rejection paths, normal reboot
persistence, secure access and bounded read/subscription load work, but the
required controlled full OPC UA server restart does not run after a structural
configuration commit. The committed configuration is persisted and activated,
while the live address space and existing sessions remain attached to the old
model and `rebootRequired` remains `true`.

The device was restored after every mutating check. Its final exported
configuration is byte-identical to the initial export:
`a462b047f3f671c190fa03e641b526f23c7e7e8f95b88eb9d2aeaffb6c9b27df`.
Final state was running revision 29, staged revision 29,
`stagedDiffers=false`, `rebootRequired=false`, with no active import session.

## Confirmed server defect

### Controlled restart is not executed after a structural commit

Severity: release blocker.

Reproduction:

1. Establish a secure authenticated OPC UA session.
2. Export the running configuration.
3. Change only the description of the existing channel and apply it through
   `BeginConfigImport` / `WriteConfigChunk` / `ValidateImportedConfig` /
   `ApplyImportedConfig`.
4. Continue calling `GetConfigState` on the original session.

Observed on hardware:

- the transaction committed and advanced running/staged revision to 28;
- the old session remained usable for 8 seconds and completed 64 consecutive
  reads;
- every observed state had `stagedDiffers=false`, no active import session and
  `rebootRequired=true`;
- no server-side TCP/session disconnect occurred;
- importing the original configuration restored the exported bytes and cleared
  `rebootRequired`, but this can happen because the running configuration again
  matches the still-old address-space snapshot; it is not evidence of restart.

The same symptom was reproduced with `ApplyConfigPreset("sensor_node")`: 86
successful state polls over 45 seconds, zero reconnect events and a permanently
true `rebootRequired`. The remaining two presets were deliberately not applied
after this failure.

Relevant implementation chain:

`model_apply_imported_config()` / `model_apply_config_preset()` ->
`config_service_replace_and_save()` ->
`config_service_run_commit_extensions()` ->
`model_config_service_restart_callback()` ->
`g_pending_actions.restart_pending` -> `model_core_task()`.

The service host tests prove that a fake callback is invoked, but there is no
integration test proving that the real callback arms the pending action, that
`UA_Server_run_iterate()` exits its lifetime loop, or that the old session is
closed. Hardware evidence narrows the failure to the real callback/predicate/
pending-action part of this chain; source-only evidence is insufficient to say
whether the callback pointer is absent at runtime or its structural predicate
returns false. Add bounded instrumentation before choosing between those two
causes.

Recommended fix:

1. Add temporary counters/diagnostics for restart callback registration,
   callback invocation, predicate result, pending-action arm and server-lifetime
   rebuild. Capture them in the failing hardware test.
2. Make the restart decision compare the committed configuration against
   `g_model_address_space_config_snapshot`, the model that is actually being
   served. Comparing only `previous_running` with `new_config` cannot recover
   if the snapshot is already stale and the same running configuration is
   committed again.
3. Keep teardown deferred until the method callback returns, but require the
   old secure channel/session to be closed before declaring the transaction
   complete from the verifier's point of view.
4. Add an integration regression: `snapshot != running`, commit
   `new == running`, assert restart is still armed, rebuild completes,
   `snapshot == new`, and `rebootRequired=false`.
5. Add on-device regression checks for both imported configuration and all
   three presets. Each must prove failure of a read on the old session, then
   reconnect, inspect the rebuilt channel model and restore the baseline.

## Release-plan semantic conflict

The release plan still describes teardown/rebuild as completing synchronously
before the configuration commit returns. The implementation deliberately only
arms `restart_pending` synchronously and performs teardown after the current
`UA_Server_run_iterate()`/Method callback returns, because deleting the active
`UA_Server` inside its own Method callback is unsafe. README, changelog and
channel-model summaries also use both meanings of “synchronous”.

This must be resolved as a separate explicit release-plan maintenance decision
before the restart fix is accepted: either formalize the safe deferred boundary
(no further request served by the old model; Method reply or disconnect is
allowed), or redesign the service/API contract around an acknowledged restart
handoff. The verification report does not silently redefine the authoritative
release plan.

## Verification-tool defects found and corrected

- The previous v0.5.0 restart check explicitly disconnected its own client and
  accepted a subsequent connection as restart evidence. It could therefore
  report a false pass. `verify_v050.py` now requires the pre-transaction session
  to become unusable within a bounded timeout.
- `stage_config.py` and the OTA tool could select the same legacy temporary
  client-certificate directory while using different Application URIs. Parallel
  checks could overwrite each other's certificate and produce transient secure
  channel/resource failures. Configuration verification now has its own
  temporary certificate directory.
- `verify_listener_recovery.py` assumes a default `COM6` and offers no
  network-only mode. The port was busy, so its serial-assisted recovery check
  could not be run. Add an explicit `--no-serial` mode that still fails closed
  for all network assertions and clearly records that serial-log assertions
  were skipped.
- Aborting a rejected future-schema import changes `importLastResult` to `OK`,
  hiding the immediately preceding validation failure from the state view.
  Consider separate bounded fields for last validation result and last session
  operation, or preserve the failure until the next `BeginConfigImport`.

The previously confirmed release blocker is fixed. `verify_v050.py

### Item 2 (`rebootRequired=false` after reconnect): still fails, different symptom

Severity: release blocker (same completion criterion as before, new root
cause).

`verify_v050.py` failed at `restart-post-commit`: after reconnecting
following the structural commit, `GetConfigState` polled stable for 45s (87
attempts) and never stopped reporting `rebootRequired: true`, even though
`runningRevision == stagedRevision`, `stagedDiffers: false`, and
`importSessionActive: false` the entire time. An independent manual probe
(`probe_reboot_required.py`, ad hoc, not committed) extended the poll window
to 180s with the same result: `rebootRequired` never cleared on its own.

This is a genuinely different defect from the one fixed in `61c104b`, not a
recurrence:

- The restart demonstrably happened (continuous uptime; rebuilt namespace
  verified correct, per item 1 above) -- this is not the old "no restart
  runs at all" bug.
- The defect is specific to the **first** controlled restart after boot.
  Applying a second structural transaction (restoring the original baseline
  through the same `ApplyImportedConfig` -> `model_apply_imported_config()`
  -> `config_service_replace_and_save()` path) cleared `rebootRequired`
  immediately (confirmed on both the `verify_v050.py` run and the manual
  probe: `best-effort-restore-stable`/final restore state read
  `rebootRequired: false` on the very first poll after reconnecting).
- `model_is_reboot_required()` (`opcua_model/src/model_channels.c:105-117`)
  is the sole source of this field, and is the OR of two independently
  computable terms:
  `model_address_space_snapshot_requires_server_restart()` (compares
  `g_model_address_space_config_snapshot`, captured immediately after
  `model_build_address_space()` on every pass through
  `model_core_lifecycle.c`'s per-server-lifetime loop, against the current
  running config) and `model_config_requires_server_reboot(running, staged)`
  (compares `config_service_get()` against `config_service_get_staged()`
  directly). Source reading traced the `ApplyImportedConfig` path to
  `config_service_replace_and_save()` (`services/src/config_service.c:1204-1292`),
  which explicitly syncs `g_staged_config = normalized_config` at commit time
  (`:1277`) immediately before writing the identical value into
  `g_running_config` (`:1284`) -- these two should already be
  content-identical the instant commit returns, which argues against the
  staged/running term as the persistent cause and points at the
  snapshot-vs-running term instead, but this was not confirmed with runtime
  instrumentation. **This session did not reach a confirmed root cause** --
  only the reproduction, its "first restart only" pattern, and the two
  candidate code paths above. Diagnosing further needs runtime
  instrumentation on the actual restart path (counters/logging around
  `g_model_address_space_config_snapshot_valid`,
  `model_address_space_snapshot_requires_server_restart()`, and the
  staged/running sync), the same recommendation the original blocker's
  report made and that was not fully acted on for this specific field.

Reproduction (two independent tool runs, same result both times):

1. Establish a secure authenticated session; export the baseline.
2. Change only a channel's `description` (structural) and commit via
   `BeginConfigImport`/`WriteConfigChunk`/`ValidateImportedConfig`/

3. Old session dies immediately; reconnect succeeds within &lt;1s.
4. `GetConfigState.rebootRequired` stays `true` indefinitely (45s and 180s

### Verdict (superseded below -- kept for the narrative)

v0.5.0 remains not release-ready on the reference hardware. Progress since
the previous run: the old-session-disconnect blocker is fixed and the
namespace rebuild itself is now proven correct. New blocker: the
`rebootRequired` diagnostic does not reliably reflect restart completion,
specifically failing after the first restart of a boot cycle while
succeeding after subsequent ones -- a client (or an operator relying on this
field) cannot use it to determine when a structural change has taken full
effect on first use. Recommended next step before any further hardware
gate: add the runtime instrumentation described above around both terms of
`model_is_reboot_required()` and re-run this same reproduction, since static
reading of `config_service_replace_and_save()` did not reveal an obvious
source-level cause and the "first restart only" pattern suggests a
timing/ordering issue rather than a pure logic bug.

rebuild is proven correct" claim above is wrong.** It was based on
`export_config`'s output changing after commit, which only proves the
*committed configuration* changed -- `export_config` reads
`config_service_get()` directly and never touches the OPC UA namespace. The

## Root cause found via runtime instrumentation (2026-08-30, same day)

Temporary diagnostic `printf`/`fflush` instrumentation was added to
`opcua_model/src/model_channels.c` (`model_is_reboot_required()`, logging
which of its two terms is true and, on a mismatch, which specific config
field differs) and `opcua_model/src/model_core_lifecycle.c`
(`model_config_service_restart_callback()`, the per-iteration fail-closed
check inside `model_core_task`'s serving loop, and every step of the
teardown/rebuild transition: post-loop-break state, `UA_Server_run_shutdown`
return code, `model_context_delete_server` completion, the
`restart_pending` re-check before `continue`, and the top of the `for(;;)`
per-server-lifetime loop). Flashed to the reference device (first via a
corrected USB BOOTSEL `factory_full.uf2` after an initial mistake -- see
below -- then via OTA) and captured over the device's USB debug console
(`COM6`, 115200) while reproducing the same structural transaction
(`BeginConfigImport`/`WriteConfigChunk`/`ValidateImportedConfig`/
`ApplyImportedConfig` changing one channel's `description`), correlated
against network-side evidence from `verify_v050.py` and ad hoc probe
scripts.

**Tooling correction found first**: the initial USB-BOOTSEL delivery
(`build-ota/ota_artifacts/factory_full.uf2`) silently shipped a stale,
non-instrumented image -- `cmake --build ... --target all` does not rebuild
the `ota_artifacts` custom target (`factory_full.bin`/`.uf2`,
`ota_payload.bin`/`.json`); it must be built explicitly
(`--target ota_artifacts`) after the app/bootloader ELFs change. Confirmed
by comparing file timestamps and grepping the binary for the instrumentation
strings before re-sending the corrected file. The same staleness affected
the first OTA attempt's payload.

### Definitive finding: the controlled restart's address-space rebuild never executes

Severity: release blocker (supersedes the earlier "stuck flag, unclear
cause" framing -- this is the actual mechanism).

A decisive test read a **live OPC UA namespace node** directly --
`ns=4;s=Device.Channels.c_<hex channel id>.Description`, one of the
`UA_Server_addVariableNode`-created static properties `model_add_channel_nodes()`
builds in `opcua_model/src/model_address_space.c:1820-1900` -- both before
and after a restart-triggering commit, on the pre-transaction session, and
again after reconnecting to a fresh session. In every case the live node
kept returning the **old** description, while `export_config()` on the same
connections correctly returned the **new** one. This proves the OPC UA
address space is never rebuilt, independent of whatever happens to the
client's session/connection.

Correlated runtime instrumentation traced the full mechanism:

1. `model_config_service_restart_callback()` (`model_core_lifecycle.c:120-141`,
   invoked synchronously from `config_service_run_commit_extensions()`
   inside the same `UA_Server_run_iterate()` call as the committing method)
   **does** fire and **does** correctly detect the need for a restart and
   arm `g_pending_actions.restart_pending = true`. Confirmed directly:
   `restart_callback invoked: requires_restart=1 snapshot_valid=1` followed
   by `restart_callback armed restart_pending=true` on the serial console at
   the exact moment `ApplyImportedConfig` completes.
2. After that, **no rebuild ever happens**: across every reproduction (four
   separate runs, two different instrumented builds, both USB-BOOTSEL and
   OTA delivery), the unconditional per-lifetime-pass log lines
   (`"[DIAG-REBOOT-REQ] for(;;) top: is_restart=..."`, and the pre-existing
   `"Creating server with configured namespace"` / `"Starting server on
   port..."` printfs that fire on every pass including restarts) **never
   appear again** after cold boot's single pass. `model_build_address_space()`
   is therefore never called a second time, so
   `g_model_address_space_config_snapshot` (only ever written right after
   that call, `model_core_lifecycle.c:1064-1072`) never gets refreshed --
   which is exactly why `model_is_reboot_required()`'s snapshot-vs-running
   term (`snapshot_differs=1`, confirmed via the per-field diagnostic:
   every scalar field reports `0`, only `channel[0] differs`) stays true
   forever. The second term (`staged_differs`) was `0` in every observation,
   ruling out `config_service_replace_and_save()`'s staged/running sync
   (`services/src/config_service.c:1276-1288`) as a contributor -- it
   correctly keeps `g_staged_config` and `g_running_config` in sync at
   commit time.
3. **The client-visible symptom is non-deterministic and does not reliably
   indicate whether a rebuild happened** (it never does, but its two
   observed shapes differ): sometimes the pre-transaction session is killed
   immediately (`SecureChannel closed` / `Socket closed` right after
   `ApplyImportedConfig succeeded`) and a new client can reconnect and
   create a session almost instantly on what must still be the *original,
   never-rebuilt* `UA_Server` instance (proven by the live-node test above,
   run specifically against this "session died, reconnect succeeded" shape);
   other times the pre-transaction session is never touched at all and keeps
   serving reads indefinitely (`verify_v050.py`'s own
   `restart-old-session-disconnected` check failed twice in a row this way:
   65 reads over 8s, then a separate run 36 reads over 5s). Neither shape
   correlates with whether `restart_pending` was armed -- both were observed
   with the callback confirmed to have fired. The mechanism that
   occasionally closes the old session in the "looks like a restart"
   shape was not identified; it does not appear to be
   `UA_Server_run_shutdown()` completing normally, since that call's own
   instrumented return code and the subsequent `model_context_delete_server`
   completion were never reached in the same window where a live-node check
   was run to confirm this (the specific run combining live-node evidence
   with the full teardown instrumentation was not completed before hardware
   access became blocked -- see below).
4. **A second, related mechanism is also stuck on the current running image**:
   `Device.Maintenance.Reboot` (`model_schedule_reboot()`, unrelated
   endpoint, arms `g_pending_actions.reboot_pending` with a due-tick) was
   confirmed via serial log to be accepted (`"[OPC UA] Reboot requested"`,
   audit event `result=success details=reboot scheduled`), but never
   actually executes (no `"[OPC UA] Executing scheduled reboot"` line;
   device uptime kept climbing continuously across two separate reboot
   requests roughly 15s and 35s apart, with no drop). Heap/PSRAM were
   confirmed healthy at the time (273 KB free heap, 265 KB min-ever, 3.8 MB
   PSRAM free), ruling out resource exhaustion as the cause. This was only
   observed after roughly 14 minutes of continuous uptime under heavy test
   load (many sessions, a full 3.3 MB OTA payload transfer, many config
   commits); whether it reproduces from a clean boot under lighter load is
   unknown. Both this and the restart mechanism share the same two
   `g_pending_actions` fields and the same consuming loop in
   `model_core_task` (`model_core_lifecycle.c`'s `while(1)`), so this is
   very likely the same underlying defect class, not a coincidence.

### Root cause localized: `UA_Server_run_shutdown(server)` never returns

The device was power-cycled (physical intervention, performed by the
operator -- the reboot deadlock in point 4 above meant no software-only path
was available) and came back up running the fully-instrumented Bank B image
staged earlier via OTA (`otaState` correctly transitioned from
`STAGED_IN_BANK_B` to `IDLE` after this boot, confirming it was consumed).
The decisive live-namespace-node reproduction was then re-run with every
teardown-sequence instrumentation point active. Serial log, in order, with
zero lines elided between them:

```
[DIAG-REBOOT-REQ] restart_callback invoked: requires_restart=1 snapshot_valid=1
[DIAG-REBOOT-REQ] restart_callback armed restart_pending=true
[OPC UA]        ApplyImportedConfig succeeded
[AUDIT] ...event=config-import-apply...result=success...
[DIAG-REBOOT-REQ] post-loop-break: restart_pending=1 reboot_pending=0
[open62541/info]        TCP 3 | SC 3 | SecureChannel closed
[open62541/info]        TCP 3 | Socket closed
[open62541/info]        TCP 3 | Connection opened from "192.168.1.101" via the server socket 0
[open62541/info]        TCP 3 | SC 4 | SecureChannel created
... (new session created and activated normally) ...
[DIAG-REBOOT-REQ] snapshot_differs=1 staged_differs=0
[DIAG-REBOOT-REQ] snapshot-vs-running: channel[0] differs
```

The **only** code between the `post-loop-break` printf and the next
`[DIAG-REBOOT-REQ]` printf in the source (`model_core_lifecycle.c`, right
after the post-loop-break log) is the single call
`status = UA_Server_run_shutdown(server);` followed immediately by a printf
of its return code. That return-code printf **never appears in any
reproduction** (confirmed across every run with this instrumentation
present). `UA_Server_run_shutdown(server)` is therefore the exact call that
never returns.

This is fully consistent with every other observation in this investigation:
the pre-transaction session dies right as this call is entered (matching
open62541's normal shutdown behavior of gracefully closing active
sessions/channels as its first step), but the server clearly keeps running
and keeps servicing new connections/sessions/method calls afterward (new
`SecureChannel`/`Session` created and successfully activated, `GetConfigState`
answered correctly) against the **old, un-rebuilt** address space --
behavior that only makes sense if `UA_Server_run_shutdown()` internally
keeps pumping the server's own event/network loop (e.g. during a configured
shutdown-delay/drain phase) but never reaches the point where it returns
control to its caller. Because it never returns, `model_context_delete_server()`,
the `continue`, and the entire rebuild pass are never reached -- explaining
why `g_model_address_space_config_snapshot` is never refreshed and
`rebootRequired` never clears.

**This also explains the independent `Device.Maintenance.Reboot` deadlock**
(point 4 above): `model_schedule_reboot()`'s hard-reset path is a completely
separate code path (`diag_service_reboot()`, no `UA_Server_run_shutdown`
involved) reached from the *same* `model_core_task` loop -- but only on a
pass where the loop's top-level `while(1)` is actually being re-entered.
Once a controlled restart has hung inside `UA_Server_run_shutdown()`, that
task never returns to any loop that re-checks `reboot_pending`, so a
`Reboot` request issued afterward is accepted (it only sets a flag) but can
never be acted on either. One stuck call explains both symptoms.

**Recommended fix direction** (for whoever picks this up -- not implemented
in this session, which was diagnostic only): investigate open62541's
`UA_Server_run_shutdown()` contract on this version/config -- in particular
whether it expects the caller to keep calling `UA_Server_run_iterate()` a
bounded number of additional times after `run_shutdown()` to let it drain
(a documented pattern in some open62541 versions), rather than being a
single blocking call safe to await synchronously the way
`model_core_lifecycle.c`'s restart path currently calls it. Check
`UA_ServerConfig`'s shutdown-delay-related field(s) and whether this
server's config sets one. Confirm the fix by re-running this session's exact
reproduction (live-namespace-node read before/after) rather than relying on
session-liveness alone, which -- as this whole investigation shows -- is not
a reliable signal of a successful rebuild.

### Recommended next steps

1. Fix `UA_Server_run_shutdown()` not returning in the controlled-restart
   path (`model_core_lifecycle.c`, right after the `post-loop-break` log --
   see root cause above) and independently confirm `Device.Maintenance.Reboot`

2. Confirm the fix using a live-namespace-node read (as in this session),
   not session-liveness -- this investigation showed session-liveness alone
   produces false positives and false negatives for whether a rebuild

3. Remove all `[DIAG-REBOOT-REQ]` temporary instrumentation

## Root cause confirmed and fixed (2026-09-01)

### Two separate bugs, not one

This session started by upgrading open62541 v1.5.3 -> v1.5.7 on the theory
that the restart hang above was the known, already-fixed (in v1.5.4) lwIP
EventLoop mutex-alignment bug. That upgrade surfaced an **unrelated** new
defect first: a deterministic hardware-watchdog reset during namespace-zero
construction. Root cause: `namespace0_generated()`'s amalgamated dispatcher
does not call each node's `_begin()`/`_finish()` as adjacent pairs -- it
batches **all** ~5320 `_begin()` calls first (zero interleaved `_finish()`
calls), then all `_finish()` calls in reverse order. A watchdog checkpoint
keyed to `_finish()` only, or to begin/finish pairs, goes silent for that
entire begin-only stretch -- long enough to trip the 16 s effective hardware
watchdog window (a 24-bit microsecond load register hard-caps the
requested 80 s down to ~16.7 s). Fix: kick the watchdog after **every
individual** call, begin or finish (`port/open62541/open62541.c`,
`rp2_open62541_ns0_tick`/`rp2_open62541_wdog_kick`, applied at the
dispatcher level and after every `UA_Server_addReference()` call). A second,
independent fix from the same investigation: node 4429 ("Mandatory", 2345
references) made GCC `-Og` reserve one debug stack slot per inline
`UA_NODEID`/`UA_EXPANDEDNODEID` compound literal (~169 KiB total for that
one function); factored into the bounded helper
`rp2_namespace0_addMandatoryReference()` so only one set of temporaries is
live at a time (guarded by
`static/tools/test_open62541_ns0_stack_bound.py`).

With that fixed, the device booted reliably -- but re-running this
document's own restart-hang reproduction (`probe_reboot_required.py`)
showed **the original bug was still present, unchanged, on v1.5.7**. The
v1.5.4 mutex fix was never the relevant one.

### The actual root cause

Confirmed on hardware with a per-iteration trace of `model_core_task`'s run
loop: the commit callback correctly arms `restart_pending`, the loop
correctly breaks on it, and `UA_Server_run_shutdown(server)` is correctly
called -- and then never returns, while the serial log shows the *old*
server object still accepting and fully activating **new** incoming
connections (`SecureChannel created` / `Session created` / `ActivateSession`)
after that point.

Traced into open62541 itself (`port/open62541/open62541.c`):
`UA_Server_run_shutdown()`'s drain loop
(`while(!testStoppedCondition(server) ...) { el->run(el, 100); }`) waits for
`UA_BinaryProtocolManager`'s open `channels` list to become empty before
transitioning to `STOPPED`. But `serverNetworkCallbackLocked()`, the
listening socket's event callback, creates a new `SecureChannel` for **any**
new connection unconditionally -- it never checks whether the component's
own lifecycle state is already `STOPPING`. Any client that reconnects during
the drain window (completely normal client behavior -- it is exactly what a
retrying OPC UA client, or this project's own test tooling, does) keeps the
channel list non-empty forever, so `testStoppedCondition()` never becomes
true and the call never returns. This is upstream open62541 behavior,
confirmed present in both the v1.5.3 and v1.5.7 amalgamations (byte-identical
`lockServer`/`unlockServer`/shutdown-drain logic in both) -- not a
version-specific regression, and not fixed by any lwIP/EventLoop mutex
change.

### Fix: bounded fallback to the existing hard-reboot path

`UA_Server_run_shutdown()` is a single blocking call on `OpcUaTask`, which
cannot time itself out of its own call. `model_core_lifecycle.c` now arms a
one-shot FreeRTOS software timer (`model_get_shutdown_deadline_timer()`,
8000 ms) on the independent Timer Service Task immediately before calling
it, and disarms it immediately after. If the timer fires first, the call is
presumed stuck in the livelock above and `diag_service_reboot()` -- the same
hardware-watchdog-based hard reset already used for the unrelated
`Device.Maintenance.Reboot` path -- is used as a fallback. It fires via
`watchdog_reboot()`'s countdown in silicon, so it works regardless of what
`OpcUaTask` is doing, unlike any FreeRTOS-task-cooperative timeout would.

No open62541 patch was needed; this stays entirely in application code,
per the deliberate choice to avoid carrying a delta against future open62541
upgrades for this one behavior.

**Verified on hardware** (`probe_reboot_required.py`, same reproduction as
throughout this document): commit -> `restart_pending` armed -> loop breaks
-> `UA_Server_run_shutdown()` blocked by a reconnecting client -> timer
fires at 8 s -> `diag_service_reboot()` -> genuine cold boot (`PSRAM init
ok` / `Booting RP2 Basic Device` / `for(;;) top: is_restart=0`) -> device
reachable again -> `rebootRequired` correctly clears (~28 s total: ~8 s
livelock detection + hard reboot + ~19 s network reconnect) and the address
space matches the newly-committed configuration. Reproduced twice, on two
separate builds (before and after removing the temporary diagnostic
instrumentation below), with matching results both times.

**Known, accepted tradeoff**: v0.5.0 T6's original design intent was a
*fast, in-process* controlled restart. Because any live/reconnecting client
triggers the open62541 livelock above, a structural config commit now costs
the full ~15-20 s hard-reboot fallback in practice whenever a client is
present -- which is the common case, not the exception. This is a
deliberate, verified-safe trade (bounded, self-recovering) in place of the
previous behavior (unbounded hang, `rebootRequired` stuck `true` forever,
recoverable only by a physical power cycle), not a hidden regression.

## Full checklist re-verified on the final build (2026-09-01, continued)

Re-ran `static/tools/verify_v050.py --reboot-verify --verify-presets`
(bounded 60 s reconnect/stability timeouts, generous for the fix's ~28 s
worst-case controlled-restart recovery) against the fixed, cleaned-up build.
This single script exercises nearly all of the original checklist in one
pass: baseline read/identity/compatibility, rejection paths, a non-structural
transaction, a structural transaction (apply + restore), an explicit
`Device.Maintenance.Reboot`, and all three configuration presets
(`sensor_node`, `remote_io`, `dev_benchmark`) applied and restored in turn.

**Passed, in order** (each entry below is one bounded reconnect/verify step
that this run's evidence file, `build/reports/verify_v050_hardware.json`,
recorded as green): baseline config-state/identity read, recovery-export
written, future-schema-version rejection, missing-driver-ID rejection
(running config unchanged in both cases), a non-structural (`alarmHysteresis`)
transaction that preserved the session, a structural (`description`)
transaction's full apply -> restart -> reconnect -> restore -> restart ->
reconnect cycle (the fix under test, exercised twice more here on top of the
dedicated reproduction earlier in this document), explicit `Reboot` verified
to preserve the restored configuration, and the `sensor_node` preset's full
apply/restore cycle. That is six independent controlled-restart cycles in a
row, all recovering correctly within the bounded timeout.

**Failed on the seventh cycle in a row** (`remote_io` preset's restore-to-
baseline step): `no reconnect in 60.0s`. The device stopped responding on
both the network and, briefly, the serial console; the OPC UA layer itself
was not confirmed hung (no crash-loop reboot banners were captured in that
window, unlike every other reset in this investigation, which always
re-announced itself over serial within a few seconds). A physical power
cycle (not a soft reset) immediately restored both serial and network
connectivity, with the persisted configuration intact and matching the
pre-test baseline (`payloadCrc32` unchanged, `rebootRequired=false`).

### Root cause of the seventh-cycle failure: W5500 has no reset pin

This board's boot log has always read `[W5x00] Reset pin not connected,
relying on power-on reset` -- the W5500 Ethernet controller's hardware
RESET pin is not wired to the RP2350. It can only be truly reset by a genuine
power-on event, never by a software-triggered MCU reboot (which is exactly
what both this session's fix and the pre-existing `reboot_pending` hard-reset
path use, via `watchdog_reboot()`). Six software reboots inside about five
minutes -- unrealistic for how an operator would actually use this feature
in production, but exactly what `--verify-presets`'s automated back-to-back
sequence does -- were absorbed fine; the W5500 apparently accumulated enough
internal state drift by the seventh that it stopped recovering
(`[NET] MACRAW socket recovery failed: len=60 sr=0x00 count=1` was observed
in the serial log shortly before connectivity was lost). This is a board
hardware-design limitation shared by every software-triggered reboot path in
this firmware, not something introduced by this session's fix, and not
something a software change to the restart/reboot logic can work around
without also touching the W5500 driver's own recovery path (out of scope for
this session).

**Practical impact**: a single structural configuration change -- the actual
production use case -- is unaffected; this only surfaced after six
back-to-back automated cycles. Documented here as a known limitation rather
than fixed, since fixing it would mean either wiring the W5500's reset pin
(hardware change, next board revision) or building software-level detection
and recovery for a degraded W5500 link (a separate investigation).
