# v0.3.2 — Maintenance Workflow Core

## Status

Unreleased.

This is the execution plan for the first unreleased version in `ROADMAP.md`.
`ROADMAP.md` remains authoritative if the two documents disagree.

The release adds a volatile, service-owned AMB maintenance workflow. It does not
add persistence, Historical Event Access, new AMB states, or a general event
historian.

## Release objective

Deliver a remotely callable maintenance workflow in which:

- `maintenance_service` is the sole owner of maintenance runtime state;
- its public API contains no open62541 types;
- OPC UA callbacks validate and convert inputs, enforce existing role policy,
  call the service, synchronize model fields, and emit live events;
- all activity data has explicit bounds;
- state changes are atomic and failures leave state unchanged;
- existing public NodeIds and BrowseNames remain stable;
- firmware, OTA metadata, and configuration export report `0.3.2` from one
  version source.

Maintenance state remains volatile across reset in this release.

## Required state model

Supported states:

- `Planned`;
- `Executing`;
- `Finished`.

Allowed transitions:

| Operation | Source state | Result state | Transition event |
| --- | --- | --- | --- |
| `PlanMaintenance` | `Finished` | `Planned` | Exactly one |
| `StartMaintenance` | `Planned` | `Executing` | Exactly one |
| `FinishMaintenance` | `Executing` | `Finished` | Exactly one |

`RescheduleMaintenance` is an update while remaining in `Planned`; it is not a
state transition. The method contract must state whether it emits a non-transition
update event, but it must not be counted as a transition event.

Do not add `Cancelled`, `Failed`, `Aborted`, or any vendor state.

All updates to `CurrentState`, `CurrentState.Id`, planned fields, optional AMB
fields, and condition metadata must be derived from one successful
service-owned transaction.

## Required method contracts

Implement only:

- `PlanMaintenance`;
- `RescheduleMaintenance`;
- `StartMaintenance`;
- `FinishMaintenance`.

Before implementation, document for each method:

- input and output names and OPC UA data types;
- native bounded representation;
- maximum string and collection lengths;
- permitted roles;
- valid source and resulting state;
- validation order;
- service result and OPC UA status-code mapping;
- fields updated atomically;
- event behavior.

Rejected calls must not mutate state or emit a transition event.

## Execution plan

### T1 — Map the existing implementation

Owner: primary agent with `code-mapper`.

This task is a hard pre-coding gate.

Completion criteria:

- current AMB construction and verification tooling were inspected;
- all relevant files, symbols, NodeIds, callbacks, role checks, and event paths
  are mapped;
- every current direct maintenance-field write is identified;
- public compatibility constraints and reusable helpers are known.

### T2 — Produce the file-level design

Owners: primary agent with `embedded-systems` and `iot-engineer`.

Design at least:

- `services/include/services/maintenance_service.h`;
- `services/src/maintenance_service.c`;
- service registration in `services/CMakeLists.txt`;
- changes to `opcua_model/src/opcua_model.c`;
- verification-tool changes;
- affected version-generation files;
- affected public documentation.

Completion criteria:

- one volatile state owner;
- public service API contains no open62541 types;
- `maintenance_activity_t` contains every roadmap-required field with explicit
  bounds;
- synchronization, transaction, snapshot, and failure semantics are explicit;
- method signatures, permissions, status mappings, and event rules are
  documented;
- no v0.3.3+ dependency is required.

No implementation may begin before T1 and T2 are complete.

### T3 — Implement `maintenance_service`

Owner: `embedded-systems`.

Implement:

- bounded activity and state storage;
- initialization and coherent state query/snapshot;
- planning, rescheduling, starting, and finishing commands;
- only the allowed transitions;
- deterministic result codes;
- atomic updates;
- unchanged state on rejection.

Completion criteria:

- all runtime maintenance state is service-owned;
- no open62541 dependency exists in the public API;
- no unbounded storage or borrowed lifetime is introduced;
- no persistence or hardware access is added.

### T4 — Integrate the OPC UA model

Owner: `iot-engineer`.

Implement adapters that:

1. validate argument count, shape, type, and bounds;
2. resolve the current authenticated role through existing mechanisms;
3. reject unauthorized calls before mutation;
4. convert arguments into native service types;
5. invoke `maintenance_service`;
6. map results deterministically;
7. update OPC UA-visible state from a coherent service result/snapshot;
8. synchronize `CurrentState` text and `CurrentState.Id`;
9. update planned and optional AMB fields;
10. emit exactly one live transition event after success.

Completion criteria:

- callbacks contain no maintenance state machine;
- no model callback directly owns or mutates maintenance business state;
- existing NodeIds and BrowseNames are preserved;
- rejected calls leave model/service state unchanged and emit no transition
  event.

### T5 — Establish one version source

Owner: primary agent with `build-engineer`.

Completion criteria:

- the authoritative version is `0.3.2`;
- runtime firmware, OTA metadata, and configuration export derive from it;
- independent stale version literals in active release paths are removed;
- generated artifacts agree on the version.

Do not introduce the broader v0.3.4 release-automation scope.

### T6 — Implement automated verification

Owner: `iot-engineer`.

Extend `static/tools/verify_amb_model.py` or add
`static/tools/verify_maintenance_workflow.py`.

The automated matrix must cover:

- every method;
- every allowed transition;
- every method from every forbidden source state;
- viewer/operator/service/admin authorization;
- missing, wrong-type, invalid, maximum-length, and oversized arguments;
- unchanged state after every rejection;
- synchronized state text and state NodeId;
- exactly one transition event after every successful transition;
- no transition event after rejection;
- two simultaneous subscribed clients observing one event each for the same
  successful transition;
- nonzero process exit on any failed assertion.

Use the documented contracts as expected results rather than accepting whatever
the server currently returns.

## Stop conditions

Stop and report the blocker if:

- this plan conflicts with `ROADMAP.md`;
- verified AMB NodeIds or existing public contracts cannot be determined;
- safe bounded activity fields or atomic synchronization cannot be defined;
- required work depends on Flash journal, reboot restoration, Historical Event
  Access, or another later-release feature;
- unrelated working-tree changes overlap a required file and ownership cannot be
  resolved;
- completing the work would require weakening authorization, compatibility, or
  deterministic failure guarantees.

Do not edit the roadmap merely to bypass a stop condition.

## Release completion criteria

The release is complete only when:

- T1 through T11 are complete;
- all v0.3.2 roadmap implementation and acceptance items pass;
- the general roadmap definition of done is satisfied;
- automated checks fail correctly when assertions fail;
- independent review findings are resolved or explicitly justified;
- no later-release functionality or unrelated changes were introduced;
- implementation, generated artifacts, tests, and documentation agree;
- any unavailable hardware, UaExpert, or network validation is clearly reported;
- the final report states which roadmap acceptance items are satisfied without
  modifying `ROADMAP.md`.
